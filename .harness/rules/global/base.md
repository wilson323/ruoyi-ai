# 团队通用规则（Global Base）

> Layer 1 的延伸层。`type: always` 表示每次会话自动注入，不需要按需引用。
> 体量纪律：本文件 ≤ 80 行。超出部分拆到 `rules/<lang>/` 或做成 Skill。

## 一、架构约束（硬性红线）

1. 严格遵循项目声明的分层架构，不得跨层直接调用
2. 业务逻辑不得写在入口/控制器层，入口层只做参数校验与响应封装
3. 所有数据库操作必须经过数据访问层，禁止在业务层直接写 SQL
4. 所有对外接口必须包含接口文档注解

## 二、代码风格

1. 函数/方法必须有简要注释说明用途
2. 错误处理**不允许**使用 `_` 或空 catch 忽略，必须显式处理或向上传递
3. 单个函数不超过 80 行，超过则拆分
4. 命名跟随语言惯例，且全项目一致

## 三、安全策略

1. 涉及数据库结构变更时，**优先生成变更脚本**，而非直接执行
2. 删除、移动文件无需额外确认；**涉及数据库结构修改必须确认**
3. 所有敏感配置（密钥、连接串）必须通过配置中心或环境变量读取，**禁止硬编码**
4. 任何输出给外部的文本，先过 PII 扫描（Skill `pii-desensitization-gate`）

## 四、开发行为

1. 添加新功能前**必须先分析现有代码库**，优先复用已有模块
2. **代码变更范围最小化**：一次 PR 只解决一个问题
3. 每次变更必须附带清晰的 commit 信息
4. 新增功能**必须同步编写单元测试**
5. 遇到"AI 第二次犯的同一个错"，按 `README.md §2` 决策树写进对应层

## 五、证据纪律

1. 任何"完成"声称必须附可执行的验证命令 + 真实输出
2. 验证证据写入 `plan.md`，不是写在聊天里
3. 证据不足时返回 **证据不足**，不返回"通过"或"失败"

## 六、五条禁止（违反即阻断）

- 禁止 `git add -A`（必须按路径或 patch 精确暂存）
- 禁止用 `rm -rf` 清理 git worktree（必须用 `git worktree remove`）
- 禁止静默 fallback 到假数据/旧缓存（查询失败必须停 + 提示）
- 禁止为了通过测试而修改生产逻辑
- 禁止未确认技术方案就写代码
