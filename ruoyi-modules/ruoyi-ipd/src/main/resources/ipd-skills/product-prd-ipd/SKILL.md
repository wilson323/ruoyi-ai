# P01 产品需求规格定义（PRD）

## 目标

产出**产品需求规格书 PRD**。G2-1：条目化 100%，每条含优先级与验收标准；未上传有效 PRD 否决（Gate / DOC-05）。

## 输入

C03/C06 概念与客群、C02 差异点、约束与非功能、干系人、既有 PRD 草稿。仅本项目资料 + 用户输入。

## 步骤

1. **定模式**（先读既有稿再写）：A 从零；B 评审已有稿；C 增量补模块（用「本次更新」标注，不整篇覆盖）。资料不足先列缺项。
2. **三视角门禁**（动笔前）：用户（痛点是否有一手证据）、商业（是否对齐 C08/卖点）、技术（研发可实现线索）。任一项无证据标「未取得」，不硬写长文。
3. **概念对齐 → 落地展开**：先交方向摘要（为谁/解决何问题/不做清单）；用户未确认前不堆实现细节。落地版默认只展开首版 Must（MVP 闸门）；Should/Could 可仅列名。
4. **产品类型侧重**（用户声明或资料可判时）：B2B 补权限/租户/集成；平台型补多角色；硬件/方案补接口与约束字段。无依据不臆造类型专章。
5. **需求条目化**：每条含 ID、描述、优先级、验收标准、来源；无验收标准列入缺项，不得计入「可提交 G2」。
6. **盲区自检**：空态/错误态、关键状态迁移、双受众文案（规格 vs 对客）、非功能（性能/安全/合规）—仅在用户或资料给出范围时展开。
7. **可选·交互说明骨架**（软件类且用户要求演示时）：先拆页面单元与跳转（导航地图级），再谈原型；不在本动作内启动通用网页生成器或第二套 MCP。原型为抛开验证，不得冒充已验收交付物。
8. 输出「模式与资料核对 / 概念摘要 / 条目表 / 自检结果 / 缺项清单」。

## 禁止事项

- 禁止方向未对齐就「一稿到底」堆细节。
- 禁止编造验收标准或未确认的 MVP 范围。
- 禁止代签 G2 或宣称 PRD 已基线冻结。
- 禁止把 HTML/原型工程当 PRD 本体替代条目化。

依据：QoderWork「PRD生成」；VibePM prd-writer 门禁；prd-html / 职场产品人七阶段（方法并入步骤 7）；上游 create-prd；五大 Gate G2-1；DOC-05。
