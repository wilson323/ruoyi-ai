## 3. 根因诊断

### 3.1 Warning#1 — 清空 thresholdJson 静默不落库（数据一致性 S2）

**根因**：全局 MyBatis-Plus `updateStrategy=NOT_NULL`（common-mybatis.yml:32）使 `updateById` **跳过 null 列**。Service.update() 将空串归一为 null 后，清空操作不落库，但接口返回"已清空" → 前后端状态不一致。

**证据链**：
```
$ 磁盘核对三要素
1. GateElement.thresholdJson 无 @TableField 注解（默认继承全局 NOT_NULL）
2. common-mybatis.yml:32 update-strategy: NOT_NULL
3. GateElementService.update() L165-167: isBlank() ? null : ... 后 updateById(merged)
→ 清空时 thresholdJson=null 被 NOT_NULL 策略跳过，UPDATE SQL 不含该列
```

**修复**：`GateElement.thresholdJson` 加 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`，强制回写该列（含 null）。

**为什么之前没拦住**：单测用 Mockito 绕过真 SQL；只有 DB 回读证（ZCL 清空→NULL）才能暴露。→ 回灌：清空类语义必须有 DB 回读断言，不能只验接口返回。

### 3.2 vite 后台进程 SIGTTIN 挂起 → 误判为浏览器 MCP 僵尸

**根因**：2nd vite 启动命令 `nohup pnpm vite ... > log 2>&1 &` **未重定向 stdin**。vite dev server 监听键盘输入(h/r/q/o)，后台运行时读控制终端 stdin → **SIGTTIN → 进程被 stopped(T 态)** → 端口在但不 serve（curl HTTP 000）→ 浏览器 CDP `Network.enable timed out`。

**误诊**：前两次判为"浏览器 MCP/Chromium 僵尸态"，实为 vite 挂起拖死 CDP 管道。

**证据链**：
```
$ ps -o pid,stat -p 31408   → TN(stopped)
$ curl 15667/                → HTTP 000 in 5.001s(超时)
$ 修复：nohup pnpm vite ... < /dev/null > log 2>&1 &   # stdin=EOF，杜绝 SIGTTIN
$ ps -o stat -p 64298        → SN(正常睡眠)
$ curl 15667/                → HTTP 200 in 0.02s ✅
```

**回灌**：后台起 dev server 必须 `< /dev/null`（或 setsid 脱离终端）。

### 3.3 elementCode 长度前后端错配（存量，非本次引入）
