## 三、深度反思 — 5 大根因(为什么 R3-R48 跨 22 轮反复)

### 根因 1:mock 单测假绿陷阱(R46.1 A3 + P-DATA-gap-1 实证)

**病征**:A3 接线单测全绿(3/3 / 16/16),真库 bonus_allocations 表 0 行,JVM 加载的代码是 A3 接线之前的版本。

**根因**:
- mock 造了真库不可能产生的数据组合(如 PENDING_SECOND 态配 confirmerId、`decision IS NULL` 但无任何生产者落 NULL 行)
- 单测契约 vs 真活契约 缺对账机制
- b1e8e713 红线「mock 单测全绿不等于真活全绿」反复触发但缺机制化

**根治建议**:每写一个 mock 测试必带真活 SQL 验证(写测试时规约见 `.claude/skills/gen-test/SKILL.md`)。

### 根因 2:汇总卡失真(R48 实证)

**病征**:5 张汇总卡 title 写"子卡已全 done 待 owner 翻",实际核实发现 P4-4 子卡 inprogress,不是 done。

**根因**:
- title 是手写文本,不是数据库约束
- 看板 PUT 是整体替换语义且单卡 GET 可能返回空描述 → 覆盖丢失陷阱
- 缺 Fresh 验证铁律:看板 PUT 后必须独立 GET 回读核验

**根治建议**:汇总卡翻 done 前必跑 `manage.py list {card_id}` Fresh 回读子卡状态。

### 根因 3:多轮反复 R3-R48 跨 22 轮(本轮最深反思)

**病征**:R3 / R6 / R11 / R15 / R25 / R30 / R37 / R39-R48,每轮都重新判断一次什么算 done。

**根因**:
- 缺 1 个统一的"项目终态判定标准"(49 页业务环节对应多少 AC / AC 与代码对应多少用例 / 用例与真活对应多少三证律)
- 治理轮越拉越长 → 失真风险累积 → 每轮重做
- SSOT(开发计划-看板镜像.md) + log.md + R 系列报告 三事实源无强制对账

**根治建议**:R49 后,固定一个"项目终态判定检查表",每轮 loop 必须先跑这个表。

### 根因 4:数据治理与业务割裂(P-DATA-gap-1/2 + P3-LOW 实证)

**病征**:bonus_allocations 实体零引用 + project_scores 表 0 行 + sys_user↔persons 字符集不一致。

**根因**:
- 架构上"先建表 + 再写 Service"导致实体零引用(19 轮反复)
- 字符集不一致是历史迁移遗留,缺统一的 ALTER TABLE 收敛策略
- DDL apply 与代码 commit 缺强制时序保证

**根治建议**:DDL 必带 Service 接线 + 字符集治理 Q3 启动 + DDL apply 与 commit 同步登记。

### 根因 5:前端后端事实源不统一(跨仓 R41 教训)

**病征**:前端仓有兄弟会话 M 改动,主协调会话无法同步事实源。

**根因**:
- `docs/开发说明/` + `docs/ipd-系统说明/` 是后端事实源,前端仓有独立 `apps/web-antd/` 事实源
- 跨仓 cd 必严格 `cd 绝对路径 &&` 开头但仍可能漂
- OPS-09 单写者约束的是"同时只有一个会话改",不约束"改完事实源同步"

**根治建议**:跨仓事实源强对账(R25 病根 ⑤ 实质化)。
