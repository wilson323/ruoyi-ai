### 1.1 本轮新发现的 3 条技术事实（6 份方案全部漏了，且直接改变结论）

#### 发现 D · 好消息：官方**有** 1,446 行可执行白名单校验层，D2 步骤 4 高估了 2.5 人天

**【实证】**：

```
agentscope-core/src/main/java/io/agentscope/core/tool/coding/
  CommandValidator.java          185 行   interface: ValidationResult validate(String command, Set<String> allowedCommands)
  UnixCommandValidator.java      215 行   剥 .sh/.py/.rb/.pl/.bash/.zsh 后比对白名单
  WindowsCommandValidator.java   247 行
  ShellCommandTool.java          799 行   implements AgentTool，走 ProcessBuilder 本地执行
                                   ────
                                   1,446 行
```

`UnixCommandValidator:54-56` 明确「whitelist 未配置则放行（向后兼容）」，`:89` 拒绝时给出 `"Command '...' is not in the allowed whitelist"`。

**但官方没有「沙箱 + 白名单」的组合点**：

| 路径 | 沙箱执行 | 白名单校验 |
|---|---|---|
| `core` `ShellCommandTool`（799 行，`ProcessBuilder`） | ❌ 本地进程 | ✅ `CommandValidator` |
| `harness` `ShellExecuteTool`（99 行薄委托 → `AbstractSandboxFilesystem.execute`） | ✅ 沙箱 | ❌ 无 |

**结论修正**：D2 步骤 4 原写「官方工具层**不存在**可执行白名单这一校验层，**必须从零自建**，工程量按「自建一整层」估算」→ **错误**。真相比"从零自建"好得多：**把官方现成的 1,446 行 `CommandValidator` 桥接到 `AbstractSandboxFilesystem.execute` 前面，加一个内部调用标记旁路**即可。

- v1 估 4.0 人天 → **修正为 1.5 人天（省 2.5 人天）**
- 诚实边界：桥接后仍需验证 `BaseSandboxFilesystem` 的 7 处自造 shell 命令（`readFile`/`listFiles`/`globFiles`/`grepFiles`/`editFile` 等）不被误杀——这个坑 D2 已识别，解法未给，**仍是步骤内最难点**。

## 2. 【新增章】与 owner 目标冲突的技术事实：逐项出路与代价对比

> **本章是 owner 点名要求的「不要含糊也不要迎合」。** 每一条冲突给出 (a) 在官方抽象内自建 / (b) 放宽官方约束 / (c) 放弃该能力 三条出路的代价。**owner 必须逐条选。**

### 2.1 🔴 冲突 1 · 图原语（节点 / 边 / 条件边 / 并行子图）

**事实**：`harness` + `core` 全仓零图原语。`HarnessAgent` 是 `ReActAgent` 的一层包装，其编排只有 middleware 栈 + `agent_spawn`。

| 出路 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **(a) 官方抽象内自建** | 在 `HarnessAgent.builder()` 上挂一组自研 `MiddlewareBase`：`RouteDecisionMiddleware.onModelCall`（路由决策，占用官方零实现的空置扩展点）+ `RunStatePersistMiddleware.onAgentStateReady`（状态落 `AgentStateStore`）+ `NodeLifecycleMiddleware.onAgent`。图定义编译成一份可序列化执行计划存在 `AgentState` | **+3.0 人天**（相对原 W3 估）；**长期多一套 261 行编译层** | 🔴 **R-1 执行顺序隐式化**：19 个官方 middleware **无一覆盖 `order()`**（实证：`MiddlewareBase.java:121` 只有默认实现），全默认 `order=1` 按注册序执行。图的控制流将**取决于 builder 调用里那几行的排列**——改一行无关代码可能悄悄改变执行顺序。必须所有自研 middleware 显式 `order()` + 命名常量 + 装配面顺序断言单测 |
| **(b) 放宽官方约束** | fork `agentscope-java`，在 `agentscope-harness` 里加 `StateGraph` 抽象 | 表面 0 人天 | 🔴🔴 **强烈不推荐**：改官方源码 = **双轨维护**（本仓一份 + fork 一份），正是 owner 要消除的东西。且本仓 `pom.xml:16` 钉 `agentscope.version = 2.0.3`，fork 后每次官方升级都要重打补丁。**这是用一种双轨换另一种双轨** |
| **(c) 放弃该能力** | aiflow 编排整体下线，AI 工作流改走 `ruoyi-aiflow` 之外的路径 / 或接受「只有 ReAct 循环，没有可视编排」 | 0 人天 | 🔴 **业务影响**：`ruoyi-aiflow` 是 49 页 IPD 前端里「AI 工作流设计器」的后端。放弃 = 该页面失去后端。**需 owner 确认业务可接受** |

**我的建议：(a)**。(b) 违背 owner 初衷；(c) 砍业务范围。

### 2.2 🔴 冲突 2 · Fan-in join（等并行分支全部完成再继续）

**事实**：官方无 join 原语。`WaitAsyncResultsTool(wait_all=true)` 是**异步工具结果 barrier**，语义是"等工具调用返回"，不是"等图分支走完"。

| 出路 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **(a) 官方抽象内自建** | join 语义落在自研 `RunState`（`AgentState` 里的 `pendingBranches: Set<nodeId>`）+ `RouteDecisionMiddleware` 判定"分支全到齐才放行" | **+1.5 人天** | 中。状态落 `AgentStateStore`（官方契约），崩溃恢复时 `pendingBranches` 需与 `t_workflow_runtime_node` 对账 |
| **(b) 放宽官方约束** | 复用 `WaitAsyncResultsTool` + `TaskRepository`（官方后台任务）当分支完成信号 | +0.5 人天 | 🔴 **语义不等价**：`TaskRepository` 生命周期是"一个后台 task"，`WorkspaceTaskRepository` 的孤儿判定（心跳 30s / 孤儿 10min / sweep 5min）**只把任务标 FAILED，不重跑**。用 timeout 判分支失败 = **静默丢分支**。**不推荐** |
| **(c) 放弃该能力** | 明确「并行分支不等待，全部跑完取并集」 | 0 人天 | 🔴 **改变业务语义**：`WorkflowEngine.errorWhenExe()` 现在硬编码「并行节点中不能包含条件分支」，说明现有图**已经有**并行分支。放弃 join = 并行分支的结果不能汇聚到后续节点。**需 owner 确认 IPD 工作流是否真的依赖汇聚** |

**我的建议：(a)**。(c) 会让现有并行分支能力失效。

### 2.3 🔴 冲突 3 · 步骤级 checkpoint / 断点续跑（`JdbcCheckpointSaver` 官方无对应物）

**事实**：全仓 `Checkpoint` 零命中。owner 点名的「结论『自建 `WorkflowCheckpointStore`』作废，必须落在官方契约内」——**可以满足**，但代价形态与 v1 假设不同。

| 出路 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **(a) 落在官方契约内** | 把「`run_id` / `node_id` / `next_node_id` / `epoch` / 已完成节点集 / 上游输出」全部编码成官方 `AgentState` 的一个 State，`AgentStateStore.save(userId, sessionId, key, state)` 持久化。**不再自建 store、不再自建序列化** | **+1.0 人天**（相对原估）；**且消除 DDL 依赖** | 🟢 低。`AgentStateStore` 是官方接口，本仓已有 3 个实现（`FailClosedAgentStateStore` / `ProjectAgentTemporaryStateStore` / `RedisAgentStateStore`）。⚠️ **注意**：`t_workflow_runtime_node` 表的现有数据需一次性迁到 Redis State（或保留双读过渡），这是**数据迁移**成本，估 +0.5 人天 |
| **(b) 放宽官方约束** | 保留 `t_workflow_checkpoint` 表 + `JdbcCheckpointSaver`（现状） | 0 人天 | 🔴 **违背 owner 目标**：这是明确的双轨（业务表 checkpoint + 官方 `AgentStateStore`） |
| **(c) 放弃断点续跑** | 进程崩溃后 run 直接标 FAILED，人工重跑 | 0 人天 | 🔴 **业务影响**：现有 `WorkflowEngine.rebuildCompletedNodes():366-396` 已实证「复杂图 resume 节点 IO 重建保真度**待生产验证**」——说明**这条路本来就还没验证过**。放弃 = 承认现状无保障。**需 owner 确认** |

**我的建议：(a)**。附带收益：**D5 §6.3 层 3 要求的 `t_workflow_runtime` 新增 `scope_key` 列（DDL + DBA 窗口 + owner 拍板）可以取消**——租户维改由 `KernelScopeKey` 复合 `sessionId` 承载，走 `AgentStateStore` 的 `(userId, sessionId)` 二元寻址。**这消掉了 v1 的 O4 这个 owner 门。**

### 2.4 🟠 降级项 4 · outbox 事务保证（官方抽象内不可得）

**事实**：`BaseStore` 接口**无事务方法**（实证：`putIfVersion` 是唯一的原子原语）。`MessageBus` 是队列消费模型（`queuePush`/`inboxPush`），**无事务边界**。官方**无 outbox 概念**。

| 出路 | 代价 | 风险 |
|---|---|---|
| **(a) 降级为「业务 DB outbox 权威 + `MessageBus` 消费」** | **+2.0 人天**；**且这是降级不是归位**——事务性由业务 MySQL 承担，官方通道只做投递 | 🟠 中。必须写进 ADR：「outbox 事务保证**保留在业务侧**，官方 `MessageBus` 只承担投递，**不构成官方归位**」 |
| **(b) 放弃事务保证** | 0 | 🔴 `HarnessEventOutboxService`（1,658 行 `event/` 包的一部分）存在的全部理由就是"事件先落库再投递"。放弃 = 崩溃时事件丢失 |
| **(c) 全部改走 `TranscriptStore.appendSegment`** | +1.0 人天 | 🟠 `appendSegment` 是**调用方自选 seq 的追加写，无 CAS**（实证：`TranscriptStore.java:41` 注释 "seqStart inclusive start sequence (caller-assigned, contiguous preferred)"，接口 6 个方法无任何 CAS 语义）。并发写会 seq 重叠 |

**我的建议：(a)**，并接受"这不是彻底归位"的诚实登记。

## 7. 验收可行性（v2 增量）

v1 已列 12 项验收缺陷，**全部继续成立**。v2 新增 5 项：

| # | 步骤 | 缺陷 | 说明 |

| **17** | 7-2（W3 彻底化版） | 🔴 **验收标准需重写** | v1 已指出的「旧编译器 vs 新编译器断言一致」在彻底化后**不适用**——旧编译器依赖 `StateGraph`（要被删）。新的等价性判据应是「**同一份 DB 边表 → 同一份执行计划**」+「**新旧两条实现对同一图产出的节点集合/分支映射/并行分组一致**」，需在 W2 与 W3 之间**并行维护两套实现**直到 W5。**这个"双实现维护期"本身是 owner 反双轨目标的对立面，需 owner 明确豁免** |
