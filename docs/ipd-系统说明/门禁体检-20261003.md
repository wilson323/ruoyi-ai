## 一句话总结论

**两个红灯都不是"代码坏了"，而是三种性质完全不同的问题被混在了同一个红灯里；而且 SOP-2 声称"提交前必跑的 5 个门禁"，实际只有 1 个被机器自动执行。**

拆开说：

1. **命名门禁那 2 条是真违规，但要改的是代码不是门禁** —— 这 2 个测试类的命名确实违反了项目自己的既有惯例（同仓 20 多个同类测试类都不带下划线，只有这 2 个带）。
2. **注释门禁那 118 条主要是门禁规则定得太宽，不是 118 处代码缺陷** —— 其中至少 28 条（23.7%）是门禁自己算错的（14 条把 `record` 声明当成了方法，14 条是 `@Override` 实现方法而注释本该从接口继承）；剩下 90 条确实"没写方法级注释"，但这个项目整体本来就没有"每个公开方法都要写注释"的惯例。
3. **SOP-2 说的"5 个门禁提交前必跑"与事实不符** —— 5 个里只有 `check-best-practices-coverage.sh` 被 CI 自动执行，另外 4 个在所有可能自动执行的位置都是零命中，而且这件事仓库自己已经登记在册。

### 这两个类名是不是本项目有意为之？

**"用验收条目编号命名测试类"是有意的；"用下划线写编号"不是——它是这两个文件独有的写法。**

### 门禁的 PascalCase 正则是否过窄？

**不过窄。它只拒绝下划线和首字母小写，对全大写缩写字头（IPD / AI / DTO）没有任何问题。**

- 正则 `^[A-Z][a-zA-Z0-9]*$` 中 `[a-zA-Z0-9]` 覆盖全部大小写字母与数字，因此 `IpdRolePermissionCatalog`、`AIAssistant`、`P111AcceptanceTest` 这类名字都能通过——字母序列里没有下划线就不会被拒。
- 实测未发现误判：全仓扫描 2225 个 Java 文件，只报 2 条，且 2 条都是真的含下划线。没有把嵌套类、`record`、`enum`、内部类误判成命名违规（这 2 条是文件里第一个类声明，就是文件的主类）。

### 结论

**真违规，需改类名**（不是门禁写错）。理由：门禁规则（PascalCase）与项目自身主导惯例（20+ 个同类测试类不带下划线）方向一致，这 2 个文件是可确证的例外。

改法（与同仓惯例对齐）：

- `P1_1_1_BidirectionalBindingTest` → `P111BidirectionalBindingTest`（文件名与类名同改）
- `P2_6_2_DualSignStageGuardTest` → `P262DualSignStageGuardTest`（同上）

改名影响面（已实测全仓引用）：

- 必须一并改的代码引用：`ruoyi-modules/ruoyi-ipd/src/test/java/org/ruoyi/ipd/service/RequirementChangeConcurrencyTest.java:50` 的注释里提到了 `P2_6_2_DualSignStageGuardTest`（仅注释，非可执行引用）。
- 会变成"与旧代码对不上"的历史存档（不影响任何测试执行）：`docs/ipd-系统说明/验收/p1-1-1-binding-2026-09-07.md:19,37,113`、`docs/ipd-系统说明/验收/知识库MCP接入-20261001/` 下 4 个 JSON 清单里的文件哈希与路径。
- 结论：改名不会跑挂任何测试，成本 = 2 个 `git mv` + 1 行注释 + 若干历史文档的新旧名对照说明。

### 阈值 5 是写死的还是可配的？在第几行？


### 结论

**这 118 条里至少 28 条（23.7%）是门禁算错了，剩下的 90 条虽然字面成立，但门禁本身的新规矩与项目现状不匹配——所以这条红主要是"门禁规则问题"，不是"118 处代码缺陷"。**

两边证据：

- 误报侧（可确证）：14 条 `record` 声明不是方法；14 条 `@Override` 方法按 Java 惯例注释从接口继承。合计 28/118。
- 真实缺口侧（字面成立但不成比例）：全仓被这条规则扫描的同类文件共 133 个 `*Service.java`，公开方法声明共 634 个，被挑出 118 个 = **18.6%**。一个项目如果有"每个公开方法都写注释"的惯例，比例不会是这个数——说明项目本来就没这条惯例，是门禁新定的规矩。
- 另外 118 条里有大量**接口声明方法**（`IBusinessConfigService` 14 条、`IDeletionRequestService` 9 条、`IAuditLogService` 8 条）。接口方法在 Java 里最常靠实现类注释 + `{@inheritDoc}`，逐个写 Javadoc 不是普遍做法。

副作用提醒：脚本头部 `:11-12` 声明它要查 4 件事（TODO/FIXME、`@deprecated`、JavaDoc 缺失、**注释与签名参数列表不一致**），但第 4 件（`:110-127` 的 `PARAM_MISMATCH`，实测 14 个 Controller）永远只打印 `[INFO]`，从不影响退出码。也就是说：**这个脚本名义上查"注释与代码是否一致"，实际上退出码只由"有没有注释"决定——真正的"注释和代码对不上"它压根不拦。**

## 附录（2026-10-03 追加）：SOP-2 五门禁里有两个**根本不能跑在本仓 CI**

本报告正文说「SOP-2 五个门禁只有 1 个被自动执行」。后续一轮收编实验（`.github/workflows/static-gates.yml`
从 6 门禁扩到 10）暴露了一个补充事实：另外 4 个里，有 2 个**即便接进本仓 CI 也会直接打红**，
原因不是脚本坏了，而是它们的扫描根指向**兄弟仓库**。

```
scripts/check-memory-leak-pattern.sh:29   FRONT_DIR="${FRONT_DIR:-$REPO/../ruoyi-ipd-web/apps/web-antd/src}"
scripts/check-a11y-basics.sh:30           FRONT_DIR="${FRONT_DIR:-$REPO/../ruoyi-ipd-web/apps/web-antd/src}"
```

本机这两个目录存在，所以 exit=0；CI 是干净检出，兄弟仓库不在，实测：

```
FRONT_DIR=/tmp/__no_such_frontend__ bash scripts/check-memory-leak-pattern.sh   → EXIT=2
FRONT_DIR=/tmp/__no_such_frontend__ bash scripts/check-a11y-basics.sh           → EXIT=2
```

底层 `scripts/lib/audit-gate-input.sh` 的约定是「输入缺失一律 exit 2，绝不降级成 0 条」——
所以这不是静默放行，是把 CI 打红。**结论：这两个门禁应挂在 `ruoyi-ipd-web` 自己的 CI**，
在后端仓库里无论怎么接都是错的（接进去当天红；为它加 clone 兄弟仓库的步骤则超出单仓边界）。

同批未被收编的还有两个，原因不同：

| 脚本 | 未收编原因 |
|---|---|
| `check-permission-mirror-fe-be.sh` | 跨仓读前端码册 + 本机已红（EXIT=1） |
| `check-cd-absolute-path.sh` | 是 pre-commit 门禁，只扫 `git diff --cached`；CI 无 staged 改动 → **恒 PASS**，收编等于塞一个永远绿的 step |
| `check-mock-data-realism.sh` | 本机即红（EXIT=2） |
| `check-r-line-count.sh` | 本机即红（EXIT=2） |

**对决策 3 的影响**：决策 3 问「那 4 个没进自动执行的门禁接进 CI 还是降级」——
现在这个问题要拆成两半：`check-memory-leak-pattern` / `check-a11y-basics` 属于**前端仓库的 CI**，
不属于本仓的决策范围；真正落在本仓决策范围内的是 `check-naming-convention`（本轮已修绿）
与 `check-doc-code-sync`（见决策 1、2）。
