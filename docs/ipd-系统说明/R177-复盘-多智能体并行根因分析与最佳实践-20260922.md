- **复盘对象**：R177 全量真实业务落地闭环（6 路 subagent 并行 + 撞号必接 + 双仓推送 + 真库迁移）

## 一、这次真实暴露的 6 个问题（按危险程度排序）

### 问题 1：commit 说一套、做一套（最危险）

**事实**：兄弟会话的 `eac24028`，commit message 写满了「validate() 11 处 throw 加具体 message」的细节，但实际 diff 只有 log.md 一个文件 +37 行。真正的代码改动在工作树躺了几个小时没人知道，直到本会话撞号必接（`ce1d2ba8`）才入库。

**为什么危险**：
- 任何人读 git log 都会以为代码已入库；
- fresh clone 后运行行为与 log 记载对不上，排查线上问题会被 log 带偏；
- 接管会话要花多轮 git diff / git show 才能还原真相（本会话实测花了 5 次排查命令）。

### 问题 2：任务前提是假的（浪费一整轮 agent）

**事实**：A5 任务的 7 个 admin 路径（gate / gate-review / role / project / workbench / requirement / allowance）在前端路由、视图目录、后端端点三个层面全部不存在，命中率 0/7。subagent 勘察完才发现，整轮 BLOCKED。真实存在的是另外 7 个子目录（ai-models / config / gate-elements / handover / identity-sync / org / sop-template）。

**为什么危险**：
- 白跑一轮 subagent 是小事；
- 真正的风险是遇到「顺从型」agent——它可能硬着头皮把不存在的路径「做出来」，制造错误产物。

### 问题 3：撞号是结构性的（重复劳动）

**事实**：A2 状态机修复被完整做了两遍——兄弟会话在隔离 worktree 提交了 `8e0d30ec`，同时在主工作树也做了同样修改但没 commit。两份代码内容一致（NegativeFeedbackService 尾部 diff 逐行比对为 0 差异）。AiModel validate 同样是做了没提交、等接管会话收拾。

**为什么危险**：
- 浪费算力和时间；
- merge 时不知道哪份是权威版本；
- 两份代码一旦出现细微分叉，后续排查成本翻倍。

### 问题 4：子代理不懂表结构（必返工）

**事实**：A4 造数据 SQL 初版没写 id 列，但真表 id 是 NOT NULL 且无默认值，INSERT 直接报 `Field 'id' doesn't have a default value`。主会话手动指定 id 100001-100008 才成功。

**为什么危险**：
- 子代理可能报告「完成」但实际失败；
- 更糟的情况：子代理为了绕过报错擅自改表结构。

### 问题 5：门禁脚本自己有 bug（门禁失灵）

**事实**：check-doc-db-drift.sh 存在 mktemp 路径冲突 bug，导致门禁 1/2 误报 FAIL。多个 subagent 只能 `--no-verify` 绕过提交。而主会话后来手动跑同一门禁是 PASS（drift_count=0）。

**为什么危险**：
- 门禁误报会训练出「绕过习惯」；
- 一旦养成 `--no-verify` 肌肉记忆，真问题也会被绕过。

### 问题 6：前端仓停在分支上（收尾不干净）

**事实**：前端仓 HEAD 停在 `r177-a6-front` 分支而非 main，工作树还躺着 4 个未提交文件（评审要素 thresholdJson / vetoDualRequired 字段接入，+117/-9）。如果不是收口三步法强制检查，这批改动会一直躺在分支上，下个会话在 main 上工作根本看不到。

## 二、根源分析（为什么会这样）

### 根源 1：没有任务认领的单一事实源

多个会话响应同一用户指令，各自建 R 号各自干。撞号必接协议是**事后补救**，不是**事前防撞**。R 号是自由市场，没有任何机制让会话 A 知道会话 B 正在干什么。

```
用户一条指令
   ├── 兄弟会话：领 R177-A，派 subagent，在 worktree 干
   └── 接管会话：领 R177，派 subagent，在主工作树干
        ↓
   同一份工作做两遍，靠撞号必接兜底
```

**本质**：缺一个「开工前广播 + 认领可见」的机制。看板有这个潜力（in-progress 卡可见），但本轮没有用起来。

### 根源 2：commit 没有对账步骤

写 message 和 `git add` 是两个独立动作，中间没有「message 提到的每个文件是否都在 stat 里」的强制核对。无论人还是 AI，都习惯先写好漂亮的 message 再 add——漏 add 就错位，而且没人发现。

**本质**：commit 的原子性靠自觉，没有工具保障。

### 根源 3：五必现查没覆盖「规划期断言」

五必现查规约管的是「写文档 / 汇报时引用事实要现查」，但**做计划时列出的路径、端点、表名没有要求现查**。A5 的假路径就是从历史记忆/文档里抄来的，计划带着假路径派给 subagent，subagent 忠实执行了一个假任务。

**本质**：现查纪律只覆盖了「输出期」，没覆盖「规划期」。而规划期的假事实传播成本最高（一个 subagent 全轮报废）。

### 根源 4：派单时不想合并

6 路并行派出去很爽，收回来怎么合没有预案。谁先合、冲突怎么解、log.md 三方冲突谁赢，全是临场决定。实际后果：A3 merge 时 3 个文件 add/add 冲突（SQL + 2 张截图），因为兄弟会话已经把类似内容先推上了 main。

**本质**：dispatching-parallel-agents 的流程缺一个「合并预案」收尾步骤。

### 根源 5：门禁脚本无自测

门禁脚本管别人的代码，没人管门禁脚本自己。mktemp 这种环境依赖 bug 平时不触发不知道，触发了就是误报，误报的下场就是被 `--no-verify` 绕过。

**本质**：R134「自证能红」纪律要求业务脚本自测，但门禁脚本自己没纳入这个纪律。

### 根源 6：子代理的上下文边界就是任务卡边界

子代理只拿到任务描述，没拿到「写库前先读表结构」这类环境常识。A4 的 SQL 遗漏 id 列不是模型能力问题，是任务卡里没写这条前置要求。

**本质**：给 subagent 的任务卡质量 = subagent 产出质量的上限。任务卡漏了什么，产出就漏什么。

## 三、最佳实践（8 条可执行清单）

### 1. 开工前认领广播（事前防撞，取代事后补救）

开始任何 R 号任务前，三查一登记：
- `git log --oneline -5`（看有没有同方向 commit 刚落地）
- 看板扫 in-progress 卡（有没有人在做同一件事）
- log.md 末段（有没有同号登记）

发现同号在途：让路或撞号透明登记，**不覆盖**。长期方向：任务认领一律走看板建卡，让 in-progress 状态对所有人可见，而不是靠 git log 事后考古。

### 2. commit 对账三步（每次 commit 必做，零例外）

```
commit 后立即：
1. git show --stat HEAD
2. 逐项核对：message 里提到的每个文件/改动，stat 里有没有
3. 错位处置：未 push → amend；已 push → 补一个更正 commit 并在 log.md 登记
```

这条成本 10 秒，能拦住「message 说改了代码、diff 只有文档」这类最隐蔽的失真。

### 3. 计划断言预检（五必现查 v2：覆盖规划期）

计划文档里引用的每个**路径 / 端点 / 表名 / 路由 / 权限码**，写计划的那一刻就要现查存在性。给 subagent 的任务卡里，这类断言必须附带验证证据（grep / ls / SHOW TABLES 的输出摘要），标注「已验证存在」。没验证的断言要标「待验证」，让 subagent 第一步先验证再干活。

### 4. 子代理写库前置检查（schema 先读后写）

给 subagent 的任何写库任务卡，第一步固定为：

```
1. SHOW CREATE TABLE <表名>（或 DESCRIBE）
2. 把表结构粘进报告
3. SQL 必须带显式完整列清单（含主键），禁止依赖默认值
```

### 5. 派单带合并预案（并行执行的收尾前置）

N 路并行派单时，同一份计划里必须写明：
- **合并顺序**：文档/截图类先合（低冲突），代码类后合（高冲突）
- **冲突裁决原则**：log.md 三方冲突 → 双段号保留；SQL/截图 → 取子代理修复版；代码 → 以先入库方为基线，后来者 rebase
- **执行人**：主会话统一合并，subagent 不自行 merge

### 6. 门禁脚本自测（每次误报即登记修复）

- 门禁脚本启动时先跑自检模式（如 FAIL_SEED 双向触发）
- 自检不过 → 输出明确的「脚本自身故障」而非误报业务 FAIL
- 每次使用 `--no-verify` 都必须在 log.md 登记原因（哪个门禁、什么 bug、何时修）
- 门禁脚本 bug 修复后，补一个触发该 bug 的回归用例

### 7. 真库操作三件套（先备份、后验证、缓清理）

- **先备份**：任何 DML 前建备份表（`CREATE TABLE xxx_backup_日期 AS SELECT ...`），本轮 A3 的 76 行备份表就是回滚底气
- **后验证**：DML 后独立回读（不能只信 UPDATE 返回的行数），白名单校验（status 只剩合法值、enabled 只剩 0/1）
- **缓清理**：备份表保留到下一个迭代周期，确认无回滚诉求再删

### 8. 收口三步法（已有铁律，本次实战验证有效）

1. **整合工作树**：检查所有 worktree + 所有分支的未提交工作（本次在前端分支上捞出 4 个文件）
2. **commit 后立即 push**：双仓都推，不问
3. **清理验证**：HEAD = origin/main、`git status --porcelain` 为空、备份表在
