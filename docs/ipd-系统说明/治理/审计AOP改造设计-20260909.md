# 审计 AOP 改造设计（2026-09-09）

> 蜂群 C 只读盘点产出（81 处调用全量分布 + 三类模式 + 字段完整度 + 可行性边界）。
> 本文档是 P2-1「78 处 auditLogService.append 缺 AOP」的落地设计，**本轮只设计不动代码**。

## 1. 现状盘点（为什么不能简单"78→1 切面"）

### 1.1 分布

`auditLogService.append` 共 **44 文件 / 81 处**（service 40 / controller 4 / guard 1）。其中约 29 处藏在私有封装方法体内（一次封装多处调用），对应**业务动作调用点约 109 个**（Controller 9 + Service 100）；其余约 52 处为业务方法内联。

### 1.2 三类模式

| 模式 | 规模 | 特征 | 改造定位 |
|---|---|---|---|
| A · Controller 拷贝式封装 | 4 文件 / 4 处 / 9 动作点 | PersonController、ReceiptLedgerController、PersonSyncController、HrSyncController 四份 `private void audit(IpdActor, String action, Long entityId, String reason)` **逐字相同** | 消重首选；action 常量、字段全、无快照 → 注解化最低风险 |
| B · Service 内联+私有封装 | 39 文件 / 76 处 / ~100 动作点 | B1 私有方法型（21 文件约 30 方法，如 GateReviewService.audit 13 调用点带 `Object... pairs` 动态载荷）；B2 纯内联（如 PersonService 5 处仅 operatorId） | 主体；按"无快照单动作"子集分批注解化 |
| C · 已集中 | 2 文件 | AuditLogService.append 本体（REQUIRES_NEW + 锚行锁 + hash 链）+ DefaultStateMachineGuard postCommit | 天然收口点，**不动** |

### 1.3 字段完整度（73 内联块静态解析）

action / entityType 100%；entityId 90%；operatorId 85%；**operatorName 仅 51%**；**operatorRole 仅 34%**；reason 77%；beforeData 20% / afterData 58%；ipAddress 3%。

⚠️ hash 链约束：`canonicalOf()` 将 null 字段以空串入哈希且历史行哈希已冻结——**历史缺失字段不可回填**；注解化后新行自动补齐 operator 三元组不破坏旧链（prevHash 锚定写入时值），反而是治理收益。

## 2. 可行性边界（能改多少）

**注解化上限约 35-45 点（≈40%），65-75 处（≈60%）永久保留手写**。六类不可注解化：

1. **beforeData 快照**（15 处）：切面拿不到 DB 变更前态（如 StageActionService 的 `statusSnapshot(a)` 在 update 前取）。
2. **afterData 程序化构造**（42 处）：GateReviewService 的 `Object... pairs` 键值对载荷。
3. **动态 action**：`"PROJECT_STAGE_" + next`。
4. **循环内多条**：BidScanService、KpiSharedCollectionService。
5. **异常路径前落库**：auditStageGuardBlocked——审计必须先于业务异常写入（REQUIRES_NEW 显式控制），与 AfterThrowing 语义不等价。
6. **特殊操作人**：系统扫描（operatorId=0 + operatorName="KPI_DEADLINE_SCANNER"）、匿名 GUEST（ipHash）、登录失败（无 id）。

⚠️ **Spring AOP 代理边界**：109 个动作点大多在同类内部调用链上，`@AuditLog` 只能标被代理的公有入口方法；一个入口方法含多动作/多分支（GateReviewService 13 点）无法等价替换——这是保留手写比例高的结构性原因。

## 3. 设计

### 3.1 基础设施

ruoyi-common 下已有 4 个 @Aspect（ruoyi-common-log 的 LogAspect、idempotent、ratelimiter、DemoAspect）；ruoyi-ipd 的 pom 已依赖 ruoyi-common-log 与 ruoyi-common-idempotent，aspectjweaver/spring-aop 已在 classpath 且代理生效——**新增 AuditAspect 零依赖成本**。但 LogAspect 是 sys_oper_log 体系（publishEvent 异步 + LoginHelper 取人），与 IPD hash 链审计是两套体系，**不可复用其异步事件模式**。

### 3.2 注解形态

```java
@AuditLog(action = "RECEIPT_REFUND",
          entityType = "receipt_ledger",      // 常量，静态
          entityId = "#result.data.id",        // SpEL：入参/返回值
          reason  = "#req.reason()",           // SpEL：record 入参
          operator = "#actor",                 // 显式指定 IpdActor 参数
          systemOperator = "KPI_SCANNER")      // 无用户上下文时的兜底
```

### 3.3 落库通道（红线）

切面**必须同步调用** `AuditLogService.append`（保 REQUIRES_NEW + 锚行锁 seq 串行语义），**禁止仿 LogAspect 的 publishEvent 异步**——异步会吞掉 requireJson 校验失败信号，且与 verifyChain 验链时序冲突。

### 3.4 附带发现（顺手治理项）

- entityType 命名不统一：`persons` / `receipt_ledger`（单数）/ `person_sync_jobs`（复数）/ HandoverService 内 `handover` 与 `person` 混用 → 抽公共组件时统一枚举。
- operatorName 51% / operatorRole 34% 缺失 → 注解化新行自动补齐（历史不可回填）。

## 4. 分批迁移（风险递增）

| 批 | 内容 | 风险 | 验收 |
|---|---|---|---|
| P0 | 抽 4 份 Controller 逐字相同 audit() 为公共组件 IpdAuditHelper（**不引 AOP 先消重**）+ 统一 entityType 枚举 | 零 | 4 Controller 行为不变，既有测试绿 |
| P1 | A 类 9 点注解化（action 常量 / IpdActor 显式 / 无快照，SpEL 只需 `#req.x` / `#result.id`） | 低 | Controller 测试 + audit_logs 新行 operator 三元组 100% |
| P2 | B1 简单型 20-30 点（单动作、无 before/after、Long operatorId 类） | 中 | 同上 + verifyChain 全绿 |
| P3（可选） | 带 afterData 内联型（HandoverService 等），切面用 `#result` 序列化 | 中高 | 逐点 JSON 往返对称校验（DEF-6 requireJson 护栏拦截畸形载荷） |
| 永久手写 | 六类不可注解化场景 + C 类集中点 | — | — |

**改造价值重估**：不在"消灭 81 处"（做不到也不必做），而在：消除 4 份拷贝、统一 entityType/action 枚举、自动补齐 operator 三元组（51%→100%）、把 hash 链收口语义文档化到切面单点。

## 5. 与其他遗留项的合并
