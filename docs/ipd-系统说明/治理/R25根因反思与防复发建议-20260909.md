## 2. 8 大系统性根因

### 根因 RC-1：重构只加新、不清旧（占比 ≈ 31%）

**现象**：Service 改名/合并后旧 Service 没删；权限码 / 错误码 / i18n / npm 包 / 路由重构后旧配置/旧组件/旧依赖没清。

**典型异常**：
- AllowanceService 已被 AllowanceLedgerService 吸收，整类死（A1-#1）
- IpdPermissionCode 4 个孤儿常量（A7.2）
- IpdReportController 4 个 PERM_* 兜底常量（A7.3）
- BusinessConfigKeys 4 个 BONUS_TIER_*（A7.4）
- 156 个未路由页面（多为重构后老模块残留，B1）
- 34 个未引用 API 方法（B2）
- 89 个 i18n 死键（B6）
- 3 个 npm 死包（B5）

**跨漏洞影响**：
- 新人 onboarding 时被旧代码误导（"这条路径到底走哪个？"）
- bundle 体积膨胀（前端每多 100 个死 vue 文件 ≈ +50KB）
- 权限码漂移 → 真用旧码 / 假用新码，调试困难

**根治建议**：
1. 新增 `scripts/check_deletion_consistency.sh`：删除某 Service/Component/常量时，**强制**扫描 `IpdPermissionCode` / `BusinessConfigKeys` / i18n / package.json / `views/` 的引用图，输出一致性报告
2. 新增 `scripts/scan_dead_code.sh`：三向交叉扫描（grep 类名 + grep import + grep new + grep extends），每周日 02:00 跑
3. 重大重构（Service 合并/拆分）必须配对 PR（合并+删除），不允许只加新

### 根因 RC-2：跨仓契约不对账（占比 ≈ 35%）

**现象**：前后端分仓开发，无定期端点/字段对账脚本；文档更新跟不上代码。

**典型异常**：
- **D1-A-1 白屏**：前端 `fetchPlatformToken()` 调 `/auth/platform-token`，后端 `IpdAuthController` 仅 5 个子路由无此端点（致命）
- 76 条孤儿端点（D1-B）：后端定义、前端 SPA 未直接调用（admin/scan/internal 类，需逐项确认外部调用方）
- 4 项功能字段缺失（D2-A）：`Project.lastActivityAt`（影响 LEGACY 倒计时 UI）、`AiDocument.{archivedAt,archivedBy,reviewComment}`、`NegativeFeedback.{content,severity,source}`、`BidInvitation.{confirmToken,confirmTokenExpires}`
- 6 个文档端点未实现（D4-A）：HR sync / wecom × 4 / ai/generate
- 1 处路径漂移（D4-B）：wecom/unbind 应在 persons 而非 auth

**跨漏洞影响**：
- 致命白屏（auth/platform-token）
- UI 不可见字段（LEGACY 倒计时永远为空）
- 文档与实现漂移，新人按文档调端点 404

**根治建议**：
1. 新增 `scripts/check_cross_repo_contract.sh`：三向对账（FE `requestIpd/api/ipd/*.ts` ↔ BE Controller `@GetMapping` 等 ↔ ZK-IPD 文档端点描述），差集 > 0 即 fail
2. 新增 `.github/workflows/contract-drift.yml`：每周日 + 每次 PR 触发
3. 新增 `scripts/check_dto_field_drift.sh`：BE domain `private Long xxx` ↔ FE `interface` 字段名/类型对账

### 根因 RC-3：配置先行 / DDL 未落地（占比 ≈ 5%）

**现象**：先写配置 / 先建 entity 后 apply DDL；entity 加字段 DDL 未同步。

**典型异常**：
- `tenant.excludes: - person_roles` 真库无此表（A7.1-#1）—— 配置先行 / DDL 未落地
- `tenant.excludes` 3 处重复登记（A7.1-#2~4）
- `RequirementPool` Entity + DDL 双轨孤儿（A1-#4）—— 表 CREATE 了，entity 建了，Mapper/Service/Controller 全没建
- D2-A 字段缺失：后端 Domain 加了字段，前端 interface 没补

**跨漏洞影响**：
- tenant 拦截器对不存在的表注入过滤（实际无副作用但误导排查）
- Entity 字段真库查询 Unknown column
- 重构遗留表占真库资源

**根治建议**：
1. **已有** `docs/script/sql/check-entity-db-drift.py`——entity ↔ 真库对账（exit 0 即对齐）
2. 新增 `scripts/check_tenant_excludes_apply.sh`：`tenant.excludes` 列出表 vs 真库 catalog 对账，不存在的表 fail
3. 新增 `scripts/check_entity_complete.sh`：entity ↔ mapper ↔ service ↔ controller ↔ route 五件套检查（新增 entity 缺任一件即 fail）

### 根因 RC-4：grep 引用核查盲区（R14 教训复发点）

**现象**：Lombok `@RequiredArgsConstructor` 注入字段名 `xxxService` 不含类名，grep 字面量会漏检；注释里的 `@link` / `* ... */` 引用算类名引用但非业务引用。

**典型异常**：
- AllowanceService R14 教训**同型复现**（main 分支）
- BidScanService / OverdueReminderService 类似漏检
- 47 个 Controller Spring 自发现但 grep 类名零命中（已通过 `@RestController` 二次确认，但扫描器易误报）
- 9 个 WorkbenchAggregator / 3 个 NotificationChannelHandler / 5 个 AI Provider Tester 同型

**跨漏洞影响**：
- 直接 `rm -rf` 删 Service → 主代码 compile 仍绿，**test 阶段才炸**（R14 AllowanceService 误删事件）
- 误删后回滚成本高（git reflog 仅 30 天）

**根治建议**：
1. **强制三向交叉**：`scan_dead_code.sh` 内置 4 个 grep（类名 / import / new / extends），**全部为零才算真孤儿**
2. 注释引用剥离：grep 前 `sed '/^\s*\*/,/\*\//d' | grep -v '^\s*//' | grep -v '^\s*\*'` 注释剥离
3. Lombok 注入字段名反向追踪：解析 `@RequiredArgsConstructor` 类 → 字段名 → 构造参数类型 → 类名
4. 判死刑前必跑 `mvn -o -pl <module> test-compile`：主代码 compile 绿不等于测试编译绿

---

### 根因 RC-5：动态加载导致静态扫描盲区

**现象**：`router/access.ts` 用 `import.meta.glob` 动态加载所有 views；后端菜单 component 字段可下发任意路径；静态扫描无法判定哪些 views 真用、哪些 dynamic-loadable。

**典型异常**：
- 8 个 high-risk dynamic-loadable 视图（B1.2）：
  - `system/oss-config/index.vue`、`system/role-assign/index.vue`、`system/user/dept-tree.vue`、`system/dict/data.vue`、`system/user/authRole.vue`、`workflow/processDefinition/category-tree.vue`
- 147 个真死 vs 8 个 dynamic-loadable 需要 owner 与后端菜单 component 字段对账才能下结论

**跨漏洞影响**：
- 静态扫描报告「156 个未路由」但实际只有 147 个真死，**9 个误判**——误删会动态菜单无法访问

**根治建议**：
1. 新增 `scripts/check_dynamic_loadable.sh`：解析 `router/access.ts` 的 `import.meta.glob` 模式 + 解析后端菜单 SQL（admin/sys_menu 表）的 component 字段，输出"动态依赖清单"
2. CI 输出"dynamic-loadable 视图"清单到 lint 报告，扫描报告**单独标注**这一类为"待 owner 复核"
3. 前端 drift-guard 扩展：禁止新增未在动态依赖清单注册的视图到 dynamic-loadable 范围

### 根因 RC-6：复制粘贴 / 历史快照未清理

**现象**：`cp -r` 后没清理、版本升级后未标 DEPRECATED。

**典型异常**：
- `开发说明_副本/` 与 `开发说明/` **100% 一致**（10 文件 md5 全同，C1）—— 典型 cp -r 残留
- 2 个根目录 `.zip` 共 164MB 零引用（C2）—— 147M vs 17M 体积差 8 倍，时间差 4 小时，是同一项目的两次手工快照
- 2 个孤儿 .md（C4）：被 v3 替代未标 DEPRECATED

**跨漏洞影响**：
- 误导新人以为有两个版本
- 仓库膨胀（164MB 二进制历史快照）
- DEPRECATED 标记缺失 → 删除决策成本高（怕误删仍有用的）

**根治建议**：
1. 新增 `scripts/check_duplicate_ssot.sh`：仓库级 `diff -rq + md5sum`，发现 100% 一致目录即 fail（带白名单豁免）
2. 新增 `scripts/check_deprecated_marker.sh`：扫描"被新版本替代"的旧文件，强制要求 `.DEPRECATED-` 前缀或在文档头部加 "DEPRECATED, use vX"
3. 大文件（>10MB）入库前警告 + 建议挪 git-lfs 或外置盘

### 根因 RC-7：文档迁移后路径未更新

**现象**：文档目录迁移后，文档内链接未同步更新；版本升级后引用未改版本号；实现路径变更后文档未同步。

**典型异常**：
- `开发说明书.md` 引用 `交互原型/spec/batch-*.md`（已迁到 `开发说明/spec/`，C3-#11）
- `.workbuddy/memory/2026-09-02.md` 引用 v1 文件名（v1 已被 v2/v3 取代，C3-#1, #2）
- `wecom/unbind` 路径漂移：文档说 auth，实现在 persons（D4-B-1）
- 文档写 `:id` vs 后端 `{id}` 风格差异（D4-A-#6）

**跨漏洞影响**：
- 新人按文档找文件 → 文件不存在 → onboarding 失败
- 文档与实现漂移 → 调端点 404

**根治建议**：
1. 新增 `scripts/check_doc_link.sh`：扫描 `.md` 内 `[text](path)` 链接，`test -e` 验证，dangling link > 0 即 fail
2. 新增 `scripts/check_endpoint_path_consistency.sh`：文档端点 vs 实现端点字符串对账
3. 文档目录迁移 SOP：迁移前先扫出所有引用方 → 批量改链接 → 迁移 → 删除旧目录

### 根因 RC-8：菜单 / i18n 重构未清旧

**现象**：菜单改版（前端 IPD 改用静态 routes）、组件替换（新 upload 用 antd 内置文案）、任务类型枚举变更（工作台硬编码中文）—— 但旧 i18n key 仍保留。

**典型异常**：
- 前端 IPD 菜单改用静态 routes 后，menu.json 36 个 key 仍保留（B6 menu.json 36 项）
- 新 upload 组件用 antd 内置文案后，component.upload 28 个 key 失业（B6 component.json 28 项）
- 工作台任务类型硬编码中文，page.workbench.taskType 17 个 key 失业（B6 page.json 17 项）

**跨漏洞影响**：
- bundle 体积膨胀（i18n 死键约 +5KB gzip 前）
- 误删会导致未来回切菜单/组件时丢文案
- 翻译协作时被误导（以为这些文案真在用）

**根治建议**：
1. 新增 `scripts/check_i18n_unused_keys.sh`：扫描 `t('key')` / `$t('key')` 引用，差集 > 阈值（暂定 30）即 warn
2. 菜单/组件重构 SOP：重构前 grep 旧 key 引用 → 重构 → 删除未引用 key → 在 commit message 注明"清旧 key N 个"
3. i18n key 命名加版本前缀（如 `menu.v2.system.role`），旧版本清旧时无歧义

## 9. 应急：当前白屏风险处置（D1-A-1）

**风险点**：前端 `fetchPlatformToken()` 调 `POST /api/v1/auth/platform-token`，后端 `IpdAuthController` 仅 5 个子路由无此端点。任何需平台票接口（chat/system）命中即 404。

**2026-09-09 补充复核（fresh 读 store/ipd-auth.ts:251）**：登录主流程已有降级保护（`try { await renewPlatformSession(); } catch { /* 降级 */ }`），换票失败不阻断 IPD 登录，**不存在登录白屏**；真实影响是平台功能（AI 平台桥 chat/system）降级不可用——`renewPlatformSession` 报 404 后平台模块无票可用。严格定性应为「平台功能降级」而非「白屏」。

**临时缓解方案**（5 分钟）：
1. 前端 `fetchPlatformToken` 走 fallback：捕获 404 时改用 `requestIpd('/auth/login')` 复用 token（折中方案，不补后端）
2. 不推荐生产环境长期使用：会丢掉"平台会话"语义（chat/system 原平台接口的票需要短期 ticket 而非 IPD 长期 token）

**正式修复**（1-2 人日）：
- 方案 A：在 `IpdAuthController` 补 `platformToken(@RequestHeader("Authorization") String bearer)` 返回 `IpdPlatformToken`
- 方案 B：若平台票功能未达上线标准，从前端 `IpdAuthenticatedPath` union type 移除 `/auth/platform-token` 选项，调用方暂走 `/auth/login` 复用 token

**建议走方案 A**，因为：
1. `IpdPlatformToken` interface 已在前端定义（auth.ts:213-218）
2. `parseSession` 同级严格度已写在注释
3. 业务语义正确（平台票 ≠ IPD 票）

**本会话未动手**（OPS-09 单一写入者守则 + 不动 Java），登记登记到 ROOT-R6-D1-WHITE 卡（P1-9）。

### 9.2 D1-A-2 端点漂移：bid-invitations select 缺 confirmToken 字段

**风险点**（fresh 核实于 2026-09-09 12:40）：
- 后端 `BidController.java:84` 是 `@PutMapping("/bid-invitations/{id}/select")` + 三个参数：`@PathVariable Long id` + `@RequestParam Long responseId` + `@RequestParam String confirmToken`
- 前端 `api/ipd/bid.ts:127` 是 `selectBidInvitation(invitationId, responseId)` 只传 2 个，**缺 confirmToken**
- 前端**零调用** `pre-select-token`（grep 整个 src/ 无结果），即 P1-5.2 的预演→确认两阶段流没接通
- 后果：每次调用 `/select` 必然因缺 `confirmToken` 参数报 400，但因为业务流没接通所以现状"无人触发"

**脚本误报根源**：`check_cross_repo_contract.sh` 把路径归一到 `:id` + `?responseId=:id` 与后端 `?responseId=&confirmToken=` 形式不一致 → 报白屏。实际不是白屏，是字段缺失。

**正式修复**（2 选 1，推荐 A）：
- 方案 A：前端补齐两阶段流（推荐）
  1. `api/ipd/bid.ts` 增加 `preSelectBidInvitation(invitationId)` 调 `POST /bid-invitations/{id}/pre-select-token` 拿 `ConfirmTokenView`
  2. `views/ipd/bid/select/index.vue:254` 在调 `selectBidInvitation` 前先调 `preSelectBidInvitation`，把 token 作为第三参数传入
  3. `selectBidInvitation` 签名改为 `(invitationId, responseId, confirmToken)`
- 方案 B：后端降级为可选参数
  1. `BidController.selectResponse` 把 `@RequestParam String confirmToken` 改为 `@RequestParam(required=false) String confirmToken`
  2. Service 层：token 为 null 时跳过"二次确认"语义（不推荐，损失业务守卫）

**建议走方案 A**，因为：
1. confirmToken 是 P1-5.2 的核心守卫（防止误点击导致 3 选 1 误选），不能去掉
2. 业务流已经定义了 `pre-select-token` 端点，前端只需补上调用链
3. 工程量与方案 B 相当，但保留业务语义

**本会话未动手**（OPS-09），登记到 ROOT-R6-D1-WHITE-B 卡（与 D1-A-1 同优先级 P1）。
