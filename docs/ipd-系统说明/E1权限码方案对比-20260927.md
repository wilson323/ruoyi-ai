# E1-① 工作流三控制器权限码方案对比（2026-09-27）

> **触发**：E1-①安全修复任务——`FlwTaskController / FlwInstanceController / FlwDefinitionController` 零权限注解（任何登录用户可调 completeTask / 删实例 / 全量待办）。
> **结论先行**：**止（不写码）**。口径调查确认存在 **≥3 种合理权限口径**，且任一口径落地都必须先动 `sys_menu` 权限码登记与角色授权（sa-token 权限判定依赖菜单表，见 §1.5），**仅改 3 个 Controller 会让全部非超管用户瞬间失去工作流能力**——这是业务/权限模型裁决，不是工程补洞。按任务规则停止写码，输出本对比供 owner 拍板。

## 1. 口径调查结论（证据全部现查，2026-09-27 磁盘现状）

### 1.1 三控制器注解全貌（受影响面）

grep `@SaCheckPermission|@SaCheckRole|@SaIgnore` 在 3 个文件 **零命中**（仅 `@Log/@RepeatSubmit/@Validated`）：

| 控制器 | 路径 | 端点数 | 写操作 | 其中"越权即事故"级 |
|---|---|---|---|---|
| FlwTaskController | `/workflow/task` | 16（7写+9读） | startWorkFlow、completeTask、terminationTask、taskOperation(委派/转办/加签/减签)、updateAssignee、backProcess、urgeTask | completeTask、taskOperation、updateAssignee、terminationTask；读侧 `pageByAllTaskWait/pageByAllTaskFinish` 为**全量**待办/已办（跨用户数据泄漏面） |
| FlwInstanceController | `/workflow/instance` | 13（8写+5读） | deleteByBusinessIds、deleteByInstanceIds、deleteHisByInstanceIds、cancelProcessApply、active、updateVariable、invalid | 三个删除端点、active、updateVariable、invalid |
| FlwDefinitionController | `/workflow/definition` | 14（8写+6读） | add、edit、publish、unPublish、remove、copy、importDef、active | publish/remove/importDef 等全部（流程定义=系统级配置） |

### 1.2 本仓 workflow 模块自有惯例（真实存在，非推测）

同模块 `FlwCategoryController / FlwSpelController / TestLeaveController` 均全量挂
**`workflow:{resource}:{action}`** 风格码（`workflow:category:list/query/add/edit/remove/export`、`workflow:spel:*`、`workflow:leave:*`）。
**没有任何** `flow:task:*` 风格码痕迹（全仓 grep `flow:task|flow:instance|flow:definition` = 0 命中）。

### 1.3 上游官方口径 = 无口径

`upstream/main`（ageerle/ruoyi-ai，本次 fetch 后实查）三个 Flw 控制器**同样零权限注解**——上游并未给出官方权限码惯例，"参照上游"路径不存在。用户提示词中假设的 `flow:task:complete` 类码源自 RuoYi-Vue-Plus 官方 workflow 模块，**本仓树内无该码表任何登记**，引入即等于发明新码表（违反选码原则）。

### 1.4 权限码登记处与前端消费现状

- **sys_menu 登记**（`docs/script/sql/ruoyi-ai.sql:2731-2749`）：仅 `workflow:category:*`、`workflow:spel:*`、`workflow:leave:*` 已登记；**`workflow:task:*`/`workflow:instance:*`/`workflow:definition:*` 零登记**。
- **IPD 域登记处**（`IpdPermissionCode.java`，约 60 个 `ipd:*` 码 + `IpdRolePermissionCatalog`）：属**另一套登录体系**（`IpdAuthSession.LOGIN_TYPE`，IPD 人 vs 平台 sys_user），与 sa-token 默认链路互不相通；工作流三控制器走平台 sys_user 链，**不适合**借用 ipd 码表。R185-P1 鉴权契约提案（docs-only 待拍板）也未覆盖此域。
- **前端 ruoyi-ipd-web**（只读参考）：`views/workflow/processInstance/index.vue:192` 与 `processDefinition/index.vue:295-305` 的按钮 v-access **错配借用 `system:user:remove`/`system:user:add`**（占位性质，已在《工作流系统性梳理-补遗-20260927.md》P1-1 立账）；task/instance/definition **无任何自有码消费**；菜单为后端 sys_menu 驱动。

### 1.5 决定性工程事实：注解生效依赖菜单表授权

`SaPermissionImpl` → `SysPermissionServiceImpl.getMenuPermission`：超管得 `*:*:*` 直通；**普通用户权限集 = sys_role_menu→sys_menu.perms 查询结果**。
推论：只给 3 个 Controller 挂 `@SaCheckPermission("workflow:task:*")` 而**不配 SQL 登记+角色授权**（且 SQL 不在本次允许改动面内），则上线瞬间**除超管外所有人 completeTask/查待办全部 403**——修复漏洞的同时熔断全部审批业务。因此"口径明确就直接补注解"的前在本任务约束下不成立，必须先拍权限模型。

## 2. 三方案对比（待拍板）

| 维度 | 方案甲：全量同构（对齐 category/spel 惯例） | **方案乙：分级最小补洞（推荐）** | 方案丙：办理人模型（类型+handler 校验） |
|---|---|---|---|
| 做法 | 3 控制器全部端点挂 `workflow:task/instance/definition:{list,query,add,edit,remove,export}` 风格码 | **管理/越权面**（definition 全部写、instance 删除/active/invalid/updateVariable、task 的 updateAssignee/terminationTask/pageByAll*）挂新码；**个人自助面**（startWorkFlow/completeTask/backProcess/cancelProcessApply/urgeTask/pageByTaskWait 等）维持仅登录 | 个人面不加码，改在 Service 层校验"当前用户 ∈ 任务办理人"；管理面同乙 |
| 消灭的漏洞 | 全部 | 全部 P0（删实例/代办他人/全量窥视/定义篡改） | 全部 P0 + 防"有权角色越权办理他人任务" |
| 新增码数 | ~15-18 个 | 7-8 个（如 `workflow:definition:edit`、`workflow:instance:remove`、`workflow:instance:edit`、`workflow:task:assignee`、`workflow:task:queryAll`、`workflow:definition:import/export`） | 同乙 |
| 需要的配套 | sys_menu INSERT + **全体员工角色**授权（否则审批链熔断） | sys_menu INSERT + **仅管理角色**授权（组长/超管）；普通员工零配置变化、零业务中断 | 同乙 + Service 层代码改动（**超出本任务 3 文件约束**） |
| 风险 | 授权矩阵工作量大；漏配即业务断；前端 5 个任务页按钮码全要重排 | 个人面仍有"有权办理人越权办理"理论面（由 warm-flow 办理人机制兜底） | 改动面最大；与引擎 handler 语义耦合 |
| 符合"不发明新码表" | ✅（复用模块惯例格式） | ✅ | ✅ |

**推荐乙**：P0 洞全闭、普通用户零冲击、sys_menu 增量最小、与补遗 P0-1 立账表述（"删除实例/全量待办/completeTask 越权"）逐条对应。若 owner 更看重"审批动作也须持证"，则升丙（需另开工单扩改动面到 Service）。
