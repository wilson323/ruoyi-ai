## 〇、口径声明（先验仪器，再读数）

**取数范围**：`information_schema.tables WHERE table_schema='ipd_dev'`，全库 166 张表。
本文档纳入 **96 张业务表**，排除口径如下（排除项内置在取数命令里，不靠调用者记得加）：

| 排除前缀/模式 | 命中表数 | 理由 |
|---|---|---|
| `sys_%` | 27 | RuoYi 基线系统表，非 IPD 业务域 |
| `sj_%` | 22 | SnailJob 调度表，独立进程 |

**行数口径**：一律用 `SELECT COUNT(*)` 逐表实测，**不使用** `information_schema.table_rows`。
后者是 InnoDB 估算值，本轮实测证实其**至少 5 张表报少**（`system_configs` 59→61、`system_config_versions` 131→133、`ai_model_configs` 10→11、`sop_templates` 1→2、`ipd_business_config` 18→19）。引用估算值会把「刚好读完」误读成「还有一条没进来」。

### 1.1 空表（75 张）—— 改动时最容易误伤的一类

**空 ≠ 无用**。75 张空表里绝大多数是**已建好但业务未激活**的表，它们的 DDL 已经进了 `docs/script/sql/update/`，代码里也已经有 Service / Mapper / Controller 引用。判断「这张表能不能动」不能看行数，要看第四节的 apply 状态。

其中三张是**明确的保留表**（表注释里写死了「保留表」二字，误删会丢已拍板的设计决策）：

- `project_scores` — 五维贡献评定，R95 拍板保留
- `project_score_records` — 项目评分记录，R95 拍板保留
- `ipd_sub_stage` — 小阶段目录，注释称「22 行元数据，主计划第二节单一事实源」，**但实测 0 行**（见第三节结论 3）

## 二、核心表「谁在写」

**关键结构性事实（决定后面所有结论）**：IPD 的持久化**全部走 MyBatis-Plus `BaseMapper` 注解 + LambdaQueryWrapper，零 mapper XML**。

```bash
find ruoyi-modules/ruoyi-ipd -name '*.xml' -path '*mapper*' | wc -l   # → 0
grep -rl 'extends BaseMapper' ruoyi-modules/ruoyi-ipd --include='*.java' | wc -l   # → 76
grep -rl '@TableName' ruoyi-modules/ruoyi-ipd --include='*.java' | wc -l          # → 81
```

对比：基线 `ruoyi-system` 有 22 个 mapper XML，**IPD 一个都没有**。
**推论**：改 IPD 表结构时，**不要去找 XML 找 SQL**，SQL 藏在 Java 的 `@Select` 注解和 Wrapper 链里。搜 XML 会得出「这个表没有查询」的假结论。

## 三、字段级高风险清单（改了会炸的）

### 结论 1 · `stage_actions` 三列 NOT NULL 无默认，且无业务唯一键

`stage_actions` 的 `action_code varchar(8)` / `depth varchar(8)` / `owner_role varchar(16)` 三列**全部 NOT NULL 且无默认值**，即任何插入必须显式给全。
更关键：`stage_actions` **只有 PRIMARY(id)，没有业务唯一键**——同一项目同一动作可以重复插行，数据库层面不拦。`ipd_action_skill_map` 有 `uk_map_action_project` 保护，`stage_actions` 没有。这是两张表之间的一致性缺口。

### 结论 2 · `audit_logs` 的 hash 链：`prev_hash` / `curr_hash` NOT NULL，且 `seq` 唯一

```
seq        bigint     NOT NULL  无默认   ← uk_audit_seq 唯一
prev_hash  char(64)   NOT NULL  无默认
curr_hash  char(64)   NOT NULL  无默认
```

`audit_log_chain_heads` 注释写明是「事务级加锁的分配器」，`audit_logs` 本身 append-only。
**风险**：只要有绕过 `AuditLogServiceImpl` 的直接 insert，`seq` 会撞唯一键报错（**这是好事，会炸而不是静默算错**）。但若绕过且不写 `prev_hash`，链会断且不报错。当前表 0 行，链尚未在真库跑过一次 —— **首次写入时的链正确性无任何历史数据可参照**。

### 结论 3 · `ipd_sub_stage` 注释与实况不符（实测 0 行 vs 注释称 22 行）

```
表注释：IPD 小阶段目录（22 行元数据，主计划第二节单一事实源落库）
实测：  0 行
```

且在有数据的 21 张表里，`ipd_sub_stage` 不在其中。配套测试 `SubStageSeedSqlContractTest` 存在，但**没有 Java 写入方**（第 2.1 节未列）。

### 结论 4 · 双表配置口径：`kpi.stopThreshold` 文档举例与实况不符

`SystemConfig.java:18` 与 `IpdBusinessConfig.java:24` 的类注释**都**把 `kpi.stopThreshold` 举为自家表的例子，但真库里它**只在 `ipd_business_config` 表**（`system_configs` 里没有该键，只有 `allowance.scoreStopThreshold=60`）。

```bash
mysql --defaults-extra-file=/tmp/my-ro.cnf -D ipd_dev -N -B -e "
SELECT 'system_configs',config_key,config_value FROM system_configs WHERE config_key LIKE '%stopThreshold%' OR config_key LIKE 'kpi.%'

SELECT 'ipd_business_config',config_key,config_value FROM ipd_business_config WHERE config_key LIKE '%stopThreshold%' OR config_key LIKE 'kpi.%';"
```

代码常量 `BusinessConfigKeys.KPI_STOP_THRESHOLD` 指向 `ipd_business_config`（正确），仅 `SystemConfig.java` 的注释举例有误。当前两处阈值**都是 60**，无实际冲突，但：
- 文档口径与实况不符
- `bonus.*` 前缀键在两张表都有分布（`system_configs` 有 `bonus.poolRate` 类 21 键，`ipd_business_config` 有 `bonus.tierCoefficient_*`）。**两张配置表按前缀混放，改配置时极易写错表。**

### 结论 5 · JSON 存 longtext/varchar 但被当字符串匹配的高危字段

### 结论 6 · 跨表强一致字段组（改一处必须改另一处）

1. **`persons.person_type` 与 `project_members.role`**：人员类型（市场PM/研发PM/组长/超管）决定其在项目中的角色，津贴计算按 `allowance.` 加 level 取参（`IpdZkScenarioInitializer.java:294` 缺参会直接抛 `IllegalStateException`）。

3. **`gate_review_elements` 与 `gates.element_snapshot` / `gate_element_results.element_snapshot`**：前者在途可变，后两者提交时冻结。**改要素定义不影响历史判定**，这是设计意图，不是 bug —— 但改代码时若以为「改了要素名，历史记录会跟着变」就会踩空。
4. **`system_configs` 与 `system_config_versions`**：改配置必须走 Service（自动追加版本行），**直接 UPDATE 表会断版本链**。

## 四、初始化与种子清单

### 4.1 Java 初始化器（3 个 IPD 初始化器）

| 类 | 触发 | 顺序 | 写哪些表 | 幂等 | 失败是否阻断启动 |
|---|---|---|---|---|---|
| `IpdGateElementSeedInitializer` | `ApplicationRunner` | `@Order(10)` | `gate_review_elements` | 是（仅当表空） | **是**（`@Transactional(rollbackFor=Exception)`，异常外抛） |
| `IpdZkScenarioInitializer` | `ApplicationRunner` | `@Order(20)` | `product_groups`/`persons`/`products`/`projects`/`project_stages`/`project_members`/`stage_actions` | 是（类内 `exists`/`selectCount`） | **否**（`try/catch` 兜住，只记 ERROR） |
| `IpdMockDataInitializer` | `ApplicationRunner` | `@Profile("dev")` | `product_groups`/`persons` | 是（`selectOne` 后判存） | 未验证（未见 try/catch） |

**最需要注意的一条**：`IpdZkScenarioInitializer` 与 `IpdGateElementSeedInitializer` 的类注释都写明「过去挂 `@Profile("dev")`，导致非 dev 环境生产装完是空库」，二者**已于 2026-10-07 摘掉 `@Profile`**，现在**生产环境也会执行**。

这意味着：**生产首次启动会自动写入 7 个产品组、20 名人员、5 个项目、30 个阶段、17 个动作**（ZK-IPD 基线场景）。如果这些是测试数据而非真实基线，生产会被灌入假数据。摘 `@Profile` 这个改动本身是否有 owner 授权，**本轮无法从只读数据判定，需 owner 确认**。

两个初始化器的失败语义**相反**：

- `IpdGateElementSeedInitializer` 失败 → 抛异常 → **阻断启动**（快速失败）
- `IpdZkScenarioInitializer` 失败 → catch 记 ERROR → **照常启动**（静默继续），类注释明确说「种子失败绝不能拖垮应用启动」

`IpdGateElementSeedInitializer` 的守卫值得称道：它用 `selectSeedPreflightIncludingDeleted`（裸 `@Select`，SQL 无 `del_flag` 过滤）而非 `selectCount`，注释解释得很清楚——若用 `selectCount`，`@TableLogic` 会自动追加 `del_flag=0`，软删行被滤掉、活行为空时**会重插 33 条**。这是本仓「校验器本身要先自证」的正面样本。

### 4.2 定时任务（`@Scheduled`）
