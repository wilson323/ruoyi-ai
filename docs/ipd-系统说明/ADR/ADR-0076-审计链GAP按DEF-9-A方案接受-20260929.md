# ADR-0076：审计链 17 处 GAP 定性为「seq 缺行」非「哈希断裂」— 按 DEF-9 A 方案接受并登记基线

- 状态：`accepted`（依据 2026-09-11 R30 收口 owner 已拍板的 DEF-9 A 方案先例；本次为 B 轨道现查复核确认适用，无新的数据变更动作）
- 日期：2026-09-29 · 决策域：审计只追加链（G-02）遗留区间处置
- 关联：`docs/ipd-系统说明/验收/B3-全业务域矩阵证据盘点-20260929.md` §GAP-A（本文推翻其「哈希断裂」表述）、DEF-9（`AuditLogServiceImpl` §verifyChain 注释）、`scripts/verify-prod.sh`

## 1. 背景与现查证据（2026-09-29 fresh，HTTP GET /api/v1/audit-logs/verify，code=0）

```json
{"chain":"GAP","hashBroken":[],"gaps":["1889","1892","1901","1903","1906","1910",
 "2469","2473","2475","2477","2479","2481","2486","2550","2554","2559","3074"],
 "broken":[…同上17项…],"total":7202}
```

- **hashBroken = []**：全链 7202 行哈希无一断裂——「17 处哈希断裂」的早期表述不成立；
- **17 处全部是 gaps 类**（seq 缺行）：成因 = 删行 / 事务回滚 / InnoDB 自增值不回填，集中于 2026-09-06~09-22 迁移试错窗口（该区间 audit_logs 1148 行，min 09-06 16:34 / max 09-22 20:36）；
- **`hash_version` 全表 NULL 非缺陷**：DDL 原设计注释即 `NULL=legacy-v1, 2=canonical-json-v2`（`2026-09-04-ipd-p0-tables.sql:577`），当前写链恒 v1 ⇒ NULL 是设计内常态，不存在「从未回填」的账。

## 2. 决策（重签 vs 标记断代 → 均不需要）

| 选项 | 判定 | 理由 |
|---|---|---|
| A. 遗留区间重签 | **否决** | 改写历史 hash 行违反 G-02 只追加不变量；且 hashBroken=[]，没有任何哈希需要"修" |
| B. 标记断代（新基线/新链头） | **不需要** | 链自 09-23 起对现存行完全连续；补一条"断代"机制是给不存在的洞打补丁（双轨反模式） |
| C. **接受 GAP + 基线登记**（DEF-9 A 方案，复用先例） | **采纳** | 2026-09-11 R30 收口 owner 已就同类问题拍板 A 方案：`verifyChain()` 默认对 GAP 宽容、严态走 `verifyChainStrict()`；本次仅把 17 个已知 GAP seq 固定为基线事实登记于本文，运行态新增 GAP 由 `/audit-logs/verify`（chain=GAP 即可视化）与验收脚本现查捕获 |

## 3. 后果与监控口径

- 正面：零数据变更、零新机制；审计防篡改语义由 hashBroken=[] 独立背书（GAP 与篡改成因不同、分列报告，见 `AuditChainVerifyResult` 设计注释——混同代价 2026-09-05 已实证过）。
- 代价/约束：若未来出现「以 GAP 伪装篡改」场景，回滚路径 = 消费方改调 `verifyChainStrict()`（原注释已预留此开关，无需改代码）。
- 基线：本文 §1 的 17 个 seq 即遗留 GAP 全集；后续任何验收引用 GAP-A 必须 fresh 调 `/audit-logs/verify` 对照，新增 GAP 须单独归因（删行来源），不得默认并入遗留。
