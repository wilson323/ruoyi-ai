## 1. 核心架构裁决（三条，均推翻上一轮计划假设）

### 裁决 A：执行栈唯一 —— 复用 `AiGenerationService.generate()`，**不引入 AiServices 第二条 LLM 路径**

现查证据：

| 事实 | 位置 |
|---|---|
| IPD 生成主链**已是 langchain4j** | `service/ai/AiGateway.java` L3-L16 直接 import `dev.langchain4j.model.openai.OpenAiChatModel` |
| 旧 HttpClient 栈已废弃 | `service/ai/AiChatClient.java` 类级 `@Deprecated` + 注释「生成主链已迁 AiGateway（Langchain4j）…新代码禁止直接注入本类做生成调用」 |
| `generate()` 内建 7 道治理 | `service/AiGenerationService.java` L105-L200：SSRF 前置(SEC-REV-04/R213 allowlist)、月度预算预检(AC-AI-08)、`Semaphore(3)` 限流、RAG 注入(AI-STRAT-1)、瞬时失败重试(AI-P1-1)、`createGenerated` 文档落库、`AI_GENERATE`/`AI_GENERATE_FAILED` 审计含 token 计量(AC-AI-09) |

**结论**：若按原计划走 ruoyi-chat 的 `ChatServiceFacade` / langchain4j `AiServices`，则 65 个业务节点的 LLM 调用**全部绕过**上述 7 道治理，形成 AGENTS.md 禁止的双轨。故本轮：

- 节点智能体的**产物生成一律经 `AiGenerationService.generate(actor, AiGenerateReq)`**；
- 新增代码里**零** `AiServices.builder` / `ChatServiceFactory` / `buildChatModel` / MCP `ToolProvider` 调用；
- `ruoyi-ipd/pom.xml` 相应**去掉 `dev.langchain4j:langchain4j` 主件**（`langchain4j-open-ai` 已在，无需第二件），保留 `ruoyi-chat`（取 `IAgentService`/`AgentVo` 配置契约）。

### 裁决 B：智能体底座的复用点在**配置层**，命名约定即映射 —— 去掉 `ActionAgentRegistry`

用户锁定的「复用 ruoyi-chat 的 Agent 底座」按裁决 A 收敛为**配置层复用**：

- 智能体身份 = `agent_info` 一行，命名约定 **`IPD-<动作码>`**（如 `IPD-C07`、`IPD-LC09`）；
- 解析入口 = 既有 `IAgentService.queryEnabledOptions()`（`ruoyi-chat` L52，已过滤 `status=0`），**不新增查询方法、不新增映射表、不新增 `system_configs` 键**；
- 智能体的 `system_prompt` 即该节点的工作指令（含输出格式/禁止事项/证据要求），`model_id` 供后续切换模型；
- 未绑定智能体（查无 `IPD-<code>` 行）时：执行器**降级为确定性行为 + `log.warn`**，绝不伪造产物（「AI 是快车道不是唯一车道」）。

**为何不自建缓存**：`SystemConfigServiceImpl` 已有 Caffeine(500/5min)+写穿透失效，PERF-02 明令「配置变更立即生效，不允许 TTL 窗口」；`agent_info` 解析发生在 R221 outbox 任务执行时（频次 = 每任务一次，远低于 LLM 调用开销），直查即可，自建 `ConcurrentHashMap` 只会制造 stale bug。

**命名约定的脆弱性与对冲**：约定是隐式契约，改名即静默解绑。对冲 = 哨兵表驱动契约测试（`ExecutorCoverageSentinelTest` 新增断言：种子 SQL 中每个 AI 档动作码都存在对应 `IPD-<code>` 行）。这正是 AGENTS.md 病根③「规则表与接线点靠人肉对账」的机制化根除。

**实施期增量（收口补记，同一对冲原则的延伸）**：前端 `ipd-enums.ts` 为「尚无 AI 任务时也能显示 execMode 徽标」存了一份 69 行静态映射 `ACTION_EXEC_MODE`（`/stage-actions` 的 VO 不带 execMode，只有已产生任务时 `AiAgentTaskView` 才带），其注释原先声称「哨兵测试保护」而全仓 grep 实测无任何测试引用该常量 = **失真陈述 + 静默漂移隐患**（后端改档位、前端徽标显示错档且不报错）。处置：补第 10 条断言 `frontEndExecModeMapMatchesActionCatalog` 做跨仓逐码对账，定位**复用** `StateMachineGuardRulesExportTest` 已有的 `IPD_FE_SHARED_DIR` 约定（成熟件复用，不另造第二套探测逻辑），前端仓不在检出内时 `Assumptions` 跳过而非假绿；三态自证已跑（篡改副本→红并点名「C01 后端=AI_GENERATE 前端=AI_DIRECT」、真值→绿、缺仓→Skipped，全程零触碰真实前端文件）。机械校验：两仓 69 码逐行零差异（AI_DIRECT 40 / AI_GENERATE 24 / HUMAN_GATE 5）。**裁决记录**：未选「给 `StageActionVo` 加 execMode 派生字段以彻底消灭前端副本」——该 VO 扇出面被兄弟多批次共用（R232-W14 / R28），收口期扩其接口回归风险高于收益；改以机制化对账锁死漂移，前端注释同步改为指名该断言。

### 裁决 C：执行器**优先扩展既有 4 个**，新增仅 2 个

原计划新增 3 个执行器；按裁决 A/B 与 `valueFields` 数据化后收敛为**新增 2 个 + 扩展 4 个**：

| 执行器 | 处置 | 码数 | 行为 |
|---|---|---|---|
| `GenerateExecutor` | **扩展**（既有 C01） | 1 + 23 | AI_GENERATE：智能体 prompt → `generate()` 出草稿 → `transit(IN_PROGRESS)` → 通知 PM 人审 |
| `LightDirectExecutor` | **扩展**（既有 P08） | 1 + 14 | AI_DIRECT ∧ LIGHT ∧ 无 valueFields：纯确定性 `recordFields(now)` + `transit(DONE)`，**零 LLM** |
| `DeepDirectExecutor` | **数据化泛化**（既有 C08） | 1 + 3 | AI_DIRECT ∧ 有 valueFields：人确认对话填表载荷 → 归集 md → OSS → `addDeliverable` → 按 `valueFields` 落 `recordFields` → `transit(DONE)`；`supportsSchedule()=false` |
| `GatePrepExecutor` | **扩展**（既有 C11，泛化 2 处 `"C11"` 字面量） | 1 + 4 | HUMAN_GATE：备料 + 非否决要素预判 PASS + 尝试 submit；**否决项绝不代判** |
| `AgentEvidenceExecutor` | **新增** | 17 | AI_DIRECT ∧ DEEP ∧ 无 valueFields：智能体出证据文档 → `generate()` → 挂为交付物（BR-IPD-03 深管 ≥1 交付物）→ `transit(DONE)`；智能体缺失则降级为确定性归集 md + WARN |
| `KpiSharedReconcileExecutor` | **兄弟 R232-W14，本轮不碰** | 4 | K01-K04 共担 KPI 台账，`supportsSchedule()=false` |

合计 24 + 15 + 4 + 5 + 17 + 4 = **69** ✓

> `DeepDirectExecutor` 泛化而非新建 `ValueFieldDirectExecutor` 的理由：C08 与 D11/V02/L08 是**同一行为族**（人确认载荷 → 归集 → 落库），差异只在 `valueFields` 是否为空。用 `ActionCatalog.byCode(code).valueFields()` 数据驱动即可消去 C08 硬编码，少一个类、少一处重复逻辑。

## 2. 信任边界（红线，不可协商）

1. **写库数值一律来自人确认载荷**：`recordFields` 的 `far/frr/certNo/certPassedAt/launchDate` 只接受 `triggerType=PASSIVE ∧ triggeredBy≠null` 的自然人确认链路上的 `fill_payload`；SCHEDULE/EVENT 无人确认环节**连查都不查**（沿用 `DeepDirectExecutor.resolvePayload` 既有收紧）。
2. **LLM 不得直接产数落库**：智能体产物只进 `ai_documents`（草稿态待人审）或 OSS 交付物，**绝不**解析 LLM 文本回填 `stage_actions` 数值字段。
3. **Gate 否决项绝不代判**：`GatePrepExecutor.isVeto` 命中即 `continue`（spec §5.1）。
4. **终态守卫**：所有执行器首行 `AiActionExecutor.terminalNoOp(...)`，人判完成后重复触发不得再备料/上传/通知。
5. **失败即 fail，不伪造完成**：智能体不可用 / 载荷缺失 / OSS 未返回 ossId → `AiExecResult.fail(...)` 走引擎退避重试，≥3 次 DEAD 转人工。
6. **不挂 SQL 执行工具**：`ExecuteSqlQueryTool` 等 supervisor 工具**不进入**任何业务节点（本轮按裁决 A 根本不走 supervisor 路径，天然满足）。
