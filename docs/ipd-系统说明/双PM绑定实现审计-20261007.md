# 双PM 绑定实现审计（纯只读 · 2026-10-07）

## 一句话结论

**双PM「绑定单点」实现了，「成对完整性」没有实现。** 单个 PM 的绑定守卫（角色互斥、快照锁定、超额备案、幂等、DB 唯一键）齐全；但**没有任何一处代码或数据库约束保证一个项目同时存在在职 MARKET_PM 和 RD_PM**——已在真库发生（`PRJ-2026-001` 只有 1 个 `MEMBER` 行）。

---

## 1. 绑定入口

`ProjectMemberController.java:23` base `/api/v1/projects/{projectId}/members`，共 **2 个端点**：

| 端点 | 入参 | 守卫 |
|---|---|---|
| `POST /` (:49-56) | `BindRequest(personId@NotNull, role@NotBlank, approvalRef?)` (:31) | `permission.requireProjectCreator()` = MARKET_PM/GROUP_LEADER/SUPER_ADMIN (`IpdPermission.java:169-171`)；service 内另有 `IpdIdorGuard.assertSameGroupIpd` (`ProjectMemberServiceImpl.java:81`) |
| `GET /` (:59-63) | 无 | `requireInternal()` |

第二入口是**移交**：`HandoverService.doAccept` 走同一个 `bindMember` 五参重载 (`HandoverService.java:442`)，因此**继承全部绑定校验**。
第三入口是**项目创建**：`ProjectService.insertNewProject` 调私有 `bindProjectPm` (`ProjectService.java:342-346`) —— **不走 `bindMember`**。

## 2. 「双PM 完整性」由谁保证 —— **无人保证**

逐条查完，**未找到**任何一处校验：

- `bindMember`：只校验单条记录合法性，**不查询同项目另一角色是否存在**（`ProjectMemberServiceImpl.java:69-163` 全文无此逻辑）。
- 开工审批 `ProjectStartService.approve` (`:47-85`)：只校验状态机 `PENDING_START→TEAMING`、产品退市、产品线负责人，**全文无 `ProjectMember` 引用**（grep `ProjectMember|MARKET_PM|RD_PM` 命中 0）。
- 阶段推进 `ProjectService.advanceStage` (`:529`)：守卫是 `requireProjectMemberOrSuperAdmin` (`:535`)，**任意成员身份即可**，不区分角色。
- 状态迁移 `changeStatus` (`:441`)：`DRAFT→TEAMING→ACTIVE` 全程无成员校验。
- Gate 环节 `GateReviewService.openSignQueue` (`:1119`)：某角色解析不到签署人时 **WARN 后 `continue` 跳过**（`:1231-1135`），注释自陈「存量 5 个无 PM 成员的在途 gate…不应因成员配置缺失回滚」。

**单边 PM 项目能走多远：能走到 Gate 双签卡死。** 具体路径：
`POST /api/v1/projects` 传 `marketPmId=<A>` 不传 `rdPmId` → 项目建成 → `approve-start` 通过（无校验）→ `TEAMING` → `changeStatus → ACTIVE` → `advance-stage` 通过（成员身份即可）→ 到 G1/G5 双签 Gate，`signerPersonId(gate,"RD_PM")` 返回 `null` (`GateReviewService.java:1262-1268`) → 该侧**永远没有签署人**，`settle` 要求 `decided.size() >= 2` (`:357`) 永不满足 → Gate 永久 `PENDING`；`scanTimeout` 会给缺席侧插弃权行，但主导方非 `leadSideOf` 时判定 `ABSTAINED_TIMEOUT` 不放行 (`:686-690`)。

**无成员能否创建/开工：能。** `bindProjectPm` 对 `personId == null` 直接 `return` (`ProjectService.java:401-403`)，两个 PM 都不传就零成员建项目；`create()` 仅校验 `marketPmId != rdPmId` (`:257`)，不校验非空。

## 3. 角色固定不可跨（B7 / BR-USER-08、BR-USER-08b、BR-TEAM-08）

代码位置：`ProjectMemberServiceImpl.java:89-92`（`role.equals(person.getPersonType())` 不等则拒）、`HandoverService.java:241-242`。**拦得住**，两条路径都拦。

**但创建路径漏了。** `ProjectService.bindProjectPm` (`:400-425`) **完全没有 `personType` 校验** —— 只查人存在、查 `level`、查津贴参数，就 insert。**推演越权路径**：`POST /api/v1/projects` 传 `marketPmId=<一个 person_type=RD_PM 的人>` → `bindProjectPm(id, X, "MARKET_PM")` 直接写入 → X 在库中同时是 `persons.person_type='RD_PM'` 和 `project_members.role='MARKET_PM'`。**同一人跨项目跨角色成立，违反 B7。** 这是本次审计最重的一处缺口。

注：`:101-106` 有一段注释声明「一个角色只能一名在任成员」的校验被**主动撤除**（理由为需求原文无此条）。该判断本身合理，但它与本次缺口无关——缺的是「两种角色都要有」。

## 4. 评级快照 + 津贴基准锁定

绑定时落，依据 `person.level`（快照）+ `system_configs['allowance.'+level]`：
- `ProjectMemberServiceImpl.java:128-135`：`level` 空 → 抛「该人员等级未同步（L1-L5），无法锁定津贴基准」；津贴 ≤0 → 抛「津贴参数缺失」。
- 落库 `:142-143`：`lockedLevel=level`、`lockedAmount=allowance.<level>`。
- DB 层 `locked_level` / `locked_amount` 均 `NOT NULL` 且**无默认值**，形成第二道 fail-fast（`show create table project_members` 实测）。
- 审计 `MEMBER_BIND` afterData 含快照值 (`:155-159`)。
- 配置实测：L1=1000 L2=1500 L3=2000 L4=2500 L5=3000。
- `bindProjectPm` 的快照仅在 `personMapper != null && systemConfigService != null` 时赋值 (`:414`) —— **两者任一为 null 则快照留空，撞 DB NOT NULL 直接炸**（旧单测构造器兼容留下的分支，生产 DI 下不会命中）。

## 5. 超额备案（approval_ref）

- 阈值配置键：`allowance.projectCountThreshold`，实测值 **3**（`system_configs`）。
- 代码：`ProjectMemberServiceImpl.java:108-126`。计数带 `FOR UPDATE` (`:111`) 串行化并发。
  - `active >= 3` → 一律拒绝（备案也不能超上限）。
  - `active == 2`（即绑第 3 个）→ `approvalRef` 空则拒；超 64 字符则拒。
- 落库仅在 `active == threshold-1` 时写 `approvalRef.trim()` (`:141`)，否则置 `null`。
- **缺口**：创建路径 `bindProjectPm` **不做项目数校验、不要求备案**，可在 `POST /api/v1/projects` 里绕过 AC-TEAM-11 直接塞第 4 个项目。

## 6. DB 约束现状（实测 information_schema / show create table）

唯一索引只有一个：`uk_pm_active_bind (active_bind_key)`，其中 `active_bind_key` 是虚拟生成列 `if(exit_date is null, concat(project_id,'-',role,'-',person_id), NULL)`。

- **拦得住**：同项目+同人+同角色的重复在任绑定。
- **拦不住**：① 同项目同角色两名**不同**人（`role` 超编）；② 同项目只有单边角色；③ 角色与 `persons.person_type` 不一致（跨表约束不存在）；④ 项目成员数超上限。

## 7. 真实现状

- 项目 6 个（`projects.del_flag='0'`），`project_members` 在任 10 行：MARKET_PM 5 / RD_PM 5。
- **单边 PM 项目 1 个：`PRJ-2026-001`（id `2107793628943179777`，status `TEAMING`，stage `CONCEPT`）—— 唯一成员是 `person_id=900101`、role=`MEMBER`（此人 `persons.person_type='SUPER_ADMIN'`，L3）。该项目市场PM、研发PM 均缺。**
  证据：该行由 `ProjectService.java:346` 的 `bindProjectPm(..., "MEMBER")` 写入，即创建时两个 PM id 均未传、仅回填了操作人。
- 同角色超编：无（实测 `group by project_id, role having count(*)>1` 返回空）。
- 跨角色不一致（persons.person_type vs project_members.role）：**未在本次 SQL 中检出**（当前 10 行均一致），故第 3 节的越权路径是**代码层可通行、数据层尚未发生**。

## 建议的最小修复（按优先级）

1. **P0 · 创建路径补 B7 角色互斥**：`ProjectService.bindProjectPm` (`:400`) 内加 `if (!"MEMBER".equals(role) && !role.equals(person.getPersonType())) throw`；或在 `create()` (`:257`) 之后、insert 之前对两个 PM id 各查一次 `persons.person_type`。测试：`ProjectServiceTest` 加「传 person_type=RD_PM 的人当 marketPmId ⇒ 抛 ROLE_LOCKED」。
2. **P0 · 创建路径补项目数上限 + 备案**：创建走 `bindProjectPm` 时复用 `ProjectMemberServiceImpl` 的阈值逻辑，否则 AC-TEAM-11 可被 `POST /projects` 绕过。
3. **P1 · 开工审批加双PM 成对校验**：`ProjectStartService.approve` (`:47`) 在 `stateMachineGuard.preCheck` 前查该项目在职 `MARKET_PM` 与 `RD_PM` 各 ≥1，否则抛 `STATE_CONFLICT`「未完成双PM 组队」。这是唯一能真正拦住单边项目进入 `TEAMING` 的点。测试：`ProjectStartServiceTest` 加「零成员/单边成员 ⇒ 拒绝开工」。
4. **P1 · 数据治理**：把 `PRJ-2026-001` 的 `MEMBER` 行处理掉（补绑双PM 或作废该项目），否则上条修复上线后该行成为历史脏数据。当前库中 0 个 `bid_invitations`，无招标链路影响。
5. **P2 · DB 兜底**：加 `UNIQUE (project_id, role, active_bind_key_role)` 形式的角色超编约束（虚拟列 `(project_id,role)` + 唯一键），把第 6 节的①类缺口下推到 DB。注意需先确认「一个角色是否允许多人」这一业务口径——代码注释 `:101-106` 认为需求未规定，故此条**须 owner 拍板后再做**。
