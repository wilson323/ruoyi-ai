## 1. B0 安全前置（先于任何 sensitivity 过滤上线）

### S1 kid 客户端直传（拒绝语义，不静默忽略）
- 校验收口层：**service 层统一谓词**，不放 Controller（4 个消费点跨 3 个类，收口一次到位）。
- 落点：`ruoyi-chat` 新增 `org.ruoyi.service.knowledge.KnowledgeAccessGate`（接口，方法 `assertReadable(Long kid)` / `List<Long> filterReadable(Collection<Long> kids)`，越权抛 `ServiceException`）。实现类在 `ruoyi-ipd`（见 §3，依赖方向 `ruoyi-modules/ruoyi-ipd/pom.xml` 单向下注 `ruoyi-chat`，接口定义在消费方、实现在权威方，不算第二套权限体系——上限判定仍全部委托 IPD 侧）。
- 接入点（4 处逐一）：
  1. `ChatServiceFacade.buildMultiKnowledgeAugmentor`：循环内 `queryById(kid)` 前调 `assertReadable`；
  2. `ChatServiceFacade.buildQueryVectorBo` 的调用方（走同一 augmentor 谓词，禁止在此再直传）；
  3. `MpChatWebSocketHandler.augmentWithKnowledge`：`kids` 汇总后先 `filterReadable`，非法 kid 抛错回 `sendError`（该类已有错误通道）；
  4. `KnowledgeFragmentServiceImpl.retrieval`：`queryById` 前 `assertReadable(bo.getKnowledgeId())`。
- 失败语义：**拒绝**（HTTP 4xx / WS 错误帧）。理由：设计文档 §8.3 明示"非法 kid 直接拒绝不静默忽略"；静默忽略会把越权探测变成不可观测。
- agentVo.getKnowledgeIds() 分支同样过闸（绑定关系是"显式授权"线索而非豁免，§5 文档口径）。

### S2 userId 客户端可控（会话派生 + 覆盖告警）
- 落点：`KnowledgeInfoServiceImpl.buildQueryWrapper`——`lqw.eq(bo.getUserId() != null, KnowledgeInfo::getUserId, bo.getUserId())` 改为：userId 一律取会话（`org.ruoyi.common.satoken.utils.LoginHelper`），`bo.getUserId()` 与派生值不一致时记 WARN 并以派生值为准（管理员角色除外——角色判定复用基线权限码，不新建体系）。
- 失败语义：**不报错、强制覆盖 + 告警**（列表页合法传参场景不存在，覆盖即安全；抛错会误伤导出等只读流）。
- 同类面：`KnowledgeFragmentServiceImpl.buildQueryWrapper` 不带任何归属条件，B0 顺带补 `knowledgeId` 归属谓词（片段列表仅在可读库内返回）。

### S3 cacheKey 无身份维度（必须先于 B2 检索过滤上线）
- 落点：`KnowledgeRetrievalServiceImpl.cacheKey(QueryVectorBo)`。现 key 首段是 kid（`invalidateKnowledge` 依赖 `key.startsWith(kid + "|")` 前缀清除），故新身份段**插在 kid 之后**：追加 `maxSensitivity|personId|scopeHash`（取自 QueryVectorBo 新增字段，见 §2）。
- 为什么必须先行：若 B2 过滤先上，同 kid+query 的不同敏感级调用者命中同一缓存条目（TTL 5min），过滤形同被缓存穿透——即设计文档 §8.4 的"假绿"。
- 失败语义：身份解析失败 → 按 PUBLIC 上限入 key（fail-closed，与 §8.2 一致）。

## 3. B2 检索接线

### 3.1 Where filter 构造点
- 唯一构造点：`WeaviateVectorStoreStrategy.search(QueryVectorBo)`（现态 GraphQL `Get{<class>_<kid>(nearVector…)` 无 `where` 子句；类中另有 `removeByDocId/removeByFid` 两处 `WhereFilter.builder()` 先例可抄 Operator 用法）。按 §2.2 的 QueryVectorBo 身份字段拼 `scope_type IN (…) ∪ 归属等值 ∪ sensitivity ≤ maxSensitivity`，语义=「作用域并集 ∪ 归属可见性 ∪ 敏感级闸门」（设计文档 §4 铁律二/§5 三页面口径）。
- 关键词通道同步过滤：`KnowledgeFragmentMapper.searchByKeyword` 的 `@Select` SQL 需 JOIN `knowledge_info` 追加 `scope/sensitivity` 谓词（混合检索 RRF 两路上下一致，否则关键词路成旁路）。
- MySQL 权威读侧：`KnowledgeInfoServiceImpl.buildQueryWrapper` 增加 sensitivity ≤ 上限与 scope 谓词（上限由 3.2 桥提供）。
- 禁双轨：不新建第二个检索服务；`MpChatWebSocketHandler` 的"独立保留"同构实现不复制过滤逻辑，统一经 `KnowledgeAccessGate`+`CustomVectorRetriever`→`KnowledgeRetrievalService` 一条链。

### 3.2 与 IPD 权限桥的调用方式
- 现成可消费类（`ruoyi-modules/ruoyi-ipd/src/main/java/org/ruoyi/ipd/security/`）：`IpdAuthSession`（`LOGIN_TYPE="ipd"`、`currentPerson()` 返回 `Person` 含 `personType/groupId`）、`IpdRolePermissionCatalog`（`permissionsOf/rolesOf(personType)`，未知类型返空=拒绝，天然 fail-closed）、`IpdPermission`（`canAccessGroup/canReadProject` 语义可复用）、`IpdStpInterfaceBridge`（loginType 分流先例）。
- 桥接：`KnowledgeAccessGate`（chat 侧接口）的 IPD 实现 `org.ruoyi.ipd.security.IpdKnowledgeAccessGate`——ipd loginType 时经 `IpdAuthSession.currentPerson()` 取 personType→映射 sensitivity 上限（§8.2 映射：SUPER_ADMIN/GROUP_LEADER→SECRET；MARKET_PM/RD_PM→INTERNAL；其余→PUBLIC）；sys_user loginType 或查不到 personId 映射→**fail-closed 到 PUBLIC**。上限映射常量与判定只写在这一处（唯一权威源在 ruoyi-ipd，chat 侧不得内嵌角色→上限表）。
- 为什么必须新增这一个接口（而非改现有类）：依赖方向 ruoyi-ipd→ruoyi-chat 单向，chat 读不到 `persons`；若不设端口只能把过滤上移到 ipd 控制器层——那会让 4 个直检点中的框架侧入口无从收口。端口模式=消费方定接口、权威方给实现，仍是单源，不构成第二套权限体系。数字员工上限=owner 上限交集规则一并落在该实现里（`Agent.sensitivity ≤ owner_person_id 上限`）。

### 3.3 与 AgentScopeRagPocIT 的契约对齐（`.worktrees/poc-agentscope-kernel/ruoyi-modules/ruoyi-chat/src/test/java/org/ruoyi/chat/poc/kernel/AgentScopeRagPocIT.java`）
- PoC 已证 API 事实（类注释）：`RetrieveConfig` 无 metadata 字段，原生过滤通道仅 `vectorName`（store 级），业务过滤载体是 `DocumentMetadata.payload`（应用层）。
- 对齐点：①payload 键名——PoC 用驼峰 `projectId`，生产现态 `text/fid/kid/docId` 亦驼峰，而设计文档 §4 列举为下划线（`scope_type`…）。**裁决建议：MySQL 列名保持 snake_case，Weaviate payload 键统一驼峰**（沿现态风格），并在 `WeaviatePayloadKeys` 常量类单源声明，PoC 合并时改引同一常量——禁两处字面量各写各的；②语义对齐：PoC 的"四维隔离预演"正负两例断言方向与 3.1 filter 一致后才准合并；③禁双轨纪律：PoC kernel 不得长出自己的检索链，合并时仅带入测试与常量引用，检索实现唯一入口仍是 `KnowledgeRetrievalService`。
