## 四、A1 未修真异常 + 真库 SQL 实证

**现象**:`/ipd/workbench` 删除审批列表 25 项中 23 项 `not_a_real_table #999999999` + 1 项 `unsupported_probe #1` + 1 项 `product #3` = **96% 测试脏数据**。

**真库 SQL 实证**(2026-09-18 16:47 PDT,ipd_dev @ 13306 socket):

```sql
-- 表名:deletion_requests,列名:entity_type / entity_id / entity_snapshot / create_time
-- 实际字段名 ≠ R33 报告描述的 target_table / target_id

SELECT entity_type, COUNT(*) AS cnt,
       MIN(create_time) AS earliest, MAX(create_time) AS latest
FROM deletion_requests WHERE del_flag=0 GROUP BY entity_type ORDER BY cnt DESC;

-- 实证结果:
-- entity_type          cnt  earliest               latest
-- cert_templates       23  2026-09-06 07:38:52     2026-09-06 13:13:20  ← 真实业务
-- not_a_real_table     23  2026-09-06 07:38:52     2026-09-06 13:13:20  ← 测试脏数据
-- product              4  2026-09-05 06:35:22     2026-09-06 07:35:23   ← 真实业务
-- products             1  2026-09-05 23:31:49     2026-09-05 23:31:49  ← 真实业务
-- unsupported_probe    1  2026-09-05 23:44:43     2026-09-05 23:44:43  ← 测试脏数据

-- 24 项测试脏数据快照全为 NULL:
SELECT id, entity_type, entity_id, status,
       JSON_EXTRACT(entity_snapshot, '$.title') AS title,
       JSON_EXTRACT(entity_snapshot, '$.name') AS name,
       create_time
FROM deletion_requests WHERE entity_type IN ('not_a_real_table','unsupported_probe') LIMIT 5;
-- id=2096269990000000001, unsupported_probe, id=1, ADMIN_REVIEW, NULL, NULL, 2026-09-05 23:44:43
-- id=2096382586229211137, not_a_real_table, id=999999999, ADMIN_REVIEW, NULL, NULL, 2026-09-06 07:38:52
```

**根因诊断**:
1. **数据污染**:entity_type='not_a_real_table' / 'unsupported_probe' 测试种子未清理(2026-09-05 23:44 ~ 2026-09-06 13:13 集中爆发)
2. **校验缺失**:Controller 未拦截 `entity_type` 不在白名单内的请求(以至于 2026-09-05 23:44 / 2026-09-06 07:38 能写入脏数据)
3. **字段名漂移**:R33 报告描述用 `target_table` / `target_id`,实际字段为 `entity_type` / `entity_id` — R33 描述与代码 schema 不对齐,**这是 R33 报告的描述性失真,不是 schema 本身错**

**修复路径**(二选一 + 提议路径 3 为治本):

**路径 1 — 数据清理**(快速闭环,owner 拍板即可执行):
```sql
DELETE FROM deletion_requests WHERE entity_type IN ('not_a_real_table', 'unsupported_probe');
SELECT entity_type, COUNT(*) FROM deletion_requests WHERE del_flag=0 GROUP BY entity_type;
-- 期望:cert_templates(23) + product(4) + products(1) = 28 项真实业务
```

**路径 2 — 前端过滤**(不改数据,前端兜底):
- 工作台删除审批组件加 `entity_type` 白名单过滤(已知表名枚举)
- 删除项必须能在数据库 `information_schema.tables` 查到对应表

**路径 3 — 后端 Controller 加拦截**(治本):
- `DeletionRequestController#create` 加业务校验,实体类型必须在 `information_schema.tables` 存在
- 避免后续误调用再现脏数据

**owner 决策点**:推荐路径 1(立刻闭环污染) + 路径 3(加拦截避免再现)。路径 2 仅临时。

```sql
-- 表名:persons,列名:name / username / person_type / account_status / employment_status / del_flag
-- 注:persons 表无 is_mock 列!Mock 标识仅在 name 字段以 'Mock-' 为前缀

SELECT COUNT(*) AS total,
       SUM(CASE WHEN name LIKE '%Mock%' THEN 1 ELSE 0 END) AS mock_cnt,
       SUM(CASE WHEN account_status='ACTIVE' THEN 1 ELSE 0 END) AS active_cnt
FROM persons;
-- total=27, mock_cnt=1, active_cnt=25

SELECT id, name, username, person_type, account_status, employment_status, del_flag, create_time
```

**根因诊断**:

**后端修复**(根因):`HandoverController#candidatesForReplacement` / `PersonsController#listActive` / `BidController#candidatesForAssign` 加过滤:
```java
// LambdaQueryWrapperX 是本仓 lambda 链式 wrapper
new LambdaQueryWrapperX<Person>()
    .eq(Person::getAccountStatus, "ACTIVE")
    .eq(Person::getEmploymentStatus, "ACTIVE")
    .eq(Person::getDelFlag, "0")
    .notLike(Person::getName, "Mock-%")     // 排除 Mock(本轮 SQL 实证:Mock 标识在 name 字段)
```
