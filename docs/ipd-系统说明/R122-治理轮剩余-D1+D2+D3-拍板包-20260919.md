## 一、D1：sys_user↔persons 字符集修复

### 1.1 问题边界

**历史背景**：sys_user 是 RuoYi-Vue-Plus 默认表（用户表），persons 是 IPD 业务表（人员表）。两表在 IPD 系统中存在外键关联（sys_user.user_id ↔ persons.id）。如果两表字符集不同，可能出现：

- sys_user 字段 latin1，persons 字段 utf8mb4 → 跨表 JOIN 时字符集冲突
- 字段中文乱码（sys_user 默认 latin1 不能存中文）
- 索引失效（utf8mb4_unicode_ci 与 utf8mb4_bin 不能共用索引）

**R49 报告登记**：sys_user↔persons 字符集修复列入 P2 待评估工作量，未指定具体动作。

### 1.2 fresh 实测（2026-09-19）

#### 1.2.1 sys_user 表字符集

执行 `SHOW FULL COLUMNS FROM sys_user;`：

### 1.3 三案详述

#### 方案 A：apply DDL ALTER TABLE sys_user CONVERT TO CHARACTER SET utf8mb4（不推荐）

**做法**：

```sql
ALTER TABLE sys_user CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**问题**：
- 已经是 utf8mb4，DDL 是 noop（MySQL 5.7+ 会直接返回 "Table already up to date"）
- 浪费工时 + 可能锁表（InnoDB ALTER TABLE 会重建表）

**风险**：无（noop），但工作量浪费。

**工作量**：10 min（含评估 + 跑 DDL + 验证）

#### 方案 B（推荐）：改 check 脚本加 alert，让脚本定期巡检字符集一致性

**做法**：

新建 `scripts/check-charset-consistency.sh`：

```bash
#!/usr/bin/env bash
# 检查 sys_user / persons 等核心表字符集一致性
TABLES=("sys_user" "persons" "projects" "stages" "actions" "real_persons")
for t in "${TABLES[@]}"; do
  CHARSET=$(mysql --defaults-file="$CNF" -N -e \
    "SELECT CCSA.character_set_name FROM information_schema.TABLES T \
     JOIN information_schema.COLLATION_CHARACTER_SET_APPLICABILITY CCSA \
     ON T.TABLE_COLLATION = CCSA.COLLATION_NAME \
     WHERE T.TABLE_SCHEMA='ipd_dev' AND T.TABLE_NAME='$t';")
  if [ "$CHARSET" != "utf8mb4" ]; then
    echo "❌ $t 字符集=$CHARSET (应为 utf8mb4)"
    FAIL=1
  else
    echo "✅ $t 字符集=utf8mb4"
  fi
done
exit $FAIL
```

**优点**：
- **零破坏性**（不改数据层，只读检查）
- **自动化**（可挂 cron 每日跑）
- **预防未来回退**（万一未来 RuoYi-Vue-Plus 升级回 latin1，脚本能立刻报警）

**风险**：脚本本身需要写 + 测，约 5 min。

**工作量**：5 min（含自证能红测试）

#### 方案 C：直接关闭 D1 项（登记"已 utf8mb4，关闭"）

**做法**：在 log.md R122 段写「D1 关闭，sys_user↔persons 字符集实测已 utf8mb4」。

**优点**：0 min。

**风险**：未来升级 RuoYi-Vue-Plus 时若 latin1 回归，无防护机制。

**工作量**：0 min

### 1.4 推荐

**推荐：方案 B**。

**理由**：
1. sys_user / persons **已是 utf8mb4**，DDL 是 noop，方案 A 浪费。
2. 方案 C 直接关闭虽然省事，但**未来回退无防护**（RuoYi-Vue-Plus 升级史上有过 latin1→utf8mb4 切换，未来也可能反向）。
3. 方案 B 是"轻量巡检 + 自动化报警"，符合 R119 5 脚本的"自证能红 + 常态化"理念（后续 R123 接入 cron）。

## 二、D2：bonus.poolRate 漂移处置（A/B/C 三案已在 A4 报告登记）

### 2.1 问题边界

**漂移定义**：`system_configs.config_value` ≠ `default_value` 的行。R46-A4 治本工程 `scripts/check-param-drift.sh` 已能检测漂移（EXIT=1 ✅），D2 = 如何处置已检测到的 1 处漂移 `bonus.poolRate`。

**A4 报告原文**（节选）：
> `bonus.poolRate`:current=`0.0500` / default=`0.05`
> update_time=2026-09-07 20:31:43 / update_by=-1（系统用户）
> **数值相等但字符串不等**：可能是 MySQL `0.0500` 与 `0.05` 字符串比较触发了漂移误报

### 2.2 fresh 实测（2026-09-19）

执行 `SELECT * FROM system_configs WHERE config_key='bonus.poolRate';`：

```
| id         | config_key     | config_value | value_type | default_value | description      | update_by | update_time         | validation_rule                             | source_ref                                                                                                                                         |
| 1948090411 | bonus.poolRate | 0.0500       | NUMBER     | 0.05          | 奖金池提取比例 5% | -1         | 2026-09-08 11:31:43 | {"max": "1", "min": "0", "kind": "DECIMAL"} | IPD系统_AI开发主Prompt_v3.md §7; 开发说明书.md D.0.7; ...                           |
```

**关键事实**：
- `config_value = "0.0500"`（字符串，4 位小数）
- `default_value = "0.05"`（字符串，2 位小数）
- `value_type = NUMBER`，`validation_rule.kind = DECIMAL`
- `update_by = -1`（系统用户，非人工）
- `update_time = 2026-09-08 11:31:43`（10 天前）

**漂移类型**：**字符串格式漂移**（trailing zeros）—— MySQL 数值字段存的是 `0.05`（数值相等），但 String 字段存的是 `0.0500`（4 位 vs 2 位小数）。R46-A4 `check-param-drift.sh` 用 SQL `!=` 字符串比较，触发了误报。

### 2.3 三案详述（A4 报告已登记）

#### 方案 A（推荐）：超管登录 `/ipd/admin/config` 编辑回 0.05（最稳）

**做法**：
1. 超管登录 ipd-admin
2. 进 `/ipd/admin/config`（系统配置管理页）
3. 找到 `bonus.poolRate` 行，编辑 `config_value` 从 `0.0500` → `0.05`
4. 保存 → 触发 system_config_versions 写入一条新版本
5. 重跑 `bash scripts/check-param-drift.sh --cnf .codex/ipd-dev/config/mysql-client.cnf --db ipd_dev` → 期望 EXIT=0

**优点**：
- **最小变更**（1 行 UPDATE 走 UI 路径）
- **最直接**（不绕弯）
- **审计完整**（update_by=超管 user_id，不是 -1）
- **风险可控**（UI 编辑不会触发全表重写）

**风险**：
- 需要超管在线（ipd-admin 账号）
- UI 编辑可能触发 system_config_versions 表写入（1 行增量）

**工作量**：5 min（含登录 + 编辑 + 重跑门禁 + 验证）

#### 方案 B：修种子脚本统一数值格式（影响范围中）

**做法**：
1. 找到种子脚本 `docs/script/sql/update/2026-09-04-ipd-p0-config-seed.sql`
2. 把 `INSERT INTO system_configs (config_key, config_value) VALUES ('bonus.poolRate', '0.0500')` 改为 `'0.05'`
3. 但 **A4 报告已确认种子脚本用 INSERT IGNORE，不更新现存行** —— 所以**修了种子脚本对已存在的 0.0500 行无影响**
4. 需要额外跑一次 `UPDATE system_configs SET config_value='0.05' WHERE config_key='bonus.poolRate';`

**优点**：
- 种子脚本长期修复（未来 reset 时自动 0.05）
- 防止下次导入再回退

**风险**：
- 修改种子脚本需要更新源文件 + commit，影响范围中
- UPDATE 是直接改数据库（绕过 UI / service 层），需 owner 拍板

**工作量**：30 min（含脚本修改 + commit + 验证）

#### 方案 C：check-param-drift.sh 加 `NUMERIC_TOLERANCE=0.0001` 容差（最快但降低门禁严格性）

**做法**：

修改 `scripts/check-param-drift.sh`：

```bash
# 把原来的 SQL:
SELECT ... WHERE config_value != default_value
# 改为:
SELECT ... WHERE ABS(CAST(config_value AS DECIMAL(10,6)) - CAST(default_value AS DECIMAL(10,6))) > 0.0001
```

**优点**：
- **5 min 改完**（一行 SQL）
- **自动消除字符串格式漂移误报**（0.0500 vs 0.05 数值差 < 0.0001，PASS）
- **未来类似 trailing zeros 漂移自动免疫**

**风险**：
- **降低门禁严格性**（容差从"完全相等"变为"差 < 0.0001"）
- **可能掩盖真实漂移**（如果真有 0.05 vs 0.06 业务误改，差 0.01 > 0.0001 仍能发现，但如果业务误改 0.05 → 0.0501，差 0.0001 ≤ 0.0001 就漏报）
- **跟 R119 自证能红理念冲突**（R119 强调门禁要严，容差 = 软化门禁）

**工作量**：5 min（改 1 行 + 验证）

### 2.4 推荐

**推荐：方案 A**。

**理由**：
1. **最小变更**——A 案只动 1 行 config_value，方案 B 动种子脚本 + commit，方案 C 动门禁脚本。
2. **最直接**——A 案走 UI 路径，审计完整（update_by=超管），方案 B/C 都绕过 UI。
3. **最符合 R46-A4 治本理念**——A 案是 R46 治本 4 工程的延续（"漂移发现 → UI 修复 → 闭环"），B/C 是"绕开问题"。
4. **风险最低**——A 案 UI 编辑风险 0（已上线 UI），B 案直接 UPDATE 风险中，C 案降低门禁严格性。

## 三、D3：SQL chain root 排程（待评估）

### 3.1 问题边界

**chain root 是什么**：`audit_log_chain_heads` 表（`GLOBAL` 行）是 IPD 系统审计链的"链锚"——所有 `audit_logs` 行的 `seq` 从 `chain_heads.GLOBAL.last_seq + 1` 开始递增，`last_hash` 是上一个 audit 行的 hash（hash 链）。`next_seq` 是下一个待分配 seq。

**R49 报告登记**：chain root 排程 = 「定期重置/初始化 audit chain」= 治理层 P2 待评估。

### 3.2 fresh 实测（2026-09-19）

执行 `SELECT * FROM audit_log_chain_heads LIMIT 10;`：

```
| chain_key | last_seq | last_hash                                                          | next_seq | initialized_at      |
| GLOBAL    | 2990     | 919d47b0866517a2a5908e4339d5075be3457629bc9b4f04edcfee97b14890b9 | 2991     | 2026-09-05 18:38:09 |
```

**关键事实**：
- **1 行 GLOBAL**（hash 链全表共用一个 GLOBAL 锚点）
- `last_seq = 2990`（已分配 2990 个 seq）
- `last_hash = 919d...b9`（SHA-256，64 字符）
- `next_seq = 2991`（待分配）
- `initialized_at = 2026-09-05 18:38:09`（14 天前初始化）

**关联 SQL**：
- `docs/script/sql/update/2026-09-17-ipd-braud01-audit-grant-restrict.sql`：收回 `ipd_app` 用户的 `INSERT/UPDATE/DELETE` 权限，**chain_heads 仅接受应用代码路径显式写入（AuditLogService.append）**。

### 3.3 三案详述

#### 方案 A：立即排程（reset / rotate chain）

**做法**：
1. owner 决定是否 reset chain（last_seq 重置为 0，last_hash 重置为全 0）
2. 如果 reset：`UPDATE audit_log_chain_heads SET last_seq=0, last_hash=REPEAT('0',64), next_seq=1 WHERE chain_key='GLOBAL';`
3. 如果 rotate（推荐）：`UPDATE audit_log_chain_heads SET chain_key='GLOBAL_2026Q4', last_seq=0, ... INSERT INTO audit_log_chain_heads VALUES ('GLOBAL', 0, ..., 1);`（双 chain 并行）

**优点**：
- 立即解决（30 min 落地）

**风险**：
- **hash 链重置 = 审计历史断链**（last_seq 从 0 开始，老审计 hash 不再连续）
- **法律风险**（如果审计链是合规要求，重置是违法的）
- **不可逆**（reset 后无法恢复 last_seq=2990 的连续性）

**工作量**：30 min

#### 方案 B（推荐）：评估工作量先（先出评估报告，再拍板 reset/rotate/维持）

**做法**：
1. 排查 chain root 用途：审计合规？业务连续性？仅日志？
2. 排查 seq=2990 是否触达上限（bigint 上限 = 9.2e18，2990 远未触达）
3. 排查 `2026-09-17-ipd-braud01-audit-grant-restrict.sql` 的 GRANT 收回是否完整
4. 出 `docs/ipd-系统说明/D3-chain-root-评估报告-20260919.md`
5. 评估报告里给 owner 3 个选项（reset / rotate / 维持现状）+ 推荐

**优点**：
- **零破坏性**（只读 + 评估）
- **数据驱动**（评估报告含真实数据 + 法律风险评估）
- **避免过早拍板**（chain root 排程不是紧急任务，seq=2990 远未触达上限）

**风险**：1 hr 评估时间。

**工作量**：1 hr 评估

#### 方案 C：推迟到 R124+

**做法**：在 log.md R122 段写「D3 推迟到 R124+」。

**优点**：0 min。

**风险**：chain root 评估被遗忘（"技术债延期"是治理恶化的常见模式）。

**工作量**：0 min

### 3.4 推荐

**推荐：方案 B（先评估工作量）**。

**理由**：
1. **seq=2990 远未触达 bigint 上限**（9.2e18），chain root reset 不是紧急任务。
2. **重置 chain root = 审计历史断链**，法律风险未知（需评估是否合规要求）。
3. **方案 B 评估报告含数据 + 风险 + 三选项**，让 owner 在下一轮（R124+）拍板时有完整信息。
