## 二、假绿类型描述

### 2.1 现象

测试期望异常类型被改成新类型让用例转绿，但实际契约缺口仍在：

- **改写测试期望**：原本 `assertThrows(BusinessException.class, ...)` → 改成 `assertThrows(RuntimeException.class, ...)`
- **扩大捕获范围**：原本精确捕获 `IllegalStateException` → 改成捕获 `Exception.class`
- **断言变成"现状"**：用 try-catch 捕获所有异常 → `assertThat(e.getClass().getName()).contains("Exception")` → 永远 PASS

### 2.2 根因

- 契约缺口（contract gap）仍存在（如某接口应该抛 `BusinessException` 但实际抛 `IllegalStateException`）
- 测试期望修改掩盖了契约缺口 → 用例转绿 → 但生产代码契约仍错
- 治标不治本：测试本应是契约的 SSOT，但反过来被生产代码"现状"反向同步

### 2.3 影响

- ✅ 单测 PASS（断言宽松 → 永远捕获 → CI 全绿）
- ❌ 契约缺口仍在：生产代码该抛 `BusinessException` 时仍抛 `IllegalStateException`
- ❌ 上层 try-catch 业务逻辑失效（如 `if (e instanceof BusinessException) retry()` 不触发）
- ❌ 监控告警错位：基于异常类型的告警规则失效

## 三、修复方案（docs-only — 不实装）

### 3.1 设计目标

测试断言必须锁住契约，**禁止反向同步**：

| 断言类型 | 错误做法 | 正确做法 |
|---|---|---|
| 异常类型断言 | `assertThrows(RuntimeException.class)` | `assertThrows(BusinessException.class)` |
| 异常消息断言 | `assertThat(e.getMessage()).isNotEmpty()` | `assertThat(e.getMessage()).contains("spec contract text")` |
| 状态断言 | `assertThat(state).isNotNull()` | `assertThat(state).isEqualTo(EXPECTED_STATE)` |

### 3.2 实现路径（待 owner 拍板 #4 + #6 后由后续 R 轮实装）

1. 在 `pom.xml` 引入 `archunit-junit5`（架构契约测试）
2. 新增 `ArchitectureContractTest.java` 强制所有 `assertThrows` 必须精确捕获（不允许 `Exception.class` / `RuntimeException.class` / `Throwable.class`）
3. 在 CI pipeline 加入 `archunit:test` 步骤，违规即 FAIL
4. 新增 `git-hook pre-commit` 检查：禁止 `assertThrows(RuntimeException.class)` / `assertThrows(Exception.class)` 提交

### 3.3 自证能红（FAIL_SEED 双向触发）

```bash
# 正常态：所有 assertThrows 精确捕获 → PASS
$ ASSERT_STRICT=1 bash scripts/check-f-green-type2.sh

EXIT=0

# 注入 FAIL_SEED：故意写入宽松断言 → FAIL
$ echo "assertThrows(RuntimeException.class, () -> service.badMethod());" >> src/test/java/FooTest.java
$ FAIL_SEED=1 bash scripts/check-f-green-type2.sh
🔴 检测到宽松断言：src/test/java/FooTest.java:42 包含 assertThrows(RuntimeException.class) → 契约缺口掩盖
EXIT=1（PASS — 双向触发）
```
