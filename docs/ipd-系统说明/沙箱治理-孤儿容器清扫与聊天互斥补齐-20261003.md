# 沙箱治理：孤儿容器清扫与聊天互斥补齐（2026-10-03）

## 1. 事实与背景

- **官方容器生命周期**（agentscope-java 源码实证，2026-10-03 三方核查）：每次 call 的 release 阶段执行 `stop()`（tar 快照落盘）+ `shutdown()`（`docker stop --time=30` + `docker rm --force`）。容器不跨 call 存活；严格口径下**容器数 = 并发在途 call 数**。
- **泄漏机制**：release 中 stop/shutdown 失败仅 warn 不重试；进程崩溃/被杀时 release 根本不执行；官方无孤儿容器清扫逻辑。容器名内嵌 SDK 随机 sessionId（`agentscope-sandbox-<uuid>`），无法从容器名反查归属 run。
- **实测**（2026-10-03）：本机残留 33 个 Up 状态沙箱容器而 `ipd_agent_run` 活跃数为 0（28 个集中创建于 10-02 14:41~16:37 批量验收轮次）。
- 本地部署硬前置：Docker daemon + 预置 `python:3.13-alpine`（`--pull=never`，缺镜像抛异常不回退主机执行）。

## 2. 一次性清理记录

- 人工清理：`docker ps -a --filter name=agentscope-sandbox -q | xargs docker rm -f`，34 → 0。
- **过程披露**：清理瞬间有 1 个活跃 run（2106284773201707009，C01，15:27:06 起）恰好在途，其容器被一并删除；该 run 最终 `SUCCEEDED`（15:28:08）——快照重建机制兜住（resume 时容器缺失 → 新容器 + tar 快照 hydrate），无数据损失。教训：**删除类操作必须先做零活跃守卫**，已固化进清扫器设计（启动模式仅在自身进程刚启动、单副本无在途 call 时全量清扫；周期模式只删超 24h 超龄容器）。

## 3. 落地一：孤儿容器清扫器 `ProjectAgentSandboxReaper`

- 位置：`ruoyi-modules/ruoyi-ipd/src/main/java/org/ruoyi/ipd/agent/service/ProjectAgentSandboxReaper.java`
- 语义：
  - **启动清扫（ApplicationRunner）**：单副本口径下进程刚启动无在途 call，全部沙箱容器视为历史孤儿，全删。
  - **周期清扫（@Scheduled 每小时 :23，已登记 IpdSchedulingConfig 错峰表）**：只删 `docker inspect` 创建时间超过孤儿 TTL（默认 24h，远大于单 run deadline）的容器；TTL 经构造器钳制至少 1h。
- 配置键：`ipd.agent.sandbox-reaper.enabled`（默认 true）、`ipd.agent.sandbox-reaper.orphan-ttl-hours`（默认 24）。
- 降级：docker CLI 缺失 / daemon 不可用 / 单命令超时（30s）只告警跳过，不阻断启动；脏输出行跳过不中断整轮。
- 测试：`ProjectAgentSandboxReaperTest`（@Tag("dev")，6 用例：超窗删/未超留/脏行跳过/启动 ZERO 全删/TTL 钳制/@Scheduled 接线），2026-10-03 实跑 6/6 通过。

## 4. 落地二：聊天内核跨副本沙箱互斥 `AgentScopeRedisSandboxGuard`（E1 补齐）

- 背景（E1，2026-10-02 评估文档遗留项，本次核查确认成立）：聊天内核唯一并发互斥是 `LocalSessionTurnGate`（static JVM 级 Semaphore），`executionGuard` 未挂（SDK 默认 noop）——多副本部署同 slot 并发穿透 + RedisAgentStateStore 版本 CAS 竞态。
- 位置：`ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/chat/kernel/AgentScopeRedisSandboxGuard.java`；装配于 `ChatOfficialCapabilities.configure(...)`（spec 级 `executionGuard`，新 6 参重载）与 `AgentScopeChatKernel` 生产构造（复用共享 Redisson，键前缀 `ruoyi:agentscope:chat:guard:`）。
- 语义：按官方 `SandboxExecutionGuard` javadoc 的 Redis 租约示例等价实现（官方 `RedisSandboxExecutionGuard` 只吃 UnifiedJedis，本仓底座是 Redisson 3.51）：`SET NX PX` 租约（TTL 30min 安全阀）+ token CAS 释放 + 自旋 500ms + 中断抛 `InterruptedException`。隔离键 = `guard:{scope}:{KernelScopeKey 复合 sessionId}`，覆盖 acquire → start → (call) → stop → release 全窗口。
- 锁序：turn gate（外层，先）→ guard（内层，后），全仓无反向获取路径，K8 双锁死锁前提不成立。
- **distributedStore 不整装裁决**：`builder.distributedStore(...)` 需补 `BaseStore` 与 Redisson 版 guard 两个适配器，且会把 PeriodicGate 换成 StoreBacked（baseStore 不可用时周期任务静默停摆）；官方提供等价更小路径（spec 级 executionGuard），故按最小依赖面走 spec 级挂载。IPD 内核不重复挂（已有 RFencedLock + DB claimEpoch 双重分布式闸门，spec guard 已显式设置所有权断言，auto-wiring 不覆盖）。
- 测试：`AgentScopeRedisSandboxGuardTest`（@Tag("dev")，4 用例：键组成/释放后可重获/中断抛出/释放失败幂等静默），2026-10-03 实跑 4/4 通过。

## 5. 部署形态声明（K-4 裁决①：当前单副本）

- **当前部署口径：单副本。** 多副本前置条件（全部满足前禁止多副本上线）：
  1. ~~聊天内核分布式互斥~~（本轮已补齐，guard 生效）；
  2. 清扫器副本协调：多副本下启动全量清扫会误删兄弟副本在途容器，须改为「仅删超龄 + 副本间租约仲裁」或按宿主机分片；
  3. K8 风险复活监控：若未来聊天内核再叠加分布式 turn gate，须复核锁序（gate → guard 唯一序）；
  4. `application-prod.yml` 连接池等单实例口径参数按实例数重估。
- guard 自旋无获取超时上限（对齐官方实现）；租约 TTL 30min 是安全阀不是正确性保证——副本崩溃后最长 30min 同 slot 串行窗口。
