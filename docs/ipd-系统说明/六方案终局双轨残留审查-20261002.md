| **Fan-in join**（等并行分支完成） | P5 §3.4 明写「官方完全无 join 原语」 | 同上 |
| 并行分支子图 | `parallel_<rootId>` 子 `StateGraph` | 同上 |
| **步骤级控制流位置（`next_node_id`）** | `rebuildCompletedNodes():366-396` | 官方 `AgentStateStore` 存的是 `State` 键值，**没有「栈 / 游标 / 位置」语义** |

**三条出路的代价**：

| 出路 | 说明 | 代价 | owner 可接受性 |
|---|---|---|---|
| **(a) 在官方抽象内自建该能力** | 落点：`AgentStateStore` 存「当前图 + nextNodeId + 已完成节点集」为 `State`；`MiddlewareBase.onAgent` 做每轮推进；`MiddlewareBase.onAgentStateReady` 做状态落盘。**逻辑仍是自研，但它落在官方扩展点内** | P5 §7 W3 已估 **8~12 天**；新增自研约 600~900 行。**注：这样它就不是「双轨」了——aiflow 不再持有 `CompiledGraph` / `StateGraph` / `AbstractCheckpointSaver`，`langgraph4j` 依赖真删** | ✅ **这是本审查推荐的出路**，且**不违反 owner 目标**。owner 反对的是「自建」这个动作在**结论层**（P5 §4.3 结论 1 写「必须自建的机制的起点」），不是反对「在官方扩展点内实现图推进逻辑」 |
| **(b) 放宽某个官方约束** | 需向 AgentScope 上游提 PR 增加图原语 | 不可行：`agentscope-harness` 是 Maven 依赖，**改官方库等于 fork**，与「基于官方定制」背道而驰。上游当前 `revision=2.0.4-SNAPSHOT`，图原语不在 roadmap 证据内 | ❌ **不可接受** |
| **(c) 该能力整体放弃** | aiflow 的可视化编排功能下线，改为纯单 agent 工具调用 | 业务上：`ruoyi-aiflow` 是**视觉 AI 工作流编排**（前端画布 + 11 类节点 + 条件边 + 并行分支）。放弃 = **整个 aiflow 模块功能作废** | ❌ **业务不可接受** |

**结论**：**技术上不是「不可能」，而是「P5 的结论措辞错了」。** 图推进逻辑必须在官方扩展点内自建——这**完全符合** owner 的硬约束。**P5 §4.3 结论 1 的「必须自建」是 V-06，作废重写为「必须在 `onAgent` / `onAgentStateReady` / `AgentStateStore` 三点内自建」。**

### §7.2 冲突二：**官方没有「执行检查点」抽象** —— 但三件官方存储能承接多少？

**证据**：P5 §4.1 实证「官方全仓 `checkpoint` 命中仅 `core/shutdown/*`（`ShutdownStateSaver` / `AgentScopeJvmShutdownHook` / `GracefulShutdownMiddleware`）——那是 JVM 优雅停机钩子，不是可回放的执行检查点」。

**owner 明确要求：「那就要继续深挖它们到底能承接到什么粒度，而不是直接跳到『自建』」。本审查深挖如下**：

| 官方存储 | 能承接到什么粒度 | 不能承接什么 | 承接到「next_node_id」的可行性 |
|---|---|---|---|
| **`AgentStateStore`**（`(userId, sessionId, key, State)`） | **能存任意 `State` 键值 + `getVersioned` / `saveIfVersion` CAS**（`:104`/`:134`） | 无「位置」概念，但**位置本身就是一个值** | ✅ **完全可行**。把 `WorkflowRunState{ graphSnapshot, nextNodeId, completedNodes, epoch }` 作为一个 `State` 实现存进去，CAS 天然解决并发续跑。**P5 §4.3 结论 2 选 `t_workflow_runtime_node` 做真相源，其实可以换成官方 `AgentStateStore`** |
| **`TaskRepository`**（`putTask` / `getTask` / `listTasks` / `cancelTask` / `findPendingDeliveries` / `markDelivered` + `WorkspaceTaskRepository` 心跳 30s / 孤儿 10min / sweep 5min） | **能表达「一个可取消、有状态、可恢复的后台工作单元」** | 生命周期是「一个后台 task」，不是「图上第 N 步」；孤儿只标 `FAILED` 不重跑 | ⚠️ **部分可行**。并行分支的每个分支 = 一个 `Task` 是**合理映射**；但「顺序推进到下一节点」不是 task |
| **`TranscriptStore`**（`appendSegment(TranscriptRef, seqStart, seqEnd, writerId, jsonl)`） | **能存不可变有序事件分段**，`listSegments` 可枚举 | 无 `nextNodeId` 概念 | ✅ **适合存 `ipd_agent_run_event` / `t_workflow_runtime_node` 的历史事件流**（P5 §4.3 结论 3 说要冻结的 `t_workflow_checkpoint` 表，其实可以落这里） |
| **`MessageBus.logAppend/logRead/logTrim`** | 追加日志 | 无 CAS、无位置 | ❌ 不适合做真相源 |

**结论**：**「步骤级断点续跑」在官方 `AgentStateStore`（键值 + 版本 CAS）内完全可实现**，P5 §4.3「必须自建 `WorkflowCheckpointStore`」的措辞**不准确**——应改为「必须用 `AgentStateStore.saveIfVersion` + 自定义 `State` 实现，**不新建序列化体系**」。
**唯一真正无解的是 Fan-in join**（需等 N 个并行分支完成）——但它可以用 `TaskRepository` 的 N 个 `Task` + `PeriodicGate.tryClaim` 轮询终态来表达，**也是官方抽象内**。

### §7.3 冲突三：以下几条**不构成**与 owner 目标的冲突（澄清，避免 owner 误判）

owner 可能以为这些也冲突，本审查逐一核实后**判定不冲突**：
