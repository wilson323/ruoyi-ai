## 1. 裁决

**全局优化是部分闭环。**

运行链已经有一条能用的单轨：`ProjectAgentController` 创建运行，`ProjectAgentRunPlanner` 合并请求技能与动作绑定技能，`ProjectAgentIntent` 在模型开口前给出意图，`ProjectAgentRunExecutor.shouldAwaitUser` 在该停的时候写 `STEP` `kind=AWAIT_USER` 并迁到 `WAITING_APPROVAL`，放行后才由 `AgentScopeProjectAgentKernel` 做只读 ReAct。产物定档走既有文档服务，库内码是 `GENERATED`，用户可见名是「待审核」，索引是 `NOT_INDEXED`。历史列表能搜动作、状态、产物标题和正文，响应里没有提问原文，也没有 `inputDigest`。

断点分成两类，不能合成一句「都要加强」。

### 1.1 主要缺口是产品方案没有做成确定性约束

用户能感知的失败，多数不是框架里少翻一个开关，而是业务规则只写在提示词里，完成时没有机器复核。

| 用户能感知的断点 | 代码事实 |
| --- | --- |
| 技能步骤写了「不得增删改序」，运行时仍可跳步、并步、提前收工 | `ProjectAgentIntent.prompt` 把「## 步骤」写进系统提示；`AgentScopeProjectAgentKernel.EventBridge` 只转发文本和工具事件，没有逐步完成检查 |
| 检索 0 命中时只劝模型标注「未取得」 | `ProjectKnowledgeSearchTool.NO_HIT_TEXT` 与 `ProjectAgentPrompt` 第 1 条都是提示词；`ProjectAgentRunHandle.finish` 在有正文时直接落草稿 |
| 澄清选项从哪来没有产品定义 | `ProjectAgentIntent` 用空泛句和「还是」正则造问题；`clarification-choices.ts` 再从成对「」里拆按钮 |
| 「完成」等于模型吐完字 | `finish(SUCCEEDED)` 不核对 `SOURCE.hits`、也不核对技能步骤是否真的走完 |

书中把这类事叫做约束，而不是建议。第 5 章「约束优先于指导」写明：能用代码强制的规则不要写成「请遵循」。第 7 章「验证器」写明：评估必须核实机器可独立复核的事实，而不是 Agent 的自我陈述。这两条在本项目里还停在提示词。

### 1.2 另一类缺口是 AgentScope 已有能力，内核没接上

这不是「再包一层 AgentScope」，而是现有 `HarnessAgent.streamEvents` 里已经发出、本内核丢掉的事件。

- 思考流：`v2/zh/docs/building-blocks/message-and-event.md` 有 `ThinkingBlockStartEvent` / `ThinkingBlockDeltaEvent` / `ThinkingBlockEndEvent`。`EventBridge.dispatch` 只处理 `TextBlockDeltaEvent`、工具起止、`ModelCallStartEvent`、`ExceedMaxItersEvent`。原生思维链增量被丢掉。界面上的「思考」只认正文里的 `<think>`（`model-message.ts`、`text-reveal.ts`）。
- 单次运行内的上下文压缩：`v2/zh/docs/harness/memory.md` 的 Compaction 管的是当前对话超长，与跨会话 `MEMORY.md` 不是同一件事。内核 `disableMemoryTools()` / `disableMemoryHooks()` 连压缩也关了。长检索原文只能靠工具预览截断（`PREVIEW_MAX_CHARS = 1000` 只作用于 `SOURCE` 预览，回给模型的命中正文没有在这里截断）。

这两处接上，不新增事件枚举，也不打开 Plan Mode。

### 1.3 不是缺口：会和 IPD 单轨冲突的 AgentScope 能力

`enablePlanMode()`、工作区 `plans/PLAN.md`、`skillsEnabled(true)` 的动态 `load_skill_through_path`、跨会话 `MEMORY.md`，文档里都有，本项目明确不用。理由见第 4 节。关掉它们不是遗漏。

## 3. 按用户任务链的优化事项

排序是一次真实使用的顺序。每一项都说明为什么不该再包一层 AgentScope。

### 3.1 意图与澄清选项从哪来

- 现状：`ProjectAgentIntent.decide` 不调用模型。空消息或「看看 / 分析一下 / 继续」等空泛句，问固定两句里的适用句（绑定了动作就多一句「请补充范围」）。句子里有不带「要 / 继续 / 需要 / 先」的「还是」，且两侧各 2～12 字，才生成「请指定其中一个」。技能「## 步骤」不参与出题。需要澄清时 `needsPlan=false`，不展开计划。前端只把问题里至少两对「」拆成按钮；没有引号时，整句就是一个按钮。
- 更好的做法：选项只来自两处确定性文本。一是技能正文里专供澄清的短清单（仍在 classpath `SKILL.md`，由 `orderedSteps` 同一风格的解析读出，不让模型现编）。二是用户原文里已经写出的「还是」两侧。空泛句继续问范围，不假装有两个业务方向。用户点选后的发送句维持 `clarificationSendText` 的「已选：…」，下一轮再走 `decide`。
- 为什么不是再包一层 AgentScope：框架不会知道 P01 该问「从零、评审已有稿、还是增量」。Plan Mode 也不会产生这些选项，它只会让模型自己写一份计划文件。
- 验收：`ProjectAgentIntentTest` 增加「技能澄清清单优先于正则」「没有清单的空泛句不编造方向」。前端 `intent-card` 测试断言按钮文案等于清单项，而不是整句问题。点选后的请求仍走 `createProjectAgentRun`，不新增接口。

### 3.2 澄清与自由计划的执行闸门

- 现状：已经落地。`shouldAwaitUser`：问题列表非空则等；需要计划且没有动作编码则等；消息第一行恰好是「按已确认计划执行」且后面至少一行步骤则不等。`awaitUser` 写 `STEP` `kind=AWAIT_USER`，`reason` 为 `CLARIFICATION` 或 `PLAN_CONFIRM`，状态 `WAITING_APPROVAL`，不调用 `kernel.execute`。前端若看到澄清布尔值为真、又已有 `TEXT_DELTA` 或工具事件、且没有 `AWAIT_USER`，会标出「仍会继续生成」，避免界面假装停住了。
- 更好的做法：保持这条闸门。不要把「是否停」再交给模型或 Plan Mode。本期只补测试，防止以后有人在 `publishIntent` 之后又提前 `kernel.execute`。
- 为什么不是再包一层 AgentScope：权限 ASK 发生在工具调用时。本项目需要的是「模型还没开口就停」。框架 HITL 停不住这一步，还会多出一套确认 UI。
- 验收：已有 `ProjectAgentRunGateTest` 保持：澄清与自由计划不产生工具事件；确认头加步骤会进内核。再加一条：只有确认头、没有步骤，仍然等待。

### 3.3 技能步骤锁进执行

- 现状：`orderedSteps` 解析「## 步骤」有序列表，最多 8 条，正文去掉编号后逐字保留。已绑定动作时这些句子成为 `INTENT.steps`，并写进系统提示「不得增删改序」。`product-prd-ipd/SKILL.md` 的步骤从「定模式」到「输出五段结果」，其中写了资料不足先列缺项。执行期没有计数器。模型可以在一步里写完整份 PRD。
- 更好的做法：仍是一次运行、同一套事件。放行内核前把步骤列表当成检查单。每收到一段正文或一次工具结果，由执行器（不是模型）判断当前未完成的第一步是否已有依据：该步要求检索时，必须先有对应 `SOURCE`；要求向用户确认时，必须先经过 `AWAIT_USER`。做不到就保持在这一步，把「仍停在第 n 步」写进现有 `STEP` 的 `kind`（继续用 `INTENT` 以外的已有 kind 字符串，例如在现有 `STEP` 载荷里用 `STEP_PROGRESS`，不新增枚举值）。失败只说明这一步，不把整次运行重开。
- 为什么不是再包一层 AgentScope：Plan Mode 的 `todo_write` 和 `plans/PLAN.md` 是模型自己维护的清单，和技能合同不是同一份。动态技能还会在运行中再读另一份 `SKILL.md`，sha256 留证会断。步骤文本已经在服务端，缺的是执行器对照，不是第二套计划器。
- 验收：用 `product-prd-ipd` 的步骤作夹具。假内核只吐最终稿、不产生检索 `SOURCE` 时，终态不得是带草稿产物的成功，或成功前必须有一步写明缺项来自 0 命中。增删步骤顺序的提示词可以被模型忽略，测试不能只断言提示词里有那 8 句。

### 3.4 检索未命中不得编造

- 现状：工具绑定项目，0 命中返回「未检索到本项目相关的已审核资料。请在输出中将相关项标注为“未取得」」。系统提示要求事实只能来自本轮输入和该工具，无来源标注「未取得」。`SOURCE` 记下 `hits`。没有人在收尾时读 `hits`。智能体化 RAG（第 3 章）要求观察「信息是否充分」后再写答案；当前观察结果只回给模型。
- 更好的做法：收尾前由 `ProjectAgentRunHandle` 读本轮 `SOURCE`。选定了检索工具且全部 `hits=0` 时，正文里不得出现没有「未取得」的事实句。做不到就不要把该正文升为可定档产物，运行可以结束，但错误或步骤里写明「检索未命中，产物未生成」。命中了的轮次，产物正文应能对上某次 `SOURCE.preview` 的摘录或显式「未取得」。不新增检索服务。
- 为什么不是再包一层 AgentScope：框架的 RAG 示例是另一套向量库。本项目检索口已经是 `AiDocEmbeddingService`，项目范围在工具构造时绑定。再接 `SimpleKnowledge` 会变成第二套知识库。
- 验收：`ProjectKnowledgeSearchToolTest` 已有未命中文案时，补运行级测试：`hits=0` 且正文无「未取得」则不写 `ARTIFACT`。`hits>0` 时允许产物，且 `SOURCE` 条数至少 1。

### 3.5 完成前验证

- 现状：流正常结束即 `SUCCEEDED`。正文非空就插入 `DRAFT` 产物。第 7 章验证器要求 FAIL 与 PASS 都能独立核对；第 9 章写明流程走完仍可能只是「像成果的东西」。本项目没有这道门。
- 更好的做法：在 `persistArtifactDraft` 之前做三件事，全部只用已落库事件。其一，绑定了技能步骤时，检查单没有「停在更早步骤」的未处理失败。其二，检索工具已选时，存在至少一次 `SOURCE`，或正文声明无资料。其三，正文不得写成 Gate 已通过（提示词第 3 条今天没有机器核对）。三件都过才落草稿。不过则失败码沿用已有 `KERNEL_ERROR` 以外的可见说明：优先用现有错误文本表加一条明确业务码，若加码会动合同枚举则只写 `STEP` 说明并以无产物的失败结束。实施时先看 `ProjectAgentErrorTexts` 是否已有空位，不发明第二套状态机。
- 为什么不是再包一层 AgentScope：框架没有 IPD Gate、已审核文档和「待审核」语义。受控执行只提供证据放哪，不提供这三条规则。
- 验收：`ProjectAgentRunServiceLifecycleTest` 增加三条：步骤未齐不落产物；检索 0 命中且正文像事实则不落产物；正文含「评审通过」不落产物。通过的路径仍是 `DRAFT`，定档后 `documentStatus=GENERATED`，展示「待审核」，`indexStatus=NOT_INDEXED`。

### 3.6 流式呈现，以及思考与正文分层

- 现状：文本增量进 `TEXT_DELTA`，前端按前缀揭示，不补字。`<think>` 进思考区，闭合后默认收起，标签仍是「思考」。原生 `ThinkingBlock*` 没有映射，模型若走思维链事件而不把 `<think>` 打进正文，用户看不到思考。`ModelCallStartEvent` 变成 `STEP` `kind=MODEL_CALL`，界面时间线有「模型调用」，这不是思考正文。
- 更好的做法：在 `EventBridge` 里把思维链增量交给现有 `sink.onText`，包进前端已经认识的 `<think>`…`</think>`，或在不改枚举的前提下让 `TEXT_DELTA` 载荷带上现有解析能看懂的同一标记。思考先揭示、回答后揭示的顺序已经在 `text-reveal.ts`。不要再做第二套打字机。静默卡死仍用运行级 `timeout`，本期不另造心跳协议。
- 为什么不是再包一层 AgentScope：流式已经是 `streamEvents`。缺的是适配器漏了事件类型，不是再嵌一个 Harness。
- 验收：内核测试喂 `ThinkingBlockDeltaEvent` 后，落库的是 `TEXT_DELTA` 且含思考标记；回答增量仍是 `TEXT_DELTA`。`assistant-turn` 与 `text-reveal` 测试保持「思考」一行、正文在限高区。不出现新的事件类型名。

### 3.7 历史可搜索，但不存提示词原文

- 现状：`GET` 列表由 `ProjectAgentRunListing` 组装。`q` 只匹配动作、状态，以及产物标题和正文（`artifacts.findRunIdsByContent`）。`RunItem` 有状态、动作、能力包、时间、`inputChars`、产物标题、至多 80 字摘录。没有 `message`，没有 `inputDigest`。前端占位是「搜索动作、状态或产物」，空结果文案是「没有匹配的运行」。点一行会 `openHistory`，从 seq 0 重放事件。存储列 `IpdAgentRun.inputDigest` 是 sha256，不能当搜索键展示。
- 缺口：没生成产物、又没绑定动作的运行，用户无法按「当时想干什么」找回来，因为原文故意不进搜索。这是产品缺口，不是列表没做。
- 更好的做法：搜索面增加已经落在事件里的非原文摘要：`INTENT.summary`、技能名、动作编码。这些不是用户提示词。不要把 `questions` 回显进搜索索引，因为「还是」类问题会带上用户原词。列表行继续不返回原文。
- 为什么不是再包一层 AgentScope：`MEMORY.md` 和 `sessions/*.log.jsonl` 会留下可检索的对话原文，和「历史不存提示词原文」相反。
- 验收：`ProjectAgentRunListTest`：用用户原句搜索命中数为 0；用动作编码、产物标题、`INTENT` 固定摘要可以命中；响应 JSON 无原文、无 digest。前端空态仍是「没有匹配的运行」。

### 3.8 产物版本点赞

- 现状：成功时 `persistArtifactDraft` 写 `DRAFT`，`ARTIFACT` 载荷含逻辑 `artifactId` 与字符串 `versionId`（版本行雪花 id）。点赞只认 `versionId`（`run-timeline.vue`：没有字符串 `versionId` 不渲染点赞）。定档仍用逻辑 `artifactId`，`applyArtifact` 走 `AiDocumentService`，状态 `GENERATED`，索引 `NOT_INDEXED`。`AiFeedbackService.resolveArtifactVersion` 按版本行查。旧事件只有 `artifactId` 时不能点赞，测试已锁这个行为（`run-timeline.test.ts`）。
- 更好的做法：新产物继续带字符串 `versionId`。旧事件不回填、不猜。点赞请求的 target 只能是版本行，禁止改成对逻辑 `artifactId` 点赞。展示名继续「待审核」，不把 `GENERATED` 当主文案，不把索引写成 `READY`。
- 为什么不是再包一层 AgentScope：产物版本、审核和索引是 IPD 文档语义，框架会话状态里没有这张表。
- 验收：`project-agent.test.ts` 与 `AiFeedbackServiceTest`：带 `versionId` 可评；缺省或空白或数字的 `versionId` 不发点赞；apply 响应 `documentStatus=GENERATED` 且 `indexStatus=NOT_INDEXED`。

### 3.9 能力从哪来（发送前，避免选错工具）

- 现状：可选工具来自能力包目录。`ProjectAgentToolCatalog` 只实现 `project_knowledge_search`。清单里有、目录里没有的工具不可用。`toolIds` 与框架 `/mcp/market` 的数字 id 不是一套编号。Planner 拒绝不在包内的动作，拒绝加载不到或 sha256 不符的技能。
- 更好的做法：保持单目录。前端加号里只列出 `available=true` 的工具。不要为了「工具多」去接 MCP 市场编号。第 4 章说默认可以用通用执行器，但安全、权限、审计要退回专用工具；本项目检索属于后者。
- 为什么不是再包一层 AgentScope：技能仓库和 MCP 会变成第二套 id。内核还在 `build` 后检查「暴露的工具 ⊆ 选定集」，多出来就拒绝运行。这道闸要留着。
- 验收：`ProjectAgentCapabilityServiceTest`、`ProjectAgentRunPlannerActionSkillTest` 继续拒绝包外动作、坏 sha256、未实现工具。不出现 `/mcp/market` 的 id 进入 `toolIds`。

### 4.1 用了会和 IPD 双轨，所以不上

### 4.3 书里有，AgentScope 也没有 IPD 这一条，必须自研
