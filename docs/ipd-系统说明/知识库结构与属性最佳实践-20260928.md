## 1. 结论

知识库从「user_id + share」扁平模型升级为
**「三层作用域 × 四维归属键 × 全链路溯源」**。

- 三层作用域（含五类取值）：`GLOBAL`（全局库）/ `GROUP`（产品线=产品组）/
  `PROJECT`（项目=产品动词面）/ `PERSON`（个人库）/ `AGENT`（数字员工库）。
- 检索语义：**叠加并集**，即「全局库 ∪ 组库 ∪ 项目库 ∪ 个人库」
  （按调用者身份与项目上下文求交集后可见的库集合），
  **不按 projectId 拆 collection**——向量物理桶按 embedding 模型分
  （见 §4），逻辑隔离靠 payload 归属过滤，避免「一项目一桶」造成的
  桶爆炸与跨桶检索不可达。
- 四维归属键：group / project / owner_person / owner_agent（§3 组一）。
- 全链路溯源：source_type / source_ref / oss_id / file_hash（§3 组二），
  任何片段可回源到「哪个文件、哪次上传、哪个业务对象」。

一句话：**桶按模型分（向量兼容性），行按归属滤（业务隔离性），
两件事绝不混在同一个维度上做。**
## 2. 现状三缺口（DDL 取证）

取证源：`docs/script/sql/ruoyi-ai.sql` 中 `knowledge_info` /
`knowledge_attach` / `knowledge_fragment` 三表 DDL；
实体侧对照 `ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/domain/entity/knowledge/`
下 `KnowledgeInfo.java`、`KnowledgeFragment.java`、`KnowledgeAttach.java`。

### 缺口① 归属维缺失（只有 user_id + tenant_id + share）

`knowledge_info` 现有归属相关键名仅：`user_id`、`tenant_id`、`share`
（是否公开 0/1），索引亦只有 `idx_tenant_user`、`idx_tenant_share`。
**没有** project / group / agent 任何一维归属列——知识库无法回答
「这个项目/产品线/数字员工该挂哪些库」，只能靠人-库二元关系硬连。
`agent_info` 侧的 `knowledge_ids`（JSON 数组）是目前唯一的库-员工关联线索，
属「显式授权清单」而非「归属边」，两者语义不同（见 §5）。

### 缺口② 向量版本不可判（库级有、片段级无）

`knowledge_info` 有库级 `vector_model`（向量库类型）与 `embedding_model`
（向量模型名），但 `knowledge_fragment` 仅有 `fid`、`idx`、`doc_id`、
`content`、`knowledge_id`、`tenant_id` 与审计列，
**片段级没有 embedding_model + embedding_dim + embedded_at 三元组**。
后果：更换 embedding 模型（如现网已发生 mock test-embed →
Qwen3-Embedding-0.6B dim=1024 切换，见
`docs/ipd-系统说明/log.md` R241 批3 记录）后，
**无法用一条 SQL 圈出哪些片段是旧模型嵌入的、需要重嵌入**；
混合检索的 FULLTEXT `ft_content` 与向量通道的一致性窗口也无法度量。

### 缺口③ 敏感级与生命周期/新鲜度缺席

`knowledge_info` 无 `sensitivity`（敏感级）、无 `valid_until`（有效期）、
无 `archived_at`（归档时间）；`share` 只是公开/私有二元开关，
不能支撑「SECRET 库仅特定 RBAC 角色可检索」这类过滤。
生命周期维度上，`knowledge_attach.status` 只表达**解析状态**
（0待解析/1解析中/2已解析/3解析失败），不表达知识条目的
「有效/过期/归档」业务生命期——过期规章、已退市产品资料仍会被检索命中。
## 3. 六组必备属性

| 组 | 属性（键名） | 落点 | 现态 |
|----|-------------|------|------|
| 一 归属 | `scope_type` / `group_id` / `project_id` / `owner_person_id` / `owner_agent_id` | knowledge_info | 缺（Part A 补，owner_person_id 由现有 `user_id` 语义承担） |
| 二 溯源 | `source_type` / `source_ref` / `oss_id` / `file_hash` | knowledge_attach 已有 `oss_id`、`file_hash`（且 `uk_knowledge_file_hash` 防重）；`source_type`/`source_ref` 为 Part B 待补 | 半有 |
| 三 向量版本三元组 | `embedding_model` / `embedding_dim` / `embedded_at` | knowledge_fragment 片段级 | 缺（Part A 补） |
| 四 生命周期 | `status` / `valid_until` / `archived_at` | knowledge_info（业务生命期，区别于 attach.status 解析状态） | 缺（Part B/C 补；`archived_at` 在 IPD 域已有先例：projects 表 P2-7.4 列，schema-snapshot 可查） |
| 五 敏感级 | `sensitivity`（PUBLIC/INTERNAL/SECRET） | knowledge_info + agent_info（员工可处理上限） | 缺（Part A 补列；检索过滤逻辑 Part B 接线，按用户 RBAC 求交） |
| 六 检索调优 | `separator` / `overlap_char` / `retrieve_limit` / `similarity_threshold` / `enable_rerank` / `rerank_score_threshold` / `rerank_top_n` / `rerank_model` / `enable_hybrid` / `hybrid_alpha` / `text_block_size` | knowledge_info | **已有，全部保留**，本设计不动其语义 |

原则：检索调优组是「库级默认、片段无关」的参数，继续留在 `knowledge_info`；
向量版本三元组是「片段级事实快照」，必须下沉到 `knowledge_fragment`——
**库级 `embedding_model` 表达「打算用什么」，片段级三元组表达「实际用了什么」，
两者共同构成换模型时的重嵌入对账基础。**
## 4. Weaviate payload 铁律

取证源：`ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/vector/impl/WeaviateVectorStoreStrategy.java`
（`createSchema`、批量写入 properties、`search` 三处现态）与
`ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/factory/VectorStoreStrategyFactory.java`
（策略注册键 `weaviate` 为默认）。

**现态**：类名桶 = `vectorStoreProperties.weaviate.classname` 拼接 `kid`
（一库一 class），每对象仅冗余四个 payload 属性
`text` / `fid` / `kid` / `docId`，`vectorizer=none` 外部嵌入 +
查询向量归一化（normalize）后近邻检索。

**铁律一：归属键必须冗余进 payload。**
向量桶解决「物理相似检索」，业务隔离必须靠 payload 元数据过滤。
目标态 payload 在现有四键之上补：`scope_type`、`group_id`、`project_id`、
`owner_person_id`、`owner_agent_id`、`sensitivity`、`embedding_model`、
`embedding_dim`——与 §3 六组属性同源，**MySQL 与向量库两侧的归属值
必须同一事务语义写入（或以 fragment 表为权威异步回填并对账），
禁止出现「库里 INTERNAL、向量侧无标」的隔离穿透**。

**铁律二：双通道——vectorName 选桶，payload filter 选行。**
- 选桶（物理维度）：按 embedding 模型分桶。同一向量空间内维度与模型必须
  一致；Weaviate 多向量能力下用 `vectorName`（按模型命名，如
  `qwen3-embedding-06b`）承载「一对象多模型向量」，检索指定 vectorName
  即锁定模型桶。仓内实证：AgentScope PoC G5 已查明
  「RetrieveConfig.metadata 实为 vectorName」
  （`docs/ipd-系统说明/log.md` R241 批1 限制条目，按现态口径登记）。
- 选行（逻辑维度）：桶内用 payload where-filter 叠加
  「作用域并集 ∪ 归属可见性 ∪ sensitivity ≤ 调用者上限」，
  即 `WhereFilter`（Operator 组合）按 §5 的页面上下文生成。
- 现态 `classname + kid` 一库一桶的做法与「不按 projectId 拆桶」并不冲突
  （kid 是库而非项目），但**按模型分桶是它的升级替代项**：Part B 落
  vectorName 后，新库并入模型桶、老库 lazy 迁移，避免每建一库开一 class
  的 schema 膨胀。迁移前后两阶段都以 payload filter 为权限权威——
  **权限永远不依赖桶名**。
## 5. 域模型接线（IPD 侧）

IPD 域取证源：`docs/script/sql/schema/schema-snapshot-2026-09-09.sql`
（`products.project_id`+`uk_products_project`、`projects.product_id`+
`uk_projects_product`、`product_groups`、`project_members.person_id/role`）；
`docs/script/sql/update/20260926-ai-agent-tasks.sql`
（`ai_agent_tasks.project_id NOT NULL`）；
`ruoyi-modules/ruoyi-ipd/src/main/resources/db/migration/V001__project_product_unique.sql`
（Product⇄Project 双向唯一键的迁移脚本原态）。

- **产品空间页（Product 资产聚合页）→ 聚合 GROUP + PROJECT 作用域库**：
  检索 filter = `scope_type IN (GLOBAL, GROUP, PROJECT)` 且
  `group_id = 当前产品组` OR `project_id = 当前项目`（产品动词面即项目，
  见 CONTEXT 篇结论一），叠加全局库兜底。
- **工作台（Person 任务入口）→ 聚合 PERSON + AGENT 库**：
  filter = `scope_type = PERSON AND owner_person_id = 当前人`
  ∪ `scope_type = AGENT AND owner_agent_id ∈ 我可管理员工`
  ∪ 当前任务上下文项目的 PROJECT 库。
- **数字员工（agent_info，目标态 DigitalEmployee）**：必须挂
  `owner_person_id`（主归属边：谁的员工）+ `project_id`（任务归属边）
  两条边（Part A 已补列，与知识库归属同构；`ai_agent_tasks.project_id`
  是任务级同款先例）。`agent_info.knowledge_ids` 多对多 JSON
  **保留为「显式授权」而非唯一线索**——归属决定默认可见集，
  授权决定跨归属借用集；两者取并集后再过 sensitivity 闸门。
- **C08 纪律（owner 口径）：AI 产出不自动入库，须人审登记。**
  仓内同源红线三处互证：①`AiSuggestionP3ScenesTest` 头注释
  「AI 输出仅 markdown 不写业务表（继承 R227-C1 红线）」；
  ②《AI能力用户故事与全功能测试计划-20260926.md》身份纪律段
  「人审闸门只卡业务写入（BR-AI-05）」；
  ③《整改清单-20260928.md》O-17 验收标准「草稿零自动入库」。
  落到知识库链路：LLM 产物 → `ai_documents`/交付物区 → 人审通过 →
  以 `source_type=AI_GENERATED + source_ref=产物ID` 显式登记进
  knowledge_attach，**永不允许 Listener 无人审直通 embedding 链**
  （定稿件自动入库提案 D5/O-17 同样以「只入定稿门限」为前置）。

## 8. 最终裁决（share × RBAC 合并、权限权威源、Part B 前置）

> 本节由主协调会话依据三路只读探针（RBAC 权威源 / share 全量真实用法 / Part B 影响面）
> 与独立 Validator 复核证据自行判定。**工程判断项，不属于需 owner 拍板的业务裁决**；
> 逐项附证据与不可逆性评估。

### 8.1 share 与 sensitivity 的关系（已定）

**事实前提（探针 B 取证）**：`share` 在全仓的唯一消费点是
`KnowledgeInfoServiceImpl.buildQueryWrapper` 里的 `lqw.eq(bo.getShare() != null, ...)`
——客户端可选筛选参数，前端 4 份表单一律不传；RAG / chat / agent 检索链路
**零 share 判断**；`idx_tenant_share` 无查询走它（死索引）；现网 `share=1` 存量为 0 行。
结论：**share 从未构成安全边界**，真正的隔离一直是 tenant 拦截器 + Sa-Token 权限码。
因此本项是工程取舍，不存在需要业务方拍板的保密偏好冲突。

最终规则：

1. 迁移映射 `share=0 → sensitivity='INTERNAL'`、`share=1 → 'PUBLIC'`；
   **SECRET 禁止由任何自动规则产生**（升密只能人审显式改）。
2. `scope_type` 存量沿用 `'PERSON'`。明确**否决**探针提出的 `scope_type='TENANT'`
   方案——Part A 枚举只有 `GLOBAL|GROUP|PROJECT|PERSON|AGENT`，不得为迁移便利发明枚举值；
   「租户内公开」语义由 `sensitivity=PUBLIC` + tenant 拦截器共同表达。
3. `share` 降级为**只读派生兼容镜像**：由后端在写 sensitivity 时同步
   `share = (sensitivity=='PUBLIC' ? 1 : 0)`，读取侧一律以 sensitivity 为准；
   前端表单不再暴露 share（随 Part B 孤儿表单收敛一并删）。
4. `idx_tenant_share` 在 Part B 检索过滤切到 sensitivity 后退役，换 `idx_tenant_sensitivity`。
5. 作废原 U1 的「share OR sensitivity 保守并集」兜底——share 非边界，并集只会
   凭空扩大可见面，属过度设计。

### 8.2 sensitivity 的权限权威源（已定：双层单源）

归属与上限的唯一权威源在 **IPD 侧**（`IpdPermission` / `IpdAuthSession` /
`IpdStpInterfaceBridge` / `IpdRolePermissionCatalog`），框架侧（ruoyi-chat）**不自立第二套上限**，
只经桥消费结果。理由：依赖方向是 ruoyi-ipd → ruoyi-chat 单向，框架天然读不到 `persons`，
反向读会形成长期双轨。

- 上限映射（effective = javaDefault ∪ dbGrant − dbRevoke）：
  `SUPER_ADMIN`/`GROUP_LEADER` → SECRET；`MARKET_PM`/`RD_PM` → INTERNAL；其余 → PUBLIC。
- `personType` 未登记或查不到 personId 映射时 **fail-closed 降到 PUBLIC**
  （`IpdRolePermissionCatalog` 对未知类型返空=拒绝一切，与之同构）。
- 数字员工（`agent_info.sensitivity`）的可处理上限不得高于其 `owner_person_id` 的上限——
  取两者交集，防止「借员工升密」。

### 8.3 既存高危口子（先于 sensitivity 存在，Part B 安全前置 B0）

| 口子 | 位置 | 现状 | 处置 |
|------|------|------|------|

### 8.4 Part B 排期（三档）

- **B0 安全前置**（S1/S2/S3）：不依赖 Part A 之外的新列，可独立评审与回归；S3 未修完
