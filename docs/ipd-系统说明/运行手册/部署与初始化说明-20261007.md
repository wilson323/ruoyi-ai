## 一、这次改造做了什么（部署前必须知道）

**改造前**：种子数据初始化器 `IpdZkScenarioInitializer` 挂着 `@Profile("dev")`，
只在开发环境灌数据。**生产环境部署完成 = 空库**——没有人员、没有产品组、没有任何项目，
登录进去什么都看不到。

**改造后**：改为**全环境默认开启**（2026-10-07，`abb6c4e8`）。

| 项 | 值 | 出处 |
|---|---|---|
| 开关 | `ipd.seed.zk-scenario.enabled` | `application.yml` |
| 默认值 | **`true`**（会灌种子数据） | `application.yml:219` |
| 关闭方式 | `ipd.seed.zk-scenario.enabled=false` | 实测该注解读取处 `IpdZkScenarioInitializer.java:66` |
| 灌什么 | ZK-IPD 基线场景：**6 个产品组 / 13 人 / 5 个项目** + 阶段与动作<br>⚠️ 此三数为**代码注释所载**，非本轮实测（见下方未取证说明） | `application.yml:214` |
| 幂等性 | 重复启动不会产生重复数据 | 实现为 rebind/存在即跳过 |

## 二、Gate 要素种子**故意没有开关**

`gate_review_elements`（33 条 Gate 要素）**不受上述开关控制**，这是刻意的：

- 它是 Gate 评审的业务前置，缺了整套评审跑不起来；
- 实现是「**仅当表空才写**」，表非空时一行不写、**绝不覆盖已有数据**。

> 排查思路：如果发现 Gate 要素不对，**不要用开关解决**——那个开关管不到它。
> 要查的是 `IpdGateElementSeedInitializer` 与表内实际内容。

### 4. 验证「不是空库」

**这是本次改造的核心验收点**——改造的意义就是避免生产装完是空库。

```bash
# ① 三个种子表都应有数据（真库回读，用 COUNT(*) 不用 table_rows 估算值）
SELECT COUNT(*) FROM product_groups;      -- 预期 6
SELECT COUNT(*) FROM sys_user;            -- 预期 ≥13
SELECT COUNT(*) FROM projects;            -- 预期 5

# ② 服务活着（401 = 活着但未登录，属正常，不是失败）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:16039/api/v1/auth/me
```

**若三张表都是 0**，按第三节排查：先看启动日志有没有 `IpdZkScenarioInitializer` 相关输出，
再确认 `ipd.seed.zk-scenario.enabled` 没被环境变量覆盖成 `false`。

## 四、出问题时的处置

| 现象 | 先查 | 处置 |
|---|---|---|
| 装完是空库 | 启动日志、`ipd.seed.zk-scenario.enabled` 取值 | 确认开关为 `true`；确认 profile 是 `ipd-local,dev` |
| 不想要基线数据（要纯空库部署） | — | 设 `ipd.seed.zk-scenario.enabled=false`。**注意：这是不可逆的种子写入，关掉只防将来灌，已经灌进去的数据要自己清** |
| Gate 要素不对 | 表内实际内容 | **不受上面开关管**；查 `IpdGateElementSeedInitializer` 与表内容 |
| 种子数据重复 | 是否绕过种子器直接插过 | 种子器本身幂等；重复多半是外部直接插数据造成的 |
