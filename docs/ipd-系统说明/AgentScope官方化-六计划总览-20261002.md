## 2. 四组官方内容，用人话说明

| 内容 | 负责什么 | 本项目如何用 |
|---|---|---|
| SDK 文档 `/docs` | 写进 Java 程序的工具箱：让模型接收任务、调用工具、保存上下文，处理权限、超时和输出 | 嵌入现有 Spring 后端，由项目服务决定业务规则 |
| Service `/service` | 另部署一套管理平台：登记智能体、派工作、组织协作、提供控制台和服务接口 | 当前不引入运行依赖；作为未来跨应用治理评估对象 |
| 集成 `/integration/overview` | 工具箱的连接件：模型、存储、知识库、MCP/协议、消息平台、调度等按需接入 | 使用已有模型和检索资源，不把全部扩展装进来 |
| Harness 四篇博客 | 如何把一次模型回答组织成可持续、可恢复、可检查的工作过程 | 用作责任、任务、信息和行动设计方法；不是锁定版本的 API 合同 |

SDK 像装在本系统里的发动机零件；Service 像额外建设的调度和管理中心。SDK 可以独立使用，不需要 Service。Service 的 Managed 是平台代跑，External 是原应用继续跑再接平台，Hosted 是平台派给现成的执行工具。本项目现查是 SDK 进程内应用，并没有因此成为 Service External。未来若接 Service，External 最接近当前形态，但注册不等于已具备任务派发、恢复和验收。

建议采用「固定业务流程 + 智能体完成专业工作」：六阶段、动作、审核和 Gate 由现有 IPD 服务控制；智能体检索、分析、生成和提出下一步。一次运行成功、产物质量通过、人员审核通过、动作批准、Gate 放行是五件不同的事。Service 页面标注预览，不把它写成当前上线前置。不用 Service 不等于不用官方 Harness；不打开每个开关也不等于缺能力。

## 3. 架构判断与适用范围

裁决：部分闭环，不能判定全局架构已完善或生产就绪。源码已具备独立 ProjectAgentController、HarnessAgent、冻结技能、选定工具检查、Redis 状态、运行归属与完成门。仍需全入口权限/存储键核验、真实故障恢复、质量与业务完成分离、行为回归、当前包一致性及真实人员旅程。

推荐链路：Person会话 → 项目权限/动作入口 → 校验并冻结运行配置 → 既有运行服务/归属锁 → SDK HarnessAgent → 已选模型与受控只读检索/MCP → 产物版本/质量结果 → 人员审核 → 既有定档应用服务 → 数据回读 → 动作批准/Gate。失败显式不可用，恢复入口走原运行服务；不回落副驾。

权威分工：业务库负责成员、角色、项目/产品、动作、审核、Gate、运行和产物；SDK状态只负责执行上下文；Redis锁只协调执行；模型输出不是事实或授权。工作区、会话、任务、WebSocket连接不能互相代替。当前模型/嵌入配置按既有权威回读，不新建第二模型配置或向量库。

立即适用：官方执行循环、明确超时/有限重试、上下文压缩、工具结果按需卸载、固定技能版本、工具参数/权限检查、最小上下文、证据完成、审计与行为回归。条件适用：分布式存储组合、团队智能体、共享记忆、沙箱、消息渠道。当前保持既有边界：动态技能、Plan、记忆、Shell/文件等能力完整启用，技能晋升经 owner 批准、计划不代替业务批准、记忆不自动成为业务事实；具体操作按官方权限扩展点限制到授权范围，禁止隐式模型回退或第二运行/文档接口。研发助手的文件工具需求与项目业务智能体分别评估。
