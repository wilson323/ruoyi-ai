## 0. 先纠正一个前提：本仓有两套 AI，一张是只读，一张早就能写

派单里说「AI 智能体目前没有任何写 IPD 业务数据的工具」。**这句话只对 AgentScope 那条线成立。** 本仓并存两套 AI，能力完全不同：

| | A. AgentScope 项目智能体 | B. AI 副驾 / 动作执行 |
|---|---|---|
| 入口 | `ProjectAgentController`（`/api/v1/project-agent/**`） | `AiCopilotController`、`StageActionController`、`AiAgentTaskController` |
| 核心类 | `AgentScopeProjectAgentKernel`、`ProjectAgentToolCatalog`、`ProjectAgentRunExecutor` | `AiCopilotService`、`AiExecutionEngine`、`service/aiexec/*` |
| 能不能读项目资料 | 能（RAG，`ProjectKnowledgeSearchTool`） | 不能（单轮 prompt，无检索） |
| 能不能写业务表 | **不能**（工具目录全只读） | **能**（`stage_actions`，且已上线） |
| 写入是否要人确认 | 是（人点 apply，只写文档库） | 是（人点保存或人点 AI 执行） |

也就是说：**「AI 出建议 → 人确认 → 写业务表」这条闭环本仓已经跑通了一年量级的迭代**（`aiexec` 包 6 个测试类在跑）。真正缺的不是「写的能力」，而是「有 RAG 的那个智能体」和「能写库的那条链」互相看不见——A 读得到资料但写不了，B 写得了库但读不到资料。

> **因此任何「新建一套 AI 写入体系」的方案都应直接否决**（本仓明文禁止双轨）。下面的设计全部建立在既有件之上。

## 1. 现状与天花板（只读 AI 的确切边界）

### 1.1 AgentScope 这条线今天能做什么

- **读项目已审核文档**：`ProjectKnowledgeSearchTool implements AgentTool`，构造时绑定 `boundProjectId`，参数 schema 不暴露 `projectId`/`tenantId`，模型传入一律忽略。执行前经 `ProjectAgentOfficialToolGovernance` 的 `OwnedTool` 包装做所有权与作用域校验。
- **读产品线 MCP**：`ProductLineMcpCatalog` / `ProductLineMcpTool`，同样是只读查询。
- **产出产物草稿**：经 `deliver_artifact` 落到 `ipd_agent_artifact_version`（`STATUS_DRAFT`）。
- **等人采纳**：`POST /agent-runs/{runId}/artifacts/{artifactId}/apply` → `ProjectAgentRunService.applyArtifact` → `AiDocumentService.createGeneratedAuthorized` → 写 `ai_document`（项目文档库）。
- **暂停 / 恢复**：`ProjectAgentAguiPauseResumeService` 提供 pause / consume / replay / loadConsumedIntent / authorizeRecoveredIntent 全套。但注意：**`ProjectAgentOfficialPermissions` 当前只登记了一条 ASK 规则，名字是 `plan_exit`。** 也就是说配套机制齐全，但实际启用的确认点只有一个。

### 1.2 为什么它「只能产草稿」——三条硬原因，各有出处

1. **工具目录层面就封死了写**：`ProjectAgentToolCatalog.descriptors()` 给每个工具构造的 `ToolDescriptor` 能力集合恒为 `{READ, SEARCH}`；`ProjectAgentToolCatalog.status()` 对任何带 `WRITE`/`DESTRUCTIVE`/`EXECUTE`/`NETWORK` 的描述符直接返回 `available=false`，理由文案是「W1 仅开放只读工具」。这不是「还没实现」，是**明确的一刀切拒绝**。
2. **唯一的业务写入发生在人的 HTTP 线程上，不在运行线程上**：`ProjectAgentRunService.applyArtifact` 第一行就是 `requireOwnRun(actor, runId)`，`actor` 来自 `IpdPermission.requireInternal()`，而 `requireInternal()` 读的是 `session.currentPerson()`（Sa-Token 会话）。运行本身则跑在后台调度器上（`ProjectAgentRunExecutor.submitPrepared` 里 `scheduler.schedule(...)`，并配 Redis 租约 `ProjectAgentRunOwnership`），**没有 HTTP 会话**。
3. **`IpdActor` 是全部越权守卫的第一入参**：`IpdIdorGuard` 的 6 个守卫、`IpdPermission.requireActionWriter` 的角色锁 + `IpdIdorGuard.requireProjectMemberOrSuperAdmin`，全部以真 actor 为前提。运行线程里造不出真 actor。

### 1.3 那条「能写」的线（B）的确切边界

- 白名单是唯一收口：`AiCopilotService.FILL_FIELD_WHITELIST` 只有一个 scene `stage-action-fields`，只有 6 个字段 `actualDoneAt / farValue / frrValue / certNo / certPassedAt / algoType`。类注释写明与 `POST /stage-actions/{id}/fields` 的可落库字段**严格同构**，且 `remark` 是刻意移除的（曾造成「假成功」）。
- 过滤函数是 `AiCopilotService.filterFillFields`，与白名单同处一个类、**包级可见**（无修饰符）。
- 产出恒为建议：`fillPayload` 里 `mode` 恒为 `"suggest"`，注释写「首切片永远 suggest（敏感字段红线）」。
- **建议行在架构上不可能被自动执行**：`AiExecutionTrigger.triggerChat` 把 CHAT 行插入即置 `STATUS_SUCCEEDED`，而 `AiExecutionEngine.dispatchCycle` 的查询里 `.ne(AiAgentTask::getTriggerType, AiAgentTask.TRIGGER_CHAT)` 把 CHAT 行排除在派发之外。注释写得很明白：「若被派发会给执行器 auto-transit，违背『填表需用户确认』的人审红线」。
- 真人写入口：`StageActionService.recordFields`（`@Transactional(rollbackFor = Exception.class)`，`stage_actions` 上有 `@Version` 乐观锁，更新行数 `!= 1` 即抛「可能并发冲突」），经过 `IpdPermission.requireActionWriter`。

**结论：B 线已经具备我需要的全部安全性质，而且其中「CHAT 建议行永不被自动派发」是一条已经实现在代码里、可被测试证明的性质。这是本切片应该复用的东西。**

## 2. 已有的安全地基够不够？——够，但确认点必须落在人的 HTTP 线程上（结论：**扩展，不新造**）

### 2.1 结论

**扩展既有两个可插拔位即可，不需要任何新机制、新表、新权限面。**

- agent 侧扩展位：新写一个 `AgentTool`，走 `Toolkit.registerAgentTool` + 既有 `OwnedTool` 治理包装，形态与 `ProjectKnowledgeSearchTool` 完全同形。
- 人确认侧扩展位：**原封不动复用 `POST /stage-actions/{id}/fields`**。

### 2.2 为什么否决「给智能体一个能在运行内直接写业务表的工具」

理由一（决定性）：**运行线程没有会话身份，写不出合规的操作人。** `IpdPermission.requireActionWriter` 需要 `session.currentPerson()`；运行在 `scheduler.schedule` 调度的后台线程上。若为此伪造一个系统 actor，等于让写入绕开 `IpdIdorGuard` 的全部门禁——那正是 W5-E 那一轮 19 个 P0（含「任意改密码」）被修复的面。**用一个高权限系统身份替模型执行写操作，是本仓安全模型里最不该开的口子。**

理由二：**本仓自己的恢复协议明确拒绝重放带副作用的工具效果。** `ProjectAgentAguiPauseResumeService.authorizeRecoveredIntent` 会扫描暂停之后的事件流，一旦发现 `TOOL_EXECUTION` / `STARTED`，直接抛「原恢复工具效果需先对账，不能自动重放」。把业务写做成工具效果，意味着每次租约恢复都要人工对账一次——这是实打实的可用性代价，不是理论风险。

理由三：**ASK 规则不是业务授权。** `ProjectAgentOfficialPermissions` 的 ASK 走的是 SDK 的 `PermissionContextState`，批准值来自客户端 `RunAgentInput.resume`。`consume()` 里虽然有 `TrustedGuard` 校验检查点与暂停序号，但**校验的是「这次恢复是否对应原中断」，不是「这个人有没有权限改这条业务行」**。业务授权必须来自 `IpdPermission`，不能来自 SDK 的批准语义。两条链混淆，就是本仓注释里记过的那种「两条同名不同机制的路径被误看成一条」的错。

### 2.3 为什么不是「新造」

因为要的性质已经全部存在且已在跑：

| 我需要的性质 | 既有的实现 | 出处 |
|---|---|---|
| AI 只能提建议，绝不能自己落业务表 | CHAT 行插入即终态 + `dispatchCycle` 排除 CHAT | `AiExecutionTrigger`、`AiExecutionEngine` |
| 字段面收窄到安全集合 | 单 scene + 6 字段白名单 + `filterFillFields` | `AiCopilotService` |
| 人确认才写 | `POST /stage-actions/{id}/fields` | `StageActionController` |
| 写入署名真人、角色锁、在职成员、租户一致 | `requireActionWriter` → `IpdIdorGuard.requireProjectMemberOrSuperAdmin` | `IpdPermission`、`IpdIdorGuard` |
| 并发安全 | `stage_actions.@Version` 乐观锁 + 行数校验 | `StageAction`、`StageActionService` |
| 失败即整体回滚 | `@Transactional(rollbackFor = Exception.class)` | `StageActionService.recordFields` |
| 可追溯 | `auditLogService.append` + before/after 6 字段快照 | `StageActionService`、`AuditEventData` |

新造任何一件都是重复实现。

## 3. 最小切片

### 3.1 一句话

**让 AgentScope 项目智能体把它从「本项目已审核文档」里读出的阶段动作字段值，写成一条 `ai_agent_tasks` 的 CHAT 建议行（scene=`stage-action-fields`，6 字段白名单，mode=suggest）；人在动作详情页看到建议、修改、点既有保存端点，由 `StageActionService.recordFields` 写入 `stage_actions`。**

选 `V02`（认证送检，`valueFields` 含 `CERT_NO`）或 `D11`（BioCV 算法评测，`valueFields` 含 `FAR,FRR`）作为首个动作——这两个恰好是「值必须从报告里抄」的典型：现在 PM 得自己翻检测报告、抄 6 个字段；改造后 AI 读文档 + 填好，人校对。

### 3.2 端到端七步

| 步 | 发生什么 | 落点 |
|---|---|---|
| 1 用户发起 | `POST /api/v1/project-agent/agent-runs`，`actionCode=V02`，工具集勾选新工具 | `ipd_agent_run` |
| 2 AI 生成待写内容 | agent 先调 `project_knowledge_search` 检索项目已审核文档，再调新工具提案 `{certNo, certPassedAt}` | 内存 |
| 3 落到具体业务表 | **落不到。** 工具只调 `AiExecutionTrigger.triggerChat(...)` 写一条 CHAT 行；`fields` 写入前先过 `AiCopilotService.filterFillFields("stage-action-fields", raw)`，白名单外一律丢弃 | `ai_agent_tasks` |
| 4 暂停等真人确认 | **不在 agent 运行内暂停。** 运行正常结束（`AGUI_INTENT`/ASK 只用于 `plan_exit`，本切片不用）。确认点是第 5 步的人 | — |
| 5 真人确认 | 打开动作详情页，新读口取回建议 → 前端回填表单 → 人改 → 点保存 | `GET` 新读口 + `POST /api/v1/stage-actions/{id}/fields` |
| 6 写入 | `requireActionWriter` → `recordFields` 事务内落库，`@Version` 乐观锁 | `stage_actions` |
| 7 回读验证 | `GET /api/v1/stage-actions?projectId=…` 读回该行，比对 6 字段与 `updateBy` | — |

### 3.3 涉及类与表

**新增（少量）**

- `StageActionFieldProposalTool implements AgentTool`（放 `org.ruoyi.ipd.agent.kernel`，与 `ProjectKnowledgeSearchTool` 同包同形）。构造时绑定 `boundProjectId` **与** `boundStageActionId`；参数 schema 只暴露 `fields`，**不暴露 projectId / stageActionId**——否则模型可重定向写入目标，与 `ProjectKnowledgeSearchTool` 的「参数 schema 不暴露 projectId」同一原则。
- 门禁测试：锁住「非白名单工具 id 一律 unavailable」。

**改造（2 处，都极小）**

- `ProjectAgentToolCatalog`：登记新工具 id 与 `ToolDescriptor`（能力集合含 `WRITE`）；把 `status()` 里「按能力一刀切拒绝」改成**按工具 id 显式白名单放行**。
- 白名单真源收口：`AiCopilotService.FILL_FIELD_WHITELIST` 与 `filterFillFields` 目前是包级可见，`org.ruoyi.ipd.agent` 包用不了。提为 public 或提到中立常量类，**禁止复制第二份**。

**复用（零改动）**

- `AiExecutionTrigger.triggerChat` —— 既有唯一写 `ai_agent_tasks` 的入口。
- `POST /api/v1/stage-actions/{id}/fields` → `StageActionService.recordFields` —— 人确认的唯一写入口。
- `IpdPermission.requireActionWriter`、`IpdIdorGuard`、`stage_actions.@Version`、`auditLogService`。

**新增一个窄读口**

- 建议内容读回。注意 `AiAgentTaskView` 的红线是「prompt / fillPayload / inputDigest / dedupKey **一律不出此 VO**」，所以**不能复用 `AiAgentTaskView`**。新读口独立 VO，只出白名单 6 字段；鉴权走 agent 运行自己的 `requireOwnRun(actor, runId)`。

**涉及表**

| 表 | 本切片对它做什么 | 备注 |
|---|---|---|
| `ai_agent_tasks` | 新增 CHAT 建议行（只增不改） | 已登记 `tenant.excludes`，运行线程无租户上下文也可安全写 |
| `stage_actions` | 唯一被写的业务表 | `@Version` 乐观锁；写入发生在有会话的 HTTP 线程 |
| `ipd_agent_run` / `ipd_agent_run_event` | 只读，不新增事件类型 | — |

### 3.4 四个「怎么」

- **确认在哪一步拦**：第 5 步的人点按。**不在 agent 运行内拦**（见 §2.2 三条理由）。
- **写失败怎么回滚**：`recordFields` 自带事务，异常整体回滚；`updateById` 行数 `!= 1` 抛业务异常。建议行不受影响——**它本来就没写过业务表**，所以不存在「AI 侧脏数据要回滚」的问题。这是本设计最大的好处。
- **重复确认怎么幂等**：填同值再存 = 同结果。并发用 `@Version`（冲突即抛「字段更新失败：可能并发冲突或记录不存在」）。若人走的是 `POST /stage-actions/{id}/ai-execute`：`AiActionExecutor.terminalNoOp` 对 DONE/NA 动作 no-op（不改写历史完成日、不重复挂交付物），`AiExecutionEngine.claim()` 用条件 UPDATE `PENDING/FAILED → RUNNING` 保证多实例下只有一个执行；失败有 attempt/退避/DEAD 三级收口。
- **越权怎么拦**：写入口三层——Sa-Token 权限码 `OPERATION_STAGE_ACTION_EXECUTE` → `requireActionWriter`（角色锁：`action.ownerRole` 对 `actor.role()`，`BOTH` 允许 MARKET_PM/RD_PM）→ `IpdIdorGuard.requireProjectMemberOrSuperAdmin`（在职成员 + 租户一致）。读建议口用 `requireOwnRun`（只看得到自己的运行）。工具侧：项目与动作在构造时绑定，schema 不外露，模型无法改目标。

## 4. 不做什么

**明确划出边界：**

- 不给 agent 任何能在运行内写业务表的工具（本切片 agent 侧写的唯一落点是 `ai_agent_tasks`）。
- 不新增第二条写 `stage_actions` 的路径——全部复用 `recordFields`。
- 不做「AI 全自动完成动作」：`transit(DONE)` 不在本切片。
- 不跨项目、不跨动作、不做批量。
- 不扩白名单到 6 字段以外。金额 / 角色 / ID 类字段永不开放。
- 不碰 Gate 双签、KPI、津贴核算、招投标。
- 不改前端仓；不改 `docs/开发说明/**` 的任何业务决策。

**必须等 owner 拍板（可直接回答）：**

1. AI 产出的阶段动作字段建议，**是否允许同项目其他成员看到并采纳**？还是仅发起运行者本人可见？（决定新读口的鉴权范围是「项目成员」还是「运行 owner」）
2. AI 建议被采纳后，**审计日志是否需要区分「AI 建议来源」与「人工填写来源」**？现在 `recordFields` 写的 reason 是固定的「P1-4.1/P1-8.2 完成字段录入」，两种来源在审计里长得一模一样。
3. 这条切片跑通后，**是否授权把工具准入从「只读白名单」扩到「写建议白名单」并在生产开启**？还是先只在非生产验证？
4. **没人采纳的建议行保留多久**？（涉及 `ai_agent_tasks` 增长与审计口径）

## 5. 风险

| # | 最可能出错的地方 | 最坏后果 | 怎么防 |
|---|---|---|---|
| R1 | 改 `ProjectAgentToolCatalog.status()` 时，为了「让新工具通过」而把它的能力集合标成 `READ` 蒙混过关，而不是显式改判定逻辑 | 所有后续写工具的准入失去唯一收口点，「W1 仅开放只读工具」这条硬约束从内部被掏空，且以后没人看得出来 | 判定改成**按工具 id 显式白名单**，不再按能力集合推断；加门禁测试锁住「非白名单 id 一律 unavailable」。这条是本次改造里**唯一需要动既有安全判定逻辑**的地方，必须单独评审 |
| R2 | 模型往 `fields` 里塞任意键（含 `id`、`projectId`、`amount`） | 若过滤漏掉，越界字段可能被下游当有效值 | 写入前过**与 `AiCopilotService` 同一份常量**的 `filterFillFields`，不复制第二份；`mode` 恒 `suggest` |
| R3 | 人在页面上不核对就点保存，等于 AI 直写 | 错误的认证编号 / 算法指标进了 `stage_actions`，污染后续 Gate 判定与 KPI | 建议值在 UI 上与人工值可区分（需 owner 拍板第 2 问）；审计已记 before/after 6 字段快照，事后可追溯；但**UI 区分这件事超出本仓范围**，必须前端仓配合 |
| R4 | 白名单两份实现漂移 | 出现「AI 填的字段端点结构性不接收」的假成功——本仓已经因为 `remark` 犯过一次，注释里写明「形成『假成功』」 | 提为单一真源；加测试锁住「白名单集合 == `POST /stage-actions/{id}/fields` 的 DTO 字段集合」 |
| R5 | 新读口图省事复用 `AiAgentTaskView` | 破掉「fillPayload / prompt 永不出 VO」的既有红线，prompt 可能被回吐给前端 | 独立 VO，只出白名单字段，不出 prompt / inputDigest / dedupKey；加测试断言 VO 无这些字段 |
| R6 | agent 线程调 `triggerChat` 的事务语义与预期不符 | 建议行落不下去（`triggerChat` 有「有事务走 afterCommit、无事务直接派发」两个分支） | 实现前先确认运行线程的 `TransactionTemplate` 使用方式（见 §6 不确定项） |

## 6. 工作量

**粗估 6～9 人日（不含前端，不含 owner 拍板等待时间）。**

依据——我读了下列代码得出这个数：

| 工作项 | 估 | 依据 |
|---|---|---|
| 新工具类 | 1 人日 | `ProjectKnowledgeSearchTool` 271 行，同形实现含 schema、参数校验、结果文本、来源上报 |

## 8. 记忆晋升（owner 2026-10-03 已拍板：按人采纳）

> 本节按 owner 已拍板的口径写，**不作为待决问题**。拍板内容：`ipd_agent_memory` 的晋升条件 = **被人工采纳过**。否掉了「按出现次数」，也否掉了「要求人工逐条点确认」。

### 8.1 先把现状说准：晋升路径设计好了没接线，而且今天晋升**不改变任何行为**

三件事必须一起看，否则会把工作量估反：

1. **晋升口已存在且正确**：`IpdAgentMemoryMapper.promoteTo(id, projectId, personId)`，SQL 带 `status = '0'` 前置条件，天然幂等，也不会把废弃条改回来。但 **src/main 里零调用方**——只有测试用反射断言它的 SQL 文本。所以「按人采纳」缺的不是晋升能力，是**触发点**。
2. **候选态今天已经能被召回**：`recallForScope` 的条件是 `del_flag = '0' AND status IN ('0','1')`。`status` 是不是 `'1'`，**今天不影响召不召回**。
3. **`status` 今天只影响标注强度**。`IpdAgentMemory` 类注释写明：`status = PROMOTED`「只表示该条已并入权威知识库，它的作用是让召回文本能区分『已沉淀』与『仍是草稿』」。

**推论：只把 `promoteTo` 接上，等于什么都没发生。** 要让 owner 的口径真正落地，必须同时改召回条件（见 §8.4）；否则「按人采纳」只是一行没人看的标注。

### 8.2 采纳信号：定义在 artifact apply 上（这条路后端可单独闭环）

**结论：「被人采纳过」在本仓最精确、已有留痕、零新存储的定义是——该次运行的产物被人 `apply` 进了项目文档库。**

理由：
- `POST /agent-runs/{runId}/artifacts/{artifactId}/apply` 已经是人主动点按的动作，服务端 `requireOwnRun(actor, runId)` 保证是本人运行。
- 结果是**持久事实**：`ipd_agent_artifact_version.status = 'APPLIED'` + `documentId` 非空，且 `markApplied` 是条件更新，幂等与并发安全都现成。
- 语义与 `PROMOTED` 的既有定义**对齐**：`apply` 把产物并入项目文档库，`PROMOTED` 表示记忆已并入权威知识库——同一个动作的两个投影。
- 有真实体量：派单转述「52 条产物里 10 条被应用过」（**该数字我未独立复核，见 §7**），所以「按人采纳」不会冷启动到零。

**为什么不直接把 `PUT /ai-feedback/{targetType}/{targetId}` 的 `UP` 当采纳用**（虽然它是最省事的既有端点）：`ipd_ai_feedback` 的唯一键是 `(target_type, target_id, person_id)`，同一人对同一目标只有一行，**先 `UP` 再 `DOWN` 会把「采纳」改写成「不采纳」**，而记忆一旦晋升就已经改变召回行为——撤销不回来，留下状态不一致。而且 `UP` 在既有 UI 里是「点赞」，把它当「采纳」用，正是本仓注释里记过的那类错：「两条同名不同机制的路径被误看成一条」。若要复用 feedback 通道，应**新增一个 `ADOPTED` 取值**，而不是借用 `UP`；且写入后不可改回。

**前端「采纳」按钮（`ruoyi-ipd-web` 仓 `ai-suggest.vue`）这一期不接。** 该组件今天只 `emit` 给宿主页面填表单、零网络请求，而且它手上的建议对象**没有 runId**——runId 只有服务端知道。要接它，必须先有 §3 那个窄读口把 `originRunId` 带到前端。所以它属于**第二期**：等 §3 的读口落地后，`ai-suggest.vue` 在 emit 的同时带 `originRunId` 发一个采纳信号，后端复用同一套晋升逻辑。这印证了派单里的判断——「按人采纳」在**建议**这条路上确实不能后端单独做完；但在**产物 apply** 这条路上，后端单独就能闭环。

### 8.3 顺序问题：抽取在运行结束、产物在运行中、采纳在两者之后——必须两个方向都覆盖

时间线：

- **t0 运行中**：`deliver_artifact` 落 DRAFT 产物。
- **t1 运行结束**：`ProjectAgentLongTermMemoryMiddleware.recordConversation` 启动**异步**抽取。
- **t1.5 抽取完成**：`ProjectScopedLongTermMemory.record()` → 模型抽 `(kind, content)` → `insertIgnoreDuplicate`，`status = STATUS_CANDIDATE`。
- **t2 人点 apply**。

t2 远晚于 t1.5 是常态，**但不是必然**：抽取有 10 秒空闲超时 + 45 秒总超时，失败会写 `MEMORY_RECEIPT`（`status = WRITE_FAILED`、`retryable = true`），类注释明说「可按回执补写」。补写若发生在 t2 之后，而系统只有「apply 时批量晋升」这一条路，那么补写出来的记忆会**永远是候选**——一次静默丢失，且外形与「这轮本来就没抽出东西」一模一样。本仓刚在 `RecordOutcome` 上专门修过这个「三态必须互斥」的问题（`noResult()` / `written()` / `failure` 恰有一个成立），不要在晋升这里再犯一次。

**所以两条路都要：**

- **方向 1（采纳 → 记忆）**：`applyDraft` 成功后，按 `runId` 批量晋升该 run 的候选记忆。需要 mapper 加一个按 runId 的批量口（现有 `promoteTo` 只按单 id）。
- **方向 2（记忆 → 采纳）**：抽取写入时先判定该 run 是否已被采纳，是则直接以 `STATUS_PROMOTED` 落库，不再是候选。

方向 2 的「该 run 是否已被采纳」查询**零新存储**：复用 `ArtifactVersionStore.listByRunIds(List.of(runId))` 判断有无 `STATUS_APPLIED`。其实现 `MybatisArtifactVersionStore.listByRunIds` **不带租户条件**，异步抽取线程可安全调用；`ipd_agent_artifact_version` 也已在 `tenant.excludes` 登记（`application.yml` 第 374 行），这条路径没有租户上下文问题。注入方式：给 `ProjectScopedLongTermMemory` 的构造器加一个小的判定接口——它现在只依赖 mapper + model，**不要让它直接依赖 artifact store**。

**执行时机**：方向 1 必须挂在 `applyDraft` 的**同一事务内**。理由与 `markApplied` 同——`applyDraft` 已经用「抛冲突让本事务回滚新建文档」的写法保证文档与产物状态同生共死，晋升必须挂在同一语义上，否则会出现「产物 applied 但记忆没晋升」。晋升失败必须让整个 apply 回滚，**不许吞掉**。

### 8.4 召回范围怎么切：同意派单的方向，但收紧一格，并补一个凭据字段

派单倾向「FACT 类只有被采纳过才召回，PREFERENCE / OBSERVATION 照旧」。**我同意这个切法的方向**，理由是它把切点落在「这条记忆会不会被模型当成业务断言」上：PREFERENCE（用户偏好）与 OBSERVATION（观察）错了只是让回答跑偏，**FACT 错了会被模型当作事实复述进正式产出**。用现成的 `kind` 字段表达这个差别，不需要新概念。

**我建议收紧一格：晋升时只升 `FACT`，不升另外两类。**

- PREFERENCE / OBSERVATION 的召回条件本来就不变，给它们打 `status = '1'` 只会稀释这个标记的含义。
- 收紧后 `status = '1'` 的语义变成单一可解释的：「这条**事实**被人间接背书过」。审计和运维看得懂，以后加别的消费者也不会误用。
- 代价：按 runId 的批量晋升口要加 `AND kind = 'FACT'`。这是设计选择，若 owner 要「全部 kind 一起升」很容易改回来——**但我建议先取窄的**：宽了以后想收窄，就得回头洗历史数据。

**再补一个我认为必要的字段：晋升必须写操作人。** 现有 `promoteTo` 只改 `status` 和 `update_time`，**没有写 `update_by`**。结果是「这条事实是何时、因谁的采纳变成已沉淀的」在库里查不到。建议新的批量晋升口带上 `update_by = 采纳人 id`（apply 路径上即 `actor.id()`）。否则以后审计问「这几百条是谁背的书」，答案只有空白。

**改完后 `recallForScope` 的条件形状**（示意，不是最终实现）：

```
WHERE project_id = ? AND person_id = ? AND del_flag = '0' AND status IN ('0','1')
  AND (status = '1' OR kind <> 'FACT')
```

**这一步是真实的行为变化，上线前必须先量现状。** 若 `ipd_agent_memory` 里已有相当比例的 FACT 候选行，收紧后它们会**立即不再被召回**——从用户视角看就是「AI 突然记性变差了」。所以：

1. 上线前先跑 `SELECT kind, status, COUNT(*) FROM ipd_agent_memory GROUP BY kind, status;` 把现状量出来（**我没有跑过这条查询，见 §7**）。
2. 若 FACT 候选占多数，做一次**一次性回填**：把 `run_id` 属于「已有 `STATUS_APPLIED` 产物」的那些 FACT 记忆行晋升。这条回填本身可验证——回填前后分别数 `kind='FACT' AND status='1'` 的行数，差值应当等于回填语句的 affected rows。
3. 回填是运维动作，**不是本设计的一部分**，须单独授权（本仓铁律：数据变更不走业务路径）。

### 8.5 这一节明确不做什么

- 不做「人工逐条点确认」（owner 已否），不做「按出现次数」（owner 已否）。
- **不做撤销/降级**：owner 口径是「被采纳**过**」，是历史事实，晋升单向。人若先 apply 后反悔（apply 本身目前也没有撤销口），记忆不回退。
- 不新增记忆表、不新增晋升状态取值、不改官方 `LongTermMemory` SPI 的两个方法签名。
- 不把记忆接进任何权限 / 动作审批 / 文档审核 / Gate 链路（`IpdAgentMemory` 类注释的权威性红线）。
- 不做「按 kind 配权重」之类的召回排序改造——超出本切片。
