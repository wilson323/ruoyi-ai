- **diff=28 不是同一根因被讨论 28 次，而是命名空间从首次打标到最近引用横跨 28 轮**

## 2. 根因判断（3 种可能性）

### 假设 ①：元根因命名粒度太细，每次都重新打标 = 假收敛
- **证据弱**：M-Root-1~7 是 R129 一次性打标，M-Root-8~11 是 R142 一次性打标，不是"每次都重新打标"
- **结论**：❌ 不成立

### 假设 ②：治理轮确实没解决真问题（28 轮反复出现 = 根因没被根治）
- **证据中**：从 R129→R157 这 28 轮里，确实多次出现同一 M-Root 的"反思段"（R142/R157 等）
- **但**：反思 ≠ 复发。反思段是**主动记录根因**，不是**根因真发生**
- **结论**：❌ 部分成立但脚本口径错（混了"反思记录"与"根因复发"）

### 假设 ③：检查脚本误报（28 是相邻 R 段号差，不是同一根因被讨论 28 次）
- **证据强**：脚本逻辑 = `last_R - first_R`，没区分"反思引用"与"根因发生"
- **结论**：✅ 成立。脚本把"首次打标 R 号"与"最近引用 R 号"混算差 = 命名空间生命跨度，不是根因复发跨度

## 3. 根因结论

**脚本设计缺陷**：把"元根因命名空间在 R 治理报告中的首次/最近出现号差"当作"根因复发跨度"。

实际语义应该是：
- **真根因复发** = 同一根因（M-Root-N）在治理轮 R 段中作为"待解决项"反复出现
- **误报** = M-Root-N 作为"已打标 / 已解决 / 已反思引用"在 28 轮内出现，这是健康状态（命名空间被持续使用 = 反思持续在做）

## 4. 推荐修复路径（docs-only，不改脚本逻辑也行）

### 路径 A：改脚本语义（撞车 0 不破）
- 把检测从"first_R vs last_R 差"改成"待解决项出现次数"（grep `TODO.*M-Root-N` 计数）
- 或改成"已闭环 M-Root-N 在最近 N 轮未再被引用 = 健康"

### 路径 B：接受误报（更现实）
- 治理轮元根因本就该持续在反思段中被引用（这才是飞轮）
- 脚本应当 PASS 而非 FAIL，把 FAIL 阈值改成 ≥ 50 轮（异常久未提 = 根因被遗忘）
- 把"反思空间健康度"作为 PASS 信号

### 路径 C：本次不修（推荐）
- 误报不破业务 — 治理轮工作流不依赖此门禁
- 等 owner 拍板 R142-P 系列后再决定改不改
