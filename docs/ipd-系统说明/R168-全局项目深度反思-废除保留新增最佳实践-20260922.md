# R168 — 全局项目深度反思：废除 / 保留 / 新增最佳实践（2026-09-22）

> **本包定位**：基于 R164 全项目大盘点（28 owner-blocked + 8 owner 派单）+ R167 拍板包（7 项 KPI 业务规则）+ BCP-015 门禁分级设计 + 5+ 轮历史教训（R25 五类病根 / 153ffded / 7bf840f6 / fdc4ea0d 等），主协调会话做**深度反思**——哪些"最佳实践"实为反模式该废除？哪些必须保留？哪些该新增？

## 一、该废除的"最佳实践"（反模式）

按"按真实发现列"原则，不强求数量：

### 1.1 「业务规则拍板包」模式 → 废除

- **反模式症状**：每次业务规则变更都起一个"OWNER 拍板包"，把所有参数列出来让 owner 选
- **实证**：R167 拍板包整理 7 项 KPI × 5 个参数 = 35 个空让 owner 填，**实际工作量 = 让 owner 做 owner 应做的工程决策**
- **根因**：把"工程决策"伪装成"业务决策"反馈给 owner
- **废除理由**：owner 不可能比执行单元更懂"PPM 目标值应该 80 还是 85"，这种参数**属于工程默认值**，可由执行单元按 DOC-01 + 行业基准 + 历史数据推断
- **新做法**：执行单元直接给默认值 + 在代码注释 + 验收报告标注「默认值待业务复核」，owner 仅有**否决权**无**指定权**

### 1.2 「等 owner 拍板再实装」流程 → 废除

- **反模式症状**：所有变更必须先拍板才能动代码 → 阻塞
- **实证**：R164 列 28 项 owner-blocked + 8 项 owner 派单，**28 项长期排队无人推**
- **根因**：把"异步串行"误用为"同步阻塞"
- **废除理由**：业务核心规则（奖金核算 / 缺陷率严重度）需 owner 拍板，**工程默认值**（PPM 目标值 / 阈值分段 / 评分维度）可以边实装边标注
- **新做法**：
  - **A 类（必须 owner 拍板）**：奖金核算 / 多实例部署 / DDL 破坏类 / 跨仓影响
  - **B 类（执行单元按默认值实装 + 标注）**：业务参数默认值 / 阈值分段 / 加权公式
  - **C 类（执行单元直跑）**：docs 同步 / 模式重构 / 命名清理

### 1.3 「撞号透明协议」过度严格化 → 部分废除

- **反模式症状**：每次撞号都要登记让路，每次 commit message 必须含"本会话 + 兄弟 + 前序"
- **实证**：R166 commit "本决策包 R166 前序:12becc36 兄弟:R165"格式复制多轮；b75416c2 借道 commit 实际 11 文件说 3 文件（**借道 commit 风险**）
- **根因**：把"写权分配"误用为"时间片分配"，每次都要登记协商
- **废除理由**：时间片分配方式撞车率高（b75416c2 借道就是时间片撞车副作用），按**子系统划分写权**效率更高
- **新做法**：
  - **保留**：单文件单写者基本纪律（避免同一文件被两会话同时改）
  - **废除**：「每次撞号都登记」→ 改为「按子系统写权分配（person / project / gate / system 各一个会话写权）」
  - **废除**：「commit message 必须含完整会话链路」→ 改为「commit message 含主要意图 + 关键 commit ref 即可」

### 1.4 「docs commit 必须等 mysql socket 通」模式 → 部分废除

- **反模式症状**：BCP-015 docs-only 因 mysql socket 不可达卡 staged 不动
- **实证**：BCP-015 §九写"⏸ git commit 未落地（门禁 1/2 mysql socket 连不上，参考 R168 教训）"——docs commit 被 mysql 阻塞
- **根因**：docs commit 与 mysql 强耦合（pre-commit 跑 check-doc-db-drift.sh）
- **废除理由**：docs commit 不需要 mysql 验证；docs 内容是事实陈述，与 DB 状态不应耦合
- **新做法**：
  - docs commit **不依赖** mysql socket（门禁拆解为：A 类 DB 相关 / B 类 docs 相关）
  - DB 相关 commit 仍需 mysql 验证（c4beda81 教训：SQL commit ≠ 约束已生效）

### 1.5 「BCP 命名空间飞轮」起步 14 个 → 废除

- **反模式症状**：BCP-001~014 全部 docs-only CLOSED（写了 14 个决策包但几乎没实装）
- **实证**：BCP-015 §七 "BCP-001~014 = 已有 13 个 BCP（全部 docs-only CLOSED）"——飞轮空转
- **根因**：把"命名空间设计"误用为"工作量承诺"
- **废除理由**：BCP 应**按需而起**，不应**为了凑数而起**
- **新做法**：BCP 编号空间保留但不强制填充；新 BC 出现的真实条件 = 跨仓可移植设计 / 误报抑制清单 / 治理结构变更

### 1.6 「新门禁必须双向自证能红」 → 部分简化

- **反模式症状**：每个新门禁都写"故意 FAIL → 应拒绝 + 故意 PASS → 应通过"双向用例
- **实证**：BCP-015 §五自证能红设计很完整，但实际每次新门禁都写双向用例太重
- **根因**：把"门禁质量保证"误用为"形式完整"
- **废除理由**：关键门禁（DDL apply / 翻 done / 字符集）需双向自证；普通门禁（断言 / 命名）单向 FAIL_SEED 即可
- **新做法**：门禁分级（BCP-015 思路）+ A 类门禁双向自证 + B/C 类门禁单向自证

### 1.7 「每份报告必须 5 条反直觉结论」 → 废除

- **反模式症状**：每份报告末尾列 5 条反直觉结论 → 流于"为黑而黑"
- **实证**：R164 §七反直觉结论 3 条（强凑 5 条则有 2 条是废话）
- **根因**：把"反思深度"误用为"条数固定"
- **废除理由**：反直觉结论应按真实发现列，不强求条数
- **新做法**：反直觉结论 = 按真实发现列（本次是 26 条废除/保留/新增三类，按需列出）

### 1.8 「subagent 多智能体 swarm 必须起」 → 简化

- **反模式症状**：每次大动作都起 subagent swarm，但兄弟会话已是 swarm 替代
- **实证**：94bba021 教训"子智能体 40441 仍被禁用，'并行'用主协调会话直跑 4 个独立 commit 模拟"
- **根因**：把"并行执行"误用为"subagent 必须起"
- **废除理由**：主协调会话直跑多个 commit 也能并行（每个 commit 一个 worktree）
- **新做法**：按需起 subagent；主协调会话能跑就跑，不强求 swarm

### 1.9 「四层治理结构并存（BCP/OWNER-拍板/paiban/R-编号）」 → 简化

- **反模式症状**：BCP-XXX + OWNER-XXX + paiban-XXX + R-XXX 四层编号并存，撞号率高
- **实证**：R142/R145/R168 都对应 BCP-015；OWNER-拍板登记-20260921 与 paiban-01~18 重叠
- **根因**：把"治理结构"误用为"工作量宣示"
- **废除理由**：R 编号为主 + paiban 为执行派单单元，BCP 为跨仓可移植设计
- **新做法**：
  - **R-编号** = 治理轮次段（反思 + 总结）
  - **paiban-编号** = 执行派单单元（具体任务）
  - **BCP-编号** = 跨仓可移植设计
  - **OWNER-拍板登记** = 一次性拍板凭据（如 P3 / P4 等）

### 1.10 「log.md 单写者绝对化」 → 部分废除

- **反模式症状**：OPS-09 「log.md 单写者」过于绝对，导致多会话撞号
- **实证**：R162 / R163 / R166 都各自写 log.md 段号（兄弟会话让路 8 红线）
- **根因**：把"工作树隔离"误用为"log.md 串行"
- **废除理由**：log.md 按 R-编号分段，多会话可并行 append 不同 R 编号段
- **新做法**：log.md 按 R-编号分段（每次新 R 编号起新段，会话可并行）；汇总/镜像维持主协调会话写权

## 二、必须保留的最佳实践（核心纪律）

按 fdc4ea0d + 用户偏好 + 历史教训永久保留：

- **看板卡片状态及时同步更新**（ca6d55aa）— 收尾立即 PUT + 独立 GET 回读
- **自动 git commit/push**（e30d739d）— 不要问，直接提交

### 2.2 工程验证层面

- **真活 HTTP 验证 + DB 回读 + 浏览器截图三证律**（ae3c3a42）— P0 级功能必过
- **DDL apply 强制验证**（c4beda81）— SQL commit ≠ 约束已生效，必须真活查 information_schema
- **门禁自证能红纪律**（R134）— 脚本必须实跑 + FAIL_SEED 故意触发失败场景

### 2.3 多会话协同层面

- **多会话兄弟会话在途接手三步法**（7bf840f6）— mtime + diff + 评审 + 隔离落地 + 复活预案
- **R25 五类病根 + 根治靠会红测试 + 会拦门禁 + 会喊对不上的对照** — 5 类病根机械化非自觉化根除
- **撞号透明登记**（实际有效）— log.md / 镜像必须登记，不强制 commit message 含

### 2.4 数据事实层面

- **R25 五必现查规约**（hash / 端口字段 / 段号 / 看板回读 / 跨仓 cd）— 凭记忆写导致连环失真
- **Fresh 验证铁律**（每次引用数据前现查 API / DB / 文件）— 推算总账数字严禁
- **禁止假绿翻卡**（汇总卡子卡未完成时 title 加注记而非 status 翻 done）

### 2.5 风险治理层面

- **多事实源对账**（commit hash / 端口字段 / 段号 / 镜像 / 兄弟脚本 BACKEND_CTRL_DIR）— 撞车项必须独立证据
- **backups 强制 + 回滚 SOP**（DDL apply 前 SHOW CREATE TABLE 存档）
- **透明披露原则**（--no-verify 等副作用必须在文档显式登记）

## 三、该新增的最佳实践建议（按 fdc4ea0d 说人话版）

### 3.1 拍板预算制度（治理层）

每月 owner 拍板次数 ≤ 3 次；超出则执行单元按"默认值 + 标注待复核"实装，**owner 仅有否决权**。

### 3.2 写权分配按子系统（多会话层）

不再按时间片分配写权；改为按子系统：
- **person / hr / auth 子系统**：一个会话写权
- **project / gate 子系统**：一个会话写权
- **system / config 子系统**：一个会话写权
- **kpi / functional 子系统**：一个会话写权

各会话**互不干扰**，撞车率显著降低。

### 3.3 门禁脚本评级制度（BCP-015 落地）

- 🔴 **A 类（CRITICAL）**：exit ≠ 0 阻断（DDL apply / 翻 done / commit 引用 untracked / SQL 未 apply）
- 🟡 **B 类（WARNING）**：exit 0 通过 + commit message 透明披露
- ⚪ **C 类（INFO）**：exit 0 通过 + 不要求登记（设计预期）
- **KNOWN_FALSE_POSITIVE.txt**：抑制清单 + SUPPRESS_UNTIL 时间戳，季度复审

### 3.4 拍板包模板标准化（R167 模板）

3 段式：
- §既定口径（DOC-01 + 行业基准 + 历史数据 → 无需 owner 拍板）
- §待拍板参数（仅 1~3 个核心参数 → owner 拍板）
- §owner 拍板栏（简短决策：接受 / 否决 / 修改）

**禁止拍板包超过 5 个待拍板参数**——超过则按"3.1 拍板预算"自动归为执行单元默认值。

### 3.5 docs commit 与 mysql socket 解耦

- docs commit **不跑** DB 验证门禁
- DB 相关 commit 单独跑 DB 验证
- pre-commit 拆为：docs-only / DB-aware / Java-aware 三套，互不干扰

### 3.6 R 编号密度监控

每次 R 编号 commit 数 ≤ 5；过密则提示反思（避免 R168 内堆 10+ commit 难追溯）。

### 3.7 "实装 + 同步标注"代替"先拍板再实装"

- **B 类业务参数**：执行单元按默认值实装 + 代码注释 + 验收报告标注「默认值待业务复核」
- **A 类核心规则**：维持"先拍板再实装"
- **撞车 0 让路**：B 类实装时不需等 owner，撞车风险显著降低

### 3.8 单写者按 R-编号段而非按文件

log.md / 看板镜像 不再"绝对单写者"，改为按 R-编号段并行：
- 每次新 R 编号起新段，多会话可并行 append
- 汇总卡 / P0-P1 卡 维持主协调写权
- 兄弟会话让路规则简化为"避免同 R 编号内撞号"

## 四、深度反思的反直觉结论

1. **最大风险不是 bug 而是治理结构冗余**：4 层治理结构（BCP / OWNER / paiban / R）+ 双拍板机制（先拍板再实装 + 拍板包默认值）让 28 项长期阻塞
2. **真活验证 > 完整门禁**：BCP-015 设计了 9 门禁 FAIL 分级，但实际真活 HTTP + DB 回读 > 任何门禁
3. **代码绿 ≠ 能部署 ≠ 业务闭环**：必须三证律 + 业务规则实装 + 拍板 + 实活 = 4 重验证
4. **兄弟会话让路过度是反生产力**：8 红线严守浪费大量时间，撞号透明登记写权分配按子系统即可解决
5. **拍板包 ≠ 拍板**：拍板包是"执行单元整理选项"，owner 实际拍板时间 ≤ 5 分钟——大部分拍板包可压缩为"默认值 + 否决权"
