# SQL 升级脚本登记（2026-10-03，清单 A5）

## 0. 性质与边界（先读）

- **只做登记，不跑库。** 本文档编写过程中未连接任何数据库、未执行任何 SQL / DDL / DML。
  依据全部来自脚本文件头注释与正文的静态阅读（`head` / `grep`），以及 git 提交记录。
- **背景**：`docs/script/sql/update/` 现存约 140 个增量脚本，其中 **16 个文件命名不符合
  本目录主流约定 `YYYY-MM-DD-<slug>.sql`**，且全仓没有统一的「每脚本 apply 台账」
  （仓库无 Flyway/Liquibase，见 `.claude/skills/ipd-guard-ddl-apply/SKILL.md`）。
- **apply 状态口径**：本文标注的「已 apply / 无记录」指**脚本头部自述**。脚本头部的自述
  可能过时或失实（实例：`kb-partA-ddl-draft-20260928.sql` 头部含一段 2026-09-28 的
  「证据更正」，承认此前把 `check-ddl-applied.sh` EXIT=0 当对齐证据是无效引用）。
  真库核验的唯一手段是 `scripts/check-ddl-applied.sh`（entity↔真库列对齐检查），
  它验的是「最终形态对不对」，不是「哪个脚本跑过」。
- 命名规范出处：`.claude/skills/_templates/example/db-migration/references/ddl-apply-rules.md`
  （写 DDL 到 `docs/script/sql/update/<version>.sql`）；目录内事实主流格式为
  `2026-MM-DD-<kebab-slug>.sql`。

## 3. 风险说明

### 3-1 重复件：`receipt_ledger.sql` 与 `2026-09-06-ipd-receipt-ledger-table.sql`

两个文件都 `CREATE TABLE IF NOT EXISTS receipt_ledgers`，**列集完全一致**
（2026-10-03 实测：各 21 列，排序 diff 为空）。两者都建同一张表，先跑者生效、
后跑者静默跳过——不会炸，但属于应清理的重复登记。建议：保留合规命名的
`2026-09-06-ipd-receipt-ledger-table.sql`（且它头部业务注释更完整），把
`receipt_ledger.sql` 标注废弃或删除（域已退役，见下）。

### 3-2 退役域脚本（R216 拆除后的处置悬置）

commit `bf16d4f1`（2026-10-03，R216）已按 owner 指令**拆除回款台账 / 奖金池 /
业绩窗口三域的代码侧**，**数据库表保留不删**。受影响的本清单脚本：

- `receipt_ledger.sql` 与 `2026-09-06-ipd-receipt-ledger-table.sql`（receipt_ledgers）
- `batch_missing_tables.sql`（bonus_allocations 等）

新库是否还要 apply 这两个脚本，取决于退役域的表是否要随基线建立（当前 owner 口径
是「表保留不动」，schema 快照见 `docs/ipd-系统说明/schema-baseline-20261003.sql`，
166 张表含这些表）——**待 owner 拍板，本文不替拍**。历史种子行的清理脚本
`2026-10-03-ipd-retire-lc01-lc03-draft.sql` 头部明标 **DO NOT APPLY**，未 apply，
禁止执行。

### 3-3 无统一 apply 台账的系统性风险

- 「已 apply」的唯一载体是散落的脚本头自述（5 处）与
  `docs/ipd-系统说明/验收/ddl-apply-check-*.json` 快照（按日期、按 entity 维度，
  非按脚本维度）。**没有任何机制回答「某文件在哪个库跑过、何时、谁跑的」**。
- 后果一：`CREATE TABLE IF NOT EXISTS` / `INSERT IGNORE` 类幂等写法掩盖「其实从没跑过」——
  10 个无记录脚本里若有列级 ALTER（MySQL 8 不支持 ADD COLUMN IF NOT EXISTS，仓内用
  information_schema 守卫 + PREPARE 补），漏跑只会在运行时以 `Unknown column` 500 暴露。
- 后果二：重命名（§1 建议名）本身零库风险（无 Flyway 按文件名跟踪），但**改名后头部
  自述的 apply 记录是唯一线索**，重命名提交须逐文件 `git mv` 保留历史可溯。
- 建议的收口动作（待 owner 拍板，不在本轮执行）：建一份
  `docs/script/sql/update/APPLY-LEDGER.md`，逐脚本登记「目标库 / 日期 / 执行人 /
  回验方式」，与 `check-ddl-applied.sh` 的最终形态校验互补。

本文全部「用途」来自脚本头部注释的转述，未逐句核验注释与正文 SQL 的一致性
（除 §3-1 的列集比对是正文实测外）。「建议规范名」只做格式归位，不改任何脚本内容。
