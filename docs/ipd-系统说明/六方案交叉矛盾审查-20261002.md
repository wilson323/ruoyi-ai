### C-1【致命】冒号复合串能否进官方层：4 种互斥模型

**矛盾点 A（说「可以直喂」）**
`AgentScope归位-compaction-20261002.md:436`（§6 遵守声明 1）：
> 「compaction 归位**全程不新增任何隔离键拼接**。官方 compaction 的 `agentId`/`sessionId` 均取自 `RuntimeContext`，而本项目 `KernelScopeKey.Scope.toRuntimeContext()` 已是四维收口后的产物——**官方直接消费即可，无需自建**。」

**矛盾点 B（说「绝对禁止」）**
`AgentScope归位-sandbox-workspace-20261002.md:678`（**红线 RL3**）：
> 「❌ **禁止**让官方层看到含 `:` 的复合身份串」
配套 `sandbox:470-478`（§4.2 层一）要求在 `KernelScopeKey` 新增 `opaqueScopeValue()`——SHA-256 前 32 hex 的**无分隔符摘要**专供官方层。

**矛盾点 C（说「不需要改格式，直喂 slotId」）**
`AgentScope归位-subagent-team-20261002.md:484`（§5.4 修正后结论）：
> 「做法统一为：**所有官方 key 接口一律喂 `scope.slotId()`**（= `p{projectId}:u{userId}:a{agentId}:s{sessionId}`，含全部四维），**禁止喂 `scope.sessionId()` 或裸 `sessionId`**。」
并在 `:625`（R2）把原「高」风险降级，理由是「官方 key 为不透明串」。

**矛盾点 D（说「加第四个视图」）**
`AgentScope归位-transcript-plan-skill-memory-20261002.md:349-351`（§5.3 约束 3）：
> 「`Scope` 需提供两个视图：`scope.toRuntimeContext()`（现有，带复合 `:`）… `scope.toFilesystemRuntimeContext()`（**新增**，`:` → `_`，供 transcript / memory / skill 的文件系统通道）」

**哪个是对的：四份都只对一半，正确的答案是「按官方接口类型分层」。**

【实证】官方对复合串的态度**不是一种，是四种**（本审查者实读）：

| 官方接口 | 遇到 `:` 怎么办 | 证据 | 能否直喂 `slotId()` |
|---|---|---|---|
| `WorkspaceMessageBus.queuePush` | **自行清洗**：`hashKey` = `key.replaceAll("[^a-zA-Z0-9._-]","_") + "_" + hash` | `bus/WorkspaceMessageBus.java:237-240` | ✅ 可以（冒号被替换成 `_`，四维信息不丢） |
| `ToolResultEvictionMiddleware.buildEvictionPath` | **自行清洗**：`agentName.replaceAll("[^a-zA-Z0-9_-]","_")` | `memory/.../ToolResultEvictionMiddleware.java:266-274` | ✅ 可以 |
| `TranscriptRef.prefix()` → `FilesystemTranscriptStore` | **不清洗**：`root.resolve(tenant).resolve(agentId).resolve(sessionId)` | `transcript/TranscriptRef.java:37-40`；`FilesystemTranscriptStore.java:165-168` | ❌ 不行（`agentId` 取 `getAgentId()`、`sessionId` 取 `rc.getSessionId()`，后者是复合含冒号串） |
| `WorkspaceManager.resolveRuntimeDataPath` | **不清洗**：`workspace.resolve(String.join("/", ns)).resolve(relativePath)` | `workspace/WorkspaceManager.java:239-249` | ❌ 不行 |

补充实证：官方 `NamespaceFactory` 在 `IsolationScope.USER` / `SESSION` 档都把 `rc.getUserId()` / `getSessionId()` **原样**塞进命名空间列表（`IsolationScope.java:102-126`），**不做任何字符处理**。

**附带发现（6 份都没提，但影响 C-1 的裁决）**：官方那两处 `replaceAll` 清洗**保留 `.`**，即 `..` 会原样穿过。而项目 `KernelScopeKey.validateSegment`（实读 `KernelScopeKey.java:66-81`）**只拒 `:` 与 `..`、不拒 `/` `\`**。也就是说：项目侧的 `..` 防护在官方清洗层之上是唯一屏障，若官方侧 key 的来源绕过 `KernelScopeKey`（例如 `HarnessAgent.name`、模型生成的 `toolCallId`），官方清洗**不构成穿越防护**。

**如果两份都执行会发生什么**：
- sandbox 的 **C9 门禁**（`sandbox:516`）要求「所有 `sandbox`/`workspace` 包的业务侧引用点必须落在 `KernelScopeIdentity` 一个文件内」；
- subagent 的 **门禁第 2b 条**（`subagent:408`）要求 `inboxPush|inboxDrain|acquire` 必须匹配 `slotId\(\)|busKey\(\)`。

这两条规则**互斥**：若 sandbox 层一落地（官方层拿摘要值），subagent 的 2b 条会因「未出现 `slotId()`」而红；若 subagent 落地（官方层拿 `slotId()`），sandbox 的 C10 会因「未显式传 `KernelScopeIdentity`」而红。**门禁互锁，任何一份先落地都会把另一份锁死。**

### C-5【致命】`FrozenProjectAgentSkills` 挂载点：两份相反

**矛盾点 A**：`blocks:586-602`（R11）+ `blocks:794-806`（T4）：
> 「`FrozenProjectAgentSkills` 实现的 9 个 `AgentSkillRepository` 方法…**在运行时永远不会被 SDK 调用**，只有 `onSystemPrompt` 是活的。」
> 「**动作**：在 A2 的 builder 上**加 `.skillRepository(selectedSkills)`**。sha256 冻结校验逻辑一个字都不动（它已经是对的），**只换挂载点**。」
—— 即：**保留 `onSystemPrompt`、保留 `.middleware(selectedSkills)`、额外加 `.skillRepository(...)`**。

**矛盾点 B**：`transplan:235-244`（§3.3 步骤 1~2）：
> 「把 `onSystemPrompt`（L64-67）**删除**，不再自己拼 prompt。」
> 「把 `.middleware(selectedSkills)` 改为 `.middleware(HarnessSkillMiddleware.frozen(List.of(selectedSkills), toolkit, SkillFilter.only(names), null, null, ShellPathPolicy.noShell()))`」
—— 即：**删掉 `onSystemPrompt`、把 middleware 换成官方 `frozen()`、不加 `skillRepository`**。

**哪个是对的：两者的目标不同，可以叠加，但执行顺序会撞。**
- blocks 的 T4 修的是**挂载点 bug**（9 个方法死代码），transplan 的步骤 1 修的是**渲染层归位**。
- 若 transplan 先做：blocks T4 的验证第 1 条「`agent.getSkillRepositories()` 返回非空且 `getAllSkillNames()` 命中选集」**仍能过**（`.skillRepository()` 生效）；但 blocks T4 的前提「middleware 保留」失效，且 T4 的动作文本「只换挂载点」会导致 reviewer 认为 transplan 改错了。
