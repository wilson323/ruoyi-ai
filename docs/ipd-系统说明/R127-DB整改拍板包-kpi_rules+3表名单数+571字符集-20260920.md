### 三.3 571 字符集不一致整改方案（病根 #3）

#### 方案 A：全库一次性 in-place `ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`

**做法**：

```sql
-- SRE apply（66 张表，1 个 ALTER 1 张表，按表顺序循环）
ALTER TABLE kpi_records CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
ALTER TABLE kpi_rule_snapshots CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
ALTER TABLE kpi_shared_confirms CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- ... 63 张表
```

**优点**：
- 一次性 = 26 张表 × ~5 sec = ~5 min 完成（假设每张表 <1 万行）
- 撞车 0 红线下只需要 1 个 SRE apply 窗口

**风险**：
- **`ALTER TABLE` 在大表上会长时间锁表**（如 `chat_message` 表如 >10 万行 = 可能锁 1-10 min）
- MySQL 8.0 `ALGORITHM=INPLACE, LOCK=NONE` 可大幅减小锁，但 `CONVERT TO CHARACTER SET` 实际是 `ALGORITHM=COPY`（重建表 = 锁表）
- 66 张表真活跑，可能有 1-2 张大表锁表时间超预期（撞车 0 红线下 SRE 拒绝 apply 的概率高）
- chain_root 不受影响（已 §1.3 说明）

**工作量**：6 hr（DDL 脚本生成 1 hr + SRE 排期 4 hr + 回归验证 1 hr）

**做法**（业务域分 4 批）：
- **第 1 批（IPD 核心域）**：kpi_* (3) + requirement_pools/receipt_ledgers/switching_acceptances (3) + projects/sops/project_stages 等 14 张 = **20 张**
