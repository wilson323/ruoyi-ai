## 0. 结论先行（5 条）

**C-1｜主推荐：Temporal（自托管）作为 IPD 端到端编排骨架；Flowable 7 为强备选，两者差距在加权分 4.3 vs 4.2（§5），以「能否接受新增一个 Server 运维面」为决策分叉点。** Temporal 的 Activity 原语（自动重试 + 超时 + 心跳断点 + 幂等建议）与 ZK-IPD 节点协议 ACT-N01–N07、超时协议 T05–TO、补偿协议 C0–C5 是**同构映射**（§4.1），「可降级可重试」三个维度（AI 节点产出/长周期断点恢复/失败降级不污染下游）一档领先；代价是无 BPMN 可视化建模器、Workflow 确定性约束学习曲线、独立 Temporal Service 运维。来源：docs.temporal.io/workflows.md、/activities.md、/encyclopedia/workflow-message-passing.md、/self-hosted-guide/deployment.md（2026-09-27 检索）+ ZK-IPD《IPD业务工作流与完整动作目录.md》L54-70、《AI开发交付工作流与节点.md》L42-62。

**C-2｜Camunda 7 直接排除（生命周期已终结），Camunda 8 排除主路线（生产许可付费墙）。** Camunda 7 Community 最后版本 7.24 定于 2025-10-14 发布、仓库随后归档、之后无任何安全补丁（camunda.com/blog/2025/02/camunda-7-enterprise-end-of-life-extension/ 一手）；Camunda 8.6 起 Self-Managed **生产环境必须购买生产许可**，Zeebe/Operate/Tasklist 等核心组件源码为 Camunda License 1.0（非 OSI），仅 Java Client / Spring Boot Starter / Exporter API / Protocol 等周边为 Apache 2.0（camunda.com/blog/2024/10/camunda-licensing-what-you-need-to-know/ + github.com/camunda/camunda README License 节，均 2026-09-27 直读）。二者与「许可证干净 + 私有化交付」相抵。

**C-3｜n8n / Dify 判定为「外挂系统」，不符合本次方向性红线，仅可作 AI 节点能力的旁路实验，不作主引擎。** n8n 为 Sustainable Use License 1.0（仅限自用内部业务，不得商用分发，非 OSI 开源，raw LICENSE.md 直读）；Dify 为「修改版 Apache 2.0」（多租户运营需书面授权、前端 LOGO/版权不可移除，raw LICENSE 直读）。二者均自带独立数据库与执行存储，与 Java Spring 业务表的深度集成只能走 HTTP/API（推断自其节点模型），IPD「数据密集对账 + 不可变台账」要求数据留在业务库事务边界内——外挂双轨 + 数据出事务域，违反「防双轨」纪律。

**C-4｜Warm-Flow 与 ruoyi-aiflow 的天花板经仓内实证，均不足以承载 IPD 全生命周期编排，但两者都有明确的保留定位。** Warm-Flow（1.8.2，Apache 2.0，7 张表）审批原语齐全（票签/委派/加减签/互斥/并行/自动审批/任意跳转，dromara/warm-flow README 直读）但定位是「快速审批场景」，README 未见定时器/超时调度/补偿 Saga 能力（[未核验项]，§7）；ruoyi-aiflow（langgraph4j 1.8.20）检查点为 `MemorySaver` 内存态（WorkflowEngine.java L109 现查），进程重启即失断点，且「并行节点中不能包含条件分支」是其表达力硬上限（同文件 L140-141）、DALLE3/FAQ_EXTRACTOR 死枚举与 GBK 乱码修复史（docs/wiki/wiki/modules/workflow.md L111-157）自证维护面风险。→ Warm-Flow 保留为存量简单审批，ruoyi-aiflow 限定为短周期 AI 管道，**均不扩容承载 90 日级生命周期**。

**C-5｜防双轨红线：无论选谁，`ruoyi-ipd` 已有的签署领域逻辑（双签盲签/五签链/仲裁/终裁/超时弃权/3 次延期）必须作为「节点执行层」保留复用，禁止在新骨架里重写第二套签署语义。** `GateReviewService`（1028 行，sign/view/reopen/scanTimeout/scanRemind/arbitrate/finalRuling/extendDeadline 等 11 个关键方法，行号见《工作流系统性梳理-20260927.md》§2.2.1）已实现 W12「盲签或顺序五签合同」（ZK-IPD 目录 L476）的领域规则；新引擎的职责是**编排这些领域服务 + 承载 AI 节点产出**，不是替代它们。这是「不造轮子 + 防双轨」的合并解。

## 3. 候选引擎逐项调研（一手来源）

### 3.1 Flowable BPMN（Apache 2.0，嵌入式）✅ 强备选
- 许可与版本：Apache 2.0；Flowable V7 要求 JDK 17+，V6 分支仍维护 Java 8+（github.com/flowable/flowable-engine README 直读，2026-09-27）[事实]。→ 与仓内 Java 17 / Spring Boot 3.5.8（根 pom.xml L17/L20）兼容 [事实+推断]。
- 表达力（flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs 直读）[事实]：
  - Multi-instance（for each）：顺序/并行重复执行活动或子流程，`completionCondition` 表达式可在任一实例结束时提前销毁剩余实例；多实例子流程可挂边界事件（中断型边界事件触发时销毁全部活跃实例）→ **并行扇出 + 全局短路降级原生**（R5/R8）。
  - Timer Boundary Event、terminate end event、事件子流程/事务子流程语义齐备 → **超时路径/失败支路原生**（R2/R6）。
  - 人任务/系统任务编排是其定位（README：「the ideal engine for orchestrating human or system activities」）[事实]。
- 长周期 [估算]：流程实例与定时器持久化于引擎表（ACT_ 前缀），重启不丢；90–180 日级实例在 BPMN 引擎是常规形态（无官方数字，标注为估算）。精确表数量未核验（Warm-Flow README 称「约 40 张」属二手，不承重）。
- 集成成本 [推断]：`flowable-spring-boot-starter` 嵌入现有 JVM，与业务表同库同事务（对账数据不出事务域，R8 友好）；无独立 Server。AI 节点 = ServiceTask（JavaDelegate/外部任务模式），长时 LLM 调用需异步作业 + 消息回填建模，胶水代码中等。
- 反对理由：AI 执行者的重试/心跳/断点语义不如 Temporal 一等公民（需自行组合 async job + 边界事件）；BPMN XML 的 69 动作 × ACT-N07 展开会生成庞大流程图（可用子流程/调用活动分层缓解）；「盲签」需在 UserTask 上自定义。

### 3.2 Camunda 7 ❌ 排除
- [事实] Camunda 7 Community 版 EOL：最终功能版本 7.24 于 2025-10-14 发布，仓库随后归档、issue 转私有，此后 CE 无任何发布与安全补丁（camunda.com/blog/2025/02/camunda-7-enterprise-end-of-life-extension/「Camunda 7 Community End of Life」节，含 2025-07 更新，2026-09-27 直读）。
- [事实] 企业版 LTS 7.24 维护至 2030-04-09（付费订阅），延期支持至 2032-04。
- [推断] 新建系统选一个 CE 已死、仅付费续命的引擎 = 引入即背上迁移义务，直接违反「不造轮子也不背死轮子」。表达力（BPMN 2.0 全家桶）本身不差，但生命周期一票否决。

### 3.3 Camunda 8（Zeebe）❌ 排除主路线（能力最强档之一，许可是硬伤）
- [事实] 许可：2024-10-08 官方博客《Camunda Licensing: What You Need to Know》明示「Camunda 8.6 introduces a new unified licensing model… Self-Managed now requires a production license for use in production environments」，Zeebe/Operate/Tasklist/Optimize/Identity 均「License needed for production use. Free for development only」。
- [事实] 组件许可（github.com/camunda/camunda README License 节直读）：Zeebe/Operate/Tasklist 源码为 **Camunda License Version 1.0**（非 OSI）；仅 Java Client、camunda-spring-boot-starter、Exporter API、Protocol、gateway-protocol-impl、bpmn-model 为 Apache 2.0。
- [事实] 架构：Zeebe 云原生引擎（Raft 分区复制、gRPC/REST Gateway、外部 Worker 执行业务代码、无需关系型数据库）（README「Using Camunda 8」节）。
- [推断] 能力面：Job Worker 天然是「节点执行者」抽象（对维度 (a) 最贴合的另一候选）；多实例/网关/定时器覆盖 R2-R8。但生产部署 = Zeebe 集群 + （Tasklist/Operate 付费或自研替代）+ 可见性存储，运维与采购双重重量（维度 e 直接爆表）。若未来 owner 预算接受商业许可，可复评。

### 3.4 Temporal ✅ 主推荐（表达力最优档）
- 许可 [事实]：Temporal Server 仓库 MIT License（raw.githubusercontent.com/temporalio/temporal/main/LICENSE 直读，© 2025 Temporal Technologies / © 2020 Uber）。Java SDK 同为 MIT（sdk-java 仓，本次未单列直读，标注）。
- 长周期与断点恢复 [事实，docs.temporal.io/workflows.md 直读原文]：「Temporal Workflows are resilient. They can run—and keep running—for years, even if the underlying infrastructure fails. If the application itself crashes, Temporal will automatically recreate its pre-failure state」；恢复机制是 Event History 逐步重放（replay）而非快照还原，「the source of truth for everything that happens in the Workflow」。→ **R3（90 日/6 月级实例）与断点恢复是一等公民**。
- Activity=节点执行者 [事实，/activities.md 直读]：「If an Activity attempt fails, it is automatically retried using its Retry Policy」；「Each attempt starts from the initial state, unless your code uses a Heartbeat detail payload for checkpointing. The last recorded Heartbeat details are made available to the Activity function on the next attempt, so your code can continue processing where it left off」；官方建议 Activity 幂等。→ 与 ACT-N03「最多 2 次有依据重试」、C3「先查回再续跑」、T 分级超时**一一对应**（映射表 §4.1）。
- 人工在环 [事实，/encyclopedia/workflow-message-passing.md 直读]：三种消息原语——Query（只读不阻塞）、Signal（异步写，fire-and-forget）、Update（同步可跟踪写，可校验后受理）。→ 盲签/五签链以 Signal/Update + 既有 ruoyi-ipd 签署域建模（领域层不重写，C-5）。
- 确定性约束 [事实，workflows.md 直读]：Workflow 代码重放时「has to make the same decisions when given the same history」，时间/随机数/IO 必须走 replay-safe API 或放入 Activity。→ 学习曲线与代码纪律成本，团队需培训。
- Java/Spring Boot 集成 [事实，/develop/java/spring-boot-integration 直读]：`io.temporal:temporal-spring-boot-starter`（文档示例 1.31.0），「currently supports Spring Boot 2.x, 3.x, and 4.x」；自动装配 WorkflowClient、Worker 显式/自动发现、测试用内存 Test Server（`spring.temporal.test-server.enabled`）。→ 与仓内 Spring Boot 3.5.8 对齐，**客户端集成成本低**。
- Server 运维 [事实，/self-hosted-guide/deployment.md 直读]：生产自托管 = 独立 Temporal Service（Docker Compose 示例含 PostgreSQL + Elasticsearch + gRPC 7233 + Web UI；或 Go 二进制 + systemd；或 Helm on K8s），schema 升级需 `temporalio/admin-tools` 手工管理；官方警告 Temporal 主机不得暴露公网、须按数据库级防护。开发期可用 `temporal server start-dev` 单二进制零依赖。→ **维度 (e) 最大负项落地为「一个新运维面」**（持久化 DB + 可见性存储 + 升级流程）。
- 反对理由（如实登记）：① 独立 Server 组件进私有化交付包，客户环境部署变重；② 无 BPMN 可视化建模器，W01–W26 流程图需以代码+自绘图维护（业务人员改流程不能拖拽）；③ 确定性约束 + 事件历史增长需 Continue-As-New 等工程纪律；④ 人工任务 UI 无现成 Tasklist（但仓内 ruoyi-ipd 前端已有 95 个 API 适配文件与 Gate 面板，此项实际成本被抵消 [推断]）。

### 3.5 n8n ❌ 排除主引擎（外挂系统 + 许可限制）
- [事实] 许可：Sustainable Use License v1.0（raw LICENSE.md 直读）——「You may use or modify the software only for your own business purposes or for non-commercial or personal use」；不得免费分发以外的分发；`.ee.` 文件需商业许可。非 OSI 开源。
- [事实] 长等待：Wait 节点「pause your workflow's execution… offloads the execution data to the database. When the resume condition is met, the workflow reloads the data」（docs.n8n.io Wait 节点直读）；恢复条件=时间间隔/指定时刻/Webhook 回调/表单提交，resumeUrl 每次执行唯一。
- [推断] 与 Java 业务表集成只能 HTTP/Code 节点间接访问，执行数据存在 n8n 自己的库里 → 双系统双状态（违反防双轨）；审批只有 Form/Webhook 弱形态，五签盲签链需大量自定义节点。判定：外挂自动化工具，不符合「智能体嵌入工作流内部承担节点产出」的形态要求。

### 3.6 Dify ❌ 排除主引擎（AI 编排强，但属外挂 + 许可附加条件）
- [事实] 许可：「modified version of the Apache License 2.0, with the following additional conditions」（raw LICENSE 直读）——① 多租户服务运营需 Dify 书面授权（一租户=一 workspace）；② 前端 LOGO/版权信息不可移除或修改。
- [事实] 工作流节点（docs.dify.ai 自部署索引 2026-09-27 直读）：LLM / Knowledge Retrieval / Agent / Question Classifier / If-Else / Iteration / Loop / Code / Template / Variable Aggregator / Document Extractor / Variable Assigner / Parameter Extractor / Answer / Output 等 15 页节点文档；Start 节点可选 User Input 或 Trigger（Schedule/Integration/Webhook）。
- [事实（缺席）] 节点清单中**无审批/会签/签署类节点** → [推断] 五签盲签链、Gate 否决短路必须在 Dify 外自建。
- [推断] 数据面：工作流实例与变量存 Dify 自身库，与业务表对账需 API 往返；发布形态为「web app / MCP server / 后端服务 API / 工具」（Start 节点页直读）——本质是**旁挂的 AI 应用平台**。IPD 数据密集对账 + 不可变台账场景下数据出事务域，不符合红线。

### 3.7 Warm-Flow / ruoyi-aiflow / ruoyi-ipd（仓内三套）
见 §2 一手证据汇总。定位裁决 [推断]：Warm-Flow=存量简单审批（不扩容）；ruoyi-aiflow=短周期 AI 管道（不承载 R3）；ruoyi-ipd 签署域=任何新骨架下的节点执行层（C-5）。

## 4. IPD 硬需求 × 引擎原语映射（核心增量）

### 4.1 ACT-N / T / C 协议 ↔ Temporal 原语（[推断] 映射设计；左列事实来自 ZK-IPD 目录/ENG 附录，右列事实来自 docs.temporal.io）

| ZK-IPD 协议（事实） | Temporal 原语（事实） | 映射说明（推断） |
|---|---|---|
| ACT-N03「技术调用失败最多 2 次有依据重试」 | Activity RetryPolicy（`maximumAttempts`） | 每个 ACT-N 节点=1 个 Activity（或子流程），重试次数/间隔按节点表配置 |
| T05/T15/T30/T60 分级超时 | Activity `startToCloseTimeout` / `scheduleToCloseTimeout` | 超时分级=不同 Activity 的 timeout 配置 |
| C3「稳定业务操作键查回，效果未知进 RECONCILE_REQUIRED」 | Heartbeat detail 断点 + 幂等 Activity | 心跳 detail 携带业务操作键，重试时先查回再续跑 |
| 并行调研/对账扇出 | Workflow 内并行 Activity（Java Future/Promise 组合） | 扇出收集后汇总对账；单支失败按 C0 标记不阻断他支 |
| ACT-N06 真人采纳 / W12 盲签五签 | Signal/Update + ruoyi-ipd `GateReviewService` | Update（同步校验受理）承载签署动作；签署规则复用既有领域服务 |
| R3 月度/+90 日/+6 月、待定起算日 | Timer / Schedules | L08 冻结后启动 Timer（条件计时在业务层触发） |
| R7 修复环路 ≤2 轮 | Workflow 代码内计数循环 | 普通代码控制流，无需额外机制 |
| 长历史膨胀 | Continue-As-New | 月度节点续接新执行，保持历史长度可控 |

### 推荐与反对理由（供 owner 拍板）

**推荐：Temporal（自托管）为 IPD 端到端编排骨架。**
- 支持理由：① ACT-N/T/C 协议与 Activity 原语同构，R1/R2/R5/R6/R7/R8 的「可降级可重试」几乎零自研（不造轮子收益最大）；② 「AI 作为节点执行者」的形态被引擎原生定义（Activity=有重试/超时/心跳/幂等约束的工作产出单元），正是方向性说明第二条要求的「真正承担节点工作产出」；③ 90 日/6 月级实例 + 崩溃恢复是官方一等能力；④ MIT 许可、`temporal-spring-boot-starter` 对 Spring Boot 3.x 原生支持，客户端集成成本低；⑤ 人工签署不重写（复用 ruoyi-ipd 签署域，C-5），前端任务 UI 仓内已有。
- 反对理由（必须接受其一才走此路线）：① 私有化交付新增 Temporal Service（DB + 可见性存储 + admin-tools 升级流程）运维面；② 无 BPMN 拖拽建模，流程变更走代码；③ Workflow 确定性约束需要团队培训与 review 纪律；④ 事件历史增长需 Continue-As-New 治理。

**备选切换条件（决策分叉）**：若 owner 裁定「私有化部署重量 + 业务人员拖拽改流程」权重高于「长 AI 任务断点恢复 + 降级自动化」→ 切换为 **Flowable 7 嵌入式**（同 JVM 同库、Apache 2.0、会签原生；AI 节点用外部任务/消息回填模式实现，接受中等胶水代码）。两者禁止并用（防双轨）。

**其余候选反对理由**：Camunda 7=CE 已死（2025-10-14 后无安全补丁）；Camunda 8=生产许可付费墙 + Zeebe 集群重量，三年 TCO 与采购流程不可控；n8n=SUL 非开源许可 + 外挂双系统；Dify=多租户限制 + 无签署节点 + 数据出事务域；Warm-Flow 扩容=README 自述定位为快速审批，定时/补偿/长周期能力未见（[未核验] 细化文档后仍缺则坐实）；ruoyi-aiflow 承载长周期=MemorySaver 实证不满足断点恢复。
