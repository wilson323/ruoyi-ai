## 2. 根因判断

### 假设 ①：三处对 BCP-014 的描述文字确实不一致（150 行差）
- **证据强**：抽样的三个原文上下文长度、维度、行数都不同
- **结论**：✅ 成立（事实层面）

### 假设 ②：hash 算法对空格/换行敏感
- **证据弱**：bcrypt / sha256sum 本身对格式不敏感，是 hash 函数标准语义
- **结论**：❌ 不成立

### 假设 ③：BCP-014 编号/主题在三源里命名漂移
- **证据弱**：三处 BCP-014 都指"最佳实践系统性梳理"，主题一致
- **结论**：❌ 不成立（编号/主题一致，描述详略不同）

### 假设 ④（核心）：脚本要求三源 hash 一致是 SSOT 病
- **证据强**：SSOT = Single Source of Truth = 一个事实一个源
- 三源是**三个独立维度的源**（反思 / 登记 / 闭环），不是同一个源的三份拷贝
- 要求 hash 一致 = 强行要求三个独立维度对齐 = 把多维信息压成单一文本 = 信息丢失
- **结论**：✅ 成立。脚本设计违背 SSOT 原则

## 3. 根因结论

**脚本设计违背 SSOT 原则**：把"反思源 / 登记源 / 闭环源"三个独立维度的描述强行要求哈希一致。

正确的三源对账应该是：
- ✅ **主题编号一致**（BCP-014 在三源都叫 BCP-014，主题都叫"最佳实践系统性梳理"）
- ✅ **状态机一致**（三源都登记 ✅ CLOSED，日期一致）
- ⚠️ **描述详略不同 = 健康**（不同维度自然写不同详略）
- 🔴 **主题编号漂移 / 状态机不一致 = 真异常**

当前 BCP-014 属于 ✅ 主题一致 + ✅ 状态一致 + ⚠️ 详略不同 = **健康**，不是异常。
