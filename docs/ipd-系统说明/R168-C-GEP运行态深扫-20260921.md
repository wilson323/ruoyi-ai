### 1.4 GEP 设计意图还原（grep log.md / BCP-Registry）

GEP = **G**oal-**E**volve-**P**rotocol（或类似），是 `.harness/` 下的自进化框架。

**预期工作流**（基于注释推断）：
1. loop.sh 跑 verify/gate
2. 失败时自动 append 到 failures.jsonl
3. 人类审查每个失败，7 天内归档到 incident.md 或结案
4. gate-7 (fail-blank) 检查：空 → PASS，非空 → FAIL

**关键反向逻辑**：
- failures.jsonl **空** = 当前没有失败 = GEP 健康（无失败记录）
- failures.jsonl **非空** = 当前有失败待处理 = GEP 异常（需要人工审查）

## 2. 根因判断

### 假设 ①：GEP 是设计但未实装（仅有 doc，无运转）
- **证据弱**：loop.sh / gate.sh / audit/ / evals/ 都存在 = 设计实装了
- **结论**：❌ 不成立（GEP 设计已实装）

### 假设 ②：脚本检测路径错
- **证据中**：failures.jsonl 在 `.harness/evolve/` 路径，脚本也检测这个路径，路径一致
- **结论**：❌ 不成立（路径对）

### 假设 ③：GEP 在别的子目录跑，脚本扫错文件
- **证据弱**：loop.sh 注释明确写"在 verify/gate 失败时自动 append 到 failures.jsonl"
- **结论**：❌ 不成立（设计是单文件）

### 假设 ④（核心）：loop.sh 在本机跑过的所有 verify/gate 都 PASS 了 = 0 失败 = 健康状态
- **证据强**：failures.jsonl 空 + loop.sh 设计是"失败才 append"
- **结论**：✅ 成立。0 数据行 = GEP 健康（当前没失败），不是"未运行"

### 假设 ⑤（备选）：loop.sh 跑了但失败记录被清空了 / rotated 了
- **证据中**：没有 rotated 文件，文件本身有注释头 = 设计初始态
- **结论**：⚠️ 部分成立但缺乏直接证据

## 3. 根因结论

**脚本语义反转错误**：failures.jsonl 空的语义被脚本解读为"GEP 未运行"，实际语义是"GEP 当前健康（无失败待处理）"。

正确的健康判定应该是：
- ✅ 0 数据行 + loop.sh 最近 7 天有运行记录 = **健康**
- ⚠️ 0 数据行 + loop.sh 最近 7 天无运行记录 = **可能未运行**
- 🔴 非空数据行 = **有失败待处理 = 真异常**

当前状态属于 ✅（如果 loop.sh 真在跑）或 ⚠️（如果 loop.sh 长期没跑）。
