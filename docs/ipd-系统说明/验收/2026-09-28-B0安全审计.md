### 2.3 问题 2：判据与 §8 裁决的一致性

**（a）现状无倒挂。** share 存量 100%=0（探针），B0 判据实效 = 仅 owner 可检索（fail-closed 收窄），方向与 §8.1 "share 从未构成安全边界、真正隔离是 tenant 拦截器 + Sa-Token" 的论断一致。租户维度核验：`ruoyi-admin/src/main/resources/application.yml` 键 `tenant.excludes`（299 行起）不含 knowledge_info/agent_info/chat_*——**tenant 拦截器对 knowledge_info 仍追加 WHERE tenant_id=?**，跨租户 kid 在 `queryById` 层即返回 null → Gate 判"库不存在"拒绝。底层租户隔离未因 B0 弱化。

**（b）未来 share 派生镜像落地后（PUBLIC 翻 1 → Gate 全租户放行）是否与 IPD 上限权威冲突？——不冲突。** §8.1 规则 2 明文："「租户内公开」语义由 sensitivity=PUBLIC + tenant 拦截器共同表达"——PUBLIC 库对租户内全量可检本就是目标模型行为，Gate 放行 = 忠实执行该语义，且 tenant 拦截器继续划租户边界。§8.2 的上限模型（effective = javaDefault ∪ dbGrant − dbRevoke、SECRET/INTERNAL 分层）管的是 **sensitivity 分层读权限上限**，属 B2 检索接线范畴，B0 尚未消费该维度，谈不上绕过。

**（c）chat 侧本地判 share/owned、未走 IpdStpInterfaceBridge——是否「自立第二套上限」违例？——判定：不构成违例，属登记在案的过渡豁免。** 依据：① §8.3 B0 处置栏明文授权本切片收敛 S1/S2/S3；② Gate 是**准入闸门**（fail-closed 收窄"谁能检"）而非**权限上限模型**（不判 sensitivity/不定义 SECRET 层级），与 §8.2 所禁的"第二套上限"（框架侧自建 effective 权限集）不是同一物；③ 替换路径已闭环：`IpdStpInterfaceBridge` 已存在于 `ruoyi-modules/ruoyi-ipd/.../security/IpdStpInterfaceBridge.java`，Gate 实现类 javadoc 明示 ipd 模块以更高优先级 Bean 覆盖（依赖方向 ruoyi-ipd → ruoyi-chat 单向，无反向读 persons 的双轨风险）。

**（d）但豁免的成立前提存在实质威胁（本审计核心证伪点）：share 翻转是 Gate 的钥匙，而翻转入口无 ownership 校验。** §8.1 规则 1 规定升密（SECRET）只能人审显式改；规则 3 规定 share 由后端写 sensitivity 时同步派生。而现状 `KnowledgeInfoController.edit`（PUT /system/info，@SaCheckPermission("system:info:edit")）→ `KnowledgeInfoServiceImpl.updateByBo` 全程无 ownership 校验——**任何持 system:info:edit 者可直接 UPDATE 任意库 share=1**，Gate 的 share 半边即刻对该库放行全租户，全程不经 IPD 侧任何审计/审批。真库权限分配探针：

```
sys_menu × sys_role_menu：system:info:* / system:fragment:* / system:attach:* 全族
  → 授予 role_id 900201 (ipd_pm) + 900202 (ipd_group_leader)
sys_user_role：910102→900202、910103→900201、910104→900201
```

即**全部 3 个非 admin 普通用户现网即持有该提权能力**。这不是 §8 意义上的上限模型冲突，而是过渡期把"上限唯一权威在 IPD"架空为一个 UPDATE 语句的距离。**结论：豁免成立，但必须以 B1 前置修复 info:edit 的 ownership 校验为条件，否则豁免变质为漏洞。**

**（e）agent 上限（§8.2 数字员工约束）**：B0 Gate 按当前会话用户判（非 agent 的 owner_person_id），属 fail-closed 更严方向，与"agent 上限不得高于 owner 上限"无冲突；B2 接 sensitivity 时须按 §8.2 取 owner∩agent 交集，届时改造。

### 2.5 问题 4：S3 缓存身份段完备性

**跨身份污染向量盘点（全仓检索缓存载体）：**

| 载体 | 位置 | 性质 | 判定 |
|------|------|------|------|
| `retrievalCache` | `KnowledgeRetrievalServiceImpl`（ConcurrentHashMap，TTL 5min / 上限 1000，满则先清过期再全清） | **全仓唯一检索结果缓存**，S3 身份段已插 kid 之后 | 已隔离（见下述残留） |
| `storeCache` | `MilvusVectorStoreStrategy` 键 `storeCache` | EmbeddingStore **连接实例**缓存（key=collectionName=kid 拼接），非内容缓存 | 无身份污染面 |
| `memoryCache` | `ChatServiceFacade` 键 `memoryCache` | 会话记忆（key=sessionId），非 RAG 检索结果 | 与 kid 无关 |
| augmentor 层 | `DefaultRetrievalAugmentor` / `CompositeContentRetriever` / `CustomVectorRetriever` | 每次 augment 现建、无 memoize、去重在单次调用内 | 无缓存 |

**无 docId/fid 维度的检索结果缓存**——docId 仅作为 `CompositeContentRetriever.retrieve` 单次调用内的去重键与 fragment 查询条件，不落任何跨请求缓存。

**invalidateKnowledge 覆盖完整性**：新键结构 `kid|identity|query|...`，`key.startsWith(kid+"|")` 对全身份段命中（专测 `invalidateKnowledgeClearsAllIdentitiesForKid` 覆盖）；数值前缀无互撞（invalidate("1") 的 "1|" 不误伤 "12|"）。调用面核验：`KnowledgeInfoServiceImpl.updateByBo`、`KnowledgeFragmentServiceImpl.updateByBo/deleteWithValidByIds` 均在变更后按 kid 前缀失效——语义完整。

**升级部署旧键残留**：retrievalCache 为进程内 Map，随重启清空，**不存在跨部署旧键（无身份段形态）残留或失效路径缺口**——该顾虑对进程内缓存不成立。

**残留两点：**
1. **非 HTTP 线程身份段恒 "anon"**：`identitySegment()` 依赖 `LoginHelper.getUserId()`，ws 消息线程与工作流执行线程均取 null → 所有 ws 用户共享 anon 段。因 ws 路径 Gate 双参前置把关（anon 段内只可能出现"已过 Gate 的 kid"的结果），不构成越权读；但漏网口 A（aiflow）恰无 Gate 直进 retrieve，其结果落入 anon 段——**S3 是纵深防御层，在 Gate 缺位的口上无保护作用**。ws 路径还造成同一用户 HTTP(userId 段) 与 ws(anon 段) 双份缓存（性能冗余，非安全问题）。
2. 身份段仅 userId 单维：B2 检索过滤接线后须将 maxSensitivity/scope 并入身份段（§8.3 已登记，本审计确认其必要性与 javadoc 约束（kid 必须保持第一段）的相容性）。
