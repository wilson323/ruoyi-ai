## 一、C09 项目等级评定与差异化系数

### 1.1 动作目的

在概念阶段为项目定档 **S / A / B** 三档，并给出该档对应的 **差异化系数**，作为后续分级管控（G1 门禁分级）与资源投入判断的输入。

权威动作定义（`ActionCatalog.java:37`）：

```
new ActionDef("C09", "项目等级评定与差异化系数", "CONCEPT", "MARKET_PM", "DEEP", true, "ALL", "", false, "", "AI_DIRECT")
```

字段逐项：阶段 `CONCEPT`；主责 R `MARKET_PM`；深度 `DEEP`；**阻断 true**；适用 `ALL`；无数值登记字段（`valueFields=""`）；无 Gate 绑定；执行档位 `AI_DIRECT`（AI 直接执行，非 AI 生成、非人工门）。

wss v3 原文第 148 行 RACI：**R 市场PM / A 产品组长 / C 研发PM / I —**，深度深，交付物「项目等级评定记录」，阻断 Y。

动作目的因此可表述为：**形成一份经产品组长确认的项目等级评定记录，且该记录在 G1 通过后与 C08 四项基准一并冻结。**

### 1.2 执行规范

**做什么**：核定等级 + 核定系数 + 记录确认链。

**谁做**：R = 市场PM（提议）；A = 产品组长（确认）；AI 代理只做校验与记录，不代填。

**用什么输入**：

| 输入 | 用途 | 来源 |
| --- | --- | --- |
| 市场机会与商业目标摘要 | 支撑等级提议理由 | 项目资料 |
| 双 PM 联合提议意见 | 等级与系数草案 | 用户/项目资料 |
| 产品组长确认结果 | A 角确认 | 系统外确认后录入 |

**按什么步骤做**（依据 `project-grade-coefficient-ipd/SKILL.md`「步骤」段）：

1. 核对是否已给出拟议等级与系数；**未给出则只列缺项，不代填**。
2. 校验系数与等级的对应关系，并落在校验区间内；不符则标「校验失败」并请用户更正。
3. 记录四要素：提议人（双 PM）、确认人（产品组长）、等级、系数、确认时间与依据。
4. 输出四块内容：资料核对 / 等级与系数表 / 确认链 / 缺项清单。

**判定通过的依据**：等级为 S/A/B 之一；系数落在该档口径区间；产品组长确认证据存在。三者齐备才算完成评定。

**AI 的禁止事项**（技能包「禁止事项」段，照录）：

- 禁止 AI 自行选定等级或代填差异化系数。
- 禁止使用与已定固定值不符的系数并声称合规。
- 禁止在无产品组长确认证据时写成「已确认」。
- 禁止给出 Gate 通过 / 不通过结论。

### 1.3 交付物与验收

**产出物形态**：`sop_templates.content` 的富文本正文（mediumtext），配套 `stage_actions` 实例绑定。

**可核对的验收点**：

| 验收点 | 核对方式 |
| --- | --- |
| 等级三档取值存在且唯一 | `projects.level` ∈ {S, A, B} |
| 系数落在该档区间 | 见 §四「与现有系统的对应」的区间表 |
| S/B 档有系数理由 | `projects.level_coefficient_reason` 非空 |
| 系数与等级的对应关系被校验 | 见 §四「与现有系统的对应」的服务端校验口径 |
| 产品组长确认链存在 | **无对应载体**（见 §四） |
| 缺项清单存在 | 正文内必须有「缺项清单」块 |

### 2.1 动作目的

对同一项目下的市场 PM 与研发 PM **各自独立**评定贡献度，形成贡献度评定表，经产品组长确认后定档。

字段逐项：阶段 `LIFECYCLE`；主责 R `BOTH`（市场PM + 研发PM）；深度 `DEEP`；阻断 true；适用 `ALL`；无 Gate 绑定；执行档位 `AI_DIRECT`。

wss v3 原文第 280 行 RACI：**R 市场PM+研发PM / A 产品组长 / C — / I —**，交付物「贡献度评定表」，阻断 Y。

### 2.2 执行规范

**做什么**：按五维度评定双 PM 各自的贡献度，给出市场 / 研发占比，记录三方确认链。

**谁做**：R = 双 PM（各自评定）；A = 产品组长（确认）；AI 代理不代评。

**用什么输入**：

| 输入 | 用途 | 来源 |
| --- | --- | --- |
| 双 PM 自评与互评要点 | 五维度素材 | 用户 |
| 产品组长确认意见 | A 角 | 用户 |
| 拟议市场 / 研发占比 | 区间校验 | 用户 |

**五维度名称**：`Contribution.java` 类注释第 20 行给出系统实现口径为「立项主导 / 差异化创新 / 上市节奏 / 市场结果 / 协同领导力」，DDL 列名为 `market_self_initiation` / `_innovation` / `_launch` / `_market_result` / `_leadership`（`schema-baseline-20261003.sql:673-682`）。**注意**：技能包 `dual-pm-contribution-ipd/SKILL.md` 明确写「仓内清单未逐条展开维度名时，不得编造维度清单」——上述五维是**代码实现口径**，wss v3 原文只写「五维度」三字、未列名。此点列入 §五待确认 Q2。

**按什么步骤做**（依据 `dual-pm-contribution-ipd/SKILL.md`「步骤」段）：

1. 收集已有评分 / 维度行；无表则列缺项并请用户提供模板字段。
2. 校验市场%、研发% 落在 40–65 / 35–60；且二者与用户声明规则一致，**不擅自重归一**。
3. 记录确认链：双 PM → 产品组长。
4. 输出：评定表摘录 / 占比校验 / 缺项清单。

**判定通过的依据**：五维度评分完整且各维在 0–100；市场占比 ∈ [0.40, 0.65]；产品组长确认完成。

**AI 的禁止事项**（技能包「禁止事项」段，照录）：

- 禁止 AI 代定贡献度百分比或伪造组长确认。
- 禁止发明未在输入中出现的五维度名称冒充制度原文。
- 禁止把两 PM 分数平均成单一奖金系数（DOC-01 约束：各自评定）。

### Q1 · C09 系数走定值还是走区间？（**最高优先级，阻塞其他**）

- **问题**：wss v3 L148 写「已定：S=1.5 / A=1.0 / B=0.8」（定值），待确认决策表 v2 E21 写「S = 1.5–2.0 / B = 0.6–0.8」（区间）。系统实装的是区间（`ProjectService:125-128`）。
- **建议方案**：**维持区间口径**。
- **理由**：① E21 是决策表 v2 的正式裁决条目，比 v3 动作清单的「已定」更晚且更具体；② `ProjectService:121-123` 的注释已写明「口径未变，避免校验静默放宽」，即代码侧是**有意**保留区间；③ 改回定值会作废 `level_coefficient_reason`「S/B 须在区间内录入具体值 + 说明理由」的审计要求（该列已建）。
- **备选**：若 owner 要定值制，则 SOP 正文需改为「系数必须等于 1.5/1.0/0.8」，且需同步收窄服务端校验——此改动会触及既有数据，**需 owner 明示后才可执行**。

### Q2 · LC04「五维度」的名称以哪份为制度原文？

- **问题**：wss v3 L280 只写「五维度」三字，未列名；代码实现有五个具体名（立项主导 / 差异化创新 / 上市节奏 / 市场结果 / 协同领导力，`Contribution.java:20`）。技能包明令「不得编造维度清单」。
- **建议方案**：**以代码实现口径为准，在 SOP 正文中明确标注这是系统实现口径而非 wss 原文**。
- **理由**：① DDL 十列已按这五维建好（`schema-baseline-20261003.sql:673-682`），改动成本极高；② SOP 是给执行人看的操作说明，缺维度名则无法执行；③ 标注来源即可满足技能包「不冒充制度原文」的禁令。
- **备选**：若 owner 认为必须回到 wss 原文，则需先由 owner 补齐 v3 的维度名，否则 SOP 无法落笔。

### Q3 · LC07 的产品组长是「知会（I）」还是「确认（A）」？

- **问题**：wss v3 L283 原文 RACI 为「R 市场PM / **A —** / C 研发PM / **I 产品组长**」；技能包禁止事项写「禁止无产品组长侧确认证据时写成已生效」，把 I 当成了确认人。
- **建议方案**：**以 v3 原文为准——产品组长是被知会，不是确认人**；SOP 正文的禁止事项改为「禁止在无产品组长知会留痕时宣称已通知」。
- **理由**：① v3 是需求权威，改技能包比改需求文档代价小得多；② 「知会」与「确认」在系统里的实现代价差异很大——确认需要身份校验与留痕字段，知会不需要；③ 当前系统本就**没有**产品组长确认载体（§4.1），按 v3 口径反而与现状自洽。
- **影响**：若 owner 裁定为「确认」，则 LC07 需要新增确认字段与校验，属新增载体，需单独立项。

### Q4 · LC07 的状态取值是三值还是四值？

- **问题**：wss v3 L283 写三值（在售 / 限售 / 停产）；`projects.lifecycle_status` 的 DDL 注释（`schema-baseline-20261003.sql:2493`）写四值 `ON_SALE|LIMITED|EOL|ARCHIVED`，多出 `ARCHIVED`。
- **建议方案**：**SOP 正文按 wss 三值写**，并在附注中标明系统列另有 `ARCHIVED` 取值（该值目前仅由 ZK 场景初始化器写入，属演示数据，见 §4.3）。
- **理由**：① `ARCHIVED` 对应的是 `projects.status='ARCHIVED'`（项目状态机字段，`ProjectService:64-69`），与 `lifecycle_status` 的生命周期语义重叠但不是一回事；② 按 wss 三值写不会把演示数据语义固化成制度。
- **备选**：若 owner 认为 `ARCHIVED` 应正式纳入生命周期取值，则需同步修订 wss v3 并补状态迁移规则。

### Q5 · LC07 的「变更留痕」载体是否要在首版新建？

- **问题**：LC07 要求产出「生命周期状态变更记录」，但系统只有 `projects.lifecycle_status` 一个当前值列，**无变更历史**（§4.3 实测）。当前值无法回答「谁在何时从什么改成什么」。
- **建议方案**：**首版 SOP 只要求正文内记录变更前后值与理由（文本层留痕），不新建历史表**；历史表作为独立事项另立项。
- **理由**：① 首版目标是 SOP 内容落地（S1/S2 是文档动作），新建表属 DDL 与接口开发，超出本刀范围；② 文本层留痕已能满足「变更记录」这一交付物形态，且与 `sop_templates.content` 的载体一致。
- **风险（须 owner 明示接受）**：文本留痕**不可查询、不可统计**，若后续 KPI 或复盘需要按状态变更频次分析，文本不够用。

### Q6 · 三个动作的 SOP 是否强制绑定 `stage_actions.sop_id`？

- **问题**：`SopTemplate` 类注释第 13 行称「实例化快照走 `SopTemplateInstance`（`stage_actions.sop_id` 绑定当时 PUBLISHED 的模板 id）」。若三个动作的 SOP 都要求实例化绑定，则新建项目时三处 `stage_actions` 行都要指到模板。
- **建议方案**：**首版只 seed `sop_templates` 模板本体，不强制实例化绑定**。
- **理由**：① 任务基线明确「首版必须靠 seed SQL，本步只出内容不出 SQL」，实例化绑定属于下一刀；② 实例化会把模板版本与项目快照绑定，模板改版后的处理策略（BR-IPD-07：新项目用新版、在研项目保持原版）需要额外校验逻辑，不宜在 S1 顺手决定。
- **备选**：若 owner 要求首版即绑定，则需明确在研项目的模板版本升级策略。

### Q7 · 三条动作的「阻断」在 SOP 层怎么表达？

- **问题**：三个动作在 `ActionCatalog` 中 `blocking=true`，即未完成则阻断阶段推进。但 SOP 正文本身不产生阻断力——阻断由 `stage_actions` 的完成状态驱动。
- **建议方案**：**SOP 正文只写「什么算完成」，不写「未完成会怎样」**；阻断行为的表述引用系统既有口径，不在 SOP 里重述。
- **理由**：① SOP 若复述阻断规则，两处一旦漂移就产生文档与实现的分叉（本项目历史上已多次吃过这类漂移的亏）；② 阻断是系统行为，不是动作规范的一部分。
- **风险**：owner 若认为业务执行人需要知道「不做会卡住哪个阶段」，则需改为在 SOP 里写明**引用**而非重述。
