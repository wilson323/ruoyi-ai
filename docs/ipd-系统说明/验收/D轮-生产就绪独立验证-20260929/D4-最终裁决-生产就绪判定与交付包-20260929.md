## 0. 终判

# 生产就绪判定：**`PARTIAL`**（明确不就绪，且非 `BLOCKED`）

**一句话裁决**：本轮 D 路完成了**独立追溯链路的建立**与**运行态/数据层/源码层三层的实测分离**，把「看板 done」与「生产就绪」之间的差距**量化到条**（273 canonical 路由中 `PROD_READY = 0`；249 AC 中 PASS 仅 47 条 = 18.9%；49 页中 21 页规格路由层面零实现）；但同时发现了**一条可立即执行的 P0 通路**——17 条 404 路由的唯一阻塞是 jar 未重建重启，**数据层与源码层均已就绪**。

1. `PROD_READY = 0`——273 条 canonical 路由中**没有任何一条**达成"生产可用"态；

### 10.4 七条方法论收获（应写入项目经验）

1. 静态扫描器给出的孤儿/命中率数字，**必须先用"形状异常"自检**（前缀是否齐、是否有畸形重复段、是否把 query 当 path）。缺陷 1–3 全是靠形状异常发现的，**不是靠跑更多测试**。
2. **HTTP 探针必须先验证探针自身**：用一个已知可用的端点（如 `/api/v1/auth/me`）做**阳性对照**。若阳性对照也失败，则是探针缺陷而非系统缺陷。
3. **404 必须拆路由级与资源级**，否则会把"数据不存在"误报为"功能未实现"。
4. **任何验收结论前先校运行态版本**：`lsof -nP -iTCP:<port> -sTCP:LISTEN` + `ps -p <pid> -o lstart,command` + jar 时间戳 + `git log --since=<jar时间>`。源码与运行态不一致时，**全部 HTTP 证据作废**。
5. **空输出 ≠ 零结果**。命令因 shell 语法失败时也可能返回空，必须先确认命令**真的执行了**（看 stderr / exit code）。
6. **判据要看方向，不只看幅度**。任何"是否随 X 增长"的判定，必须比较 X 的最小端与最大端，而不是看极差占比——极差可能来自噪声端（如首样本冷缓存）。
7. **区分"测了不达标"与"无可测对象"**。模型延迟、向量查询、恢复演练三项都是后者，必须标 `BLOCKED` 并说明为何不可测；**绝不能用 TEST provider 或空库的漂亮数字冒充达标**（那是最隐蔽的假绿）。
