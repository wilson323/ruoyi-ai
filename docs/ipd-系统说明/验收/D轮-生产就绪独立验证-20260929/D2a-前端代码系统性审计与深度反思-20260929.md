## 4. 典型案例深读

### 4.1（P1，新引入）自定义错误文案在错误链路中被静默吞掉

`views/ipd/project/detail/flow.vue:121-137`（本席位已读源码复核）：

```ts
    if (subStageProgress.value?.currentSubStageCode !== target) {
      throw new Error('推进结果与服务端回读不一致，请刷新后核实');   // L131
    }
  } catch (cause) {
    await loadSubStageProgress();
    subStageError.value = ipdErrorText(cause, { domain: 'project', fallback: '小阶段推进失败' });  // L136
```

`ipdErrorText` 只在 `error instanceof IpdRequestError` 时走 code 三级查表链（`ipd-error-text.ts:119-120`），普通 `Error` 直接落 `fallback`。后果链：
1. L131 精心撰写的提示是**不可达死文案**；
2. 推进实际成功、仅回读抖动时（`loadSubStageProgress` 内部吞错置 null → `null !== target` 必然触发 L131），用户看到「小阶段推进失败」——**与事实相反**，误导重复提交；
3. `flow.test.ts` 新增用例只覆盖 happy path，此分支无测——典型病根①。

### 4.2（P2，新引入）新增 API 模块绕过「ID 字符串 + 格式拒绝」约定且零测试

`api/ipd/stage-sub-stages.ts:25-27`：

```ts
export function fetchSubStages(): Promise<SubStage[]> {
  return ipdGet<SubStage[]>('/ipd/stage/sub-stages');   // 纯编译期 as T 断言，无运行时形态校验
}
```

对照同仓约定（`ai-document.ts:142`：「ID 一律字符串…格式异常直接拒绝，不做静默修补」）。若后端雪花 ID 序列化漂移为 number，此处静默放行。同一波 A 路新增的 guide-script.ts 配了测试、本文件没有——**纪律执行不一致**，说明"新增 api 模块 checklist"只存在于人肉记忆。

### 4.3（P2，存量）api 层反向依赖 views 层

`api/ipd/portal.ts:16`、`api/ipd/ai-document.ts:21` 运行时 import `views/ipd/_shared/ipd-error-text`，而该文件头自述「api 层不许 import views 层（否则循环依赖）」。当前未形成真环，但依赖方向倒置为运行时耦合；历史上 bid-error.ts 等 4 份分散码表正是同类漂移根因。

### 4.4（P2，存量）共享枚举 helper「有测无用」假覆盖

`_shared/ipd-enums.ts` 中 `deletionStateLabel / gateStateLabel / priorityText / severityText / demandStateTone` 等非测试引用均为 0（本席位逐一 grep 复核）。删除域页面用的是另一组 `DELETION_STATUS_TEXT`。覆盖率数字被无消费者导出虚撑——「测试全绿」在此处不等于「行为被锁」。

### 4.5（P2，新引入）window 事件自产自销 + 文案口径分叉

`_shared/ai-assistant.vue:500`（dispatch）与 `:546`（listen）为 `ipd:guide-sub-stage` 全仓唯一生产者与消费者（grep 复核）——组件内调用绕道全局事件总线，属「原型中没有的自创机制」红线排查对象（除非存在页面外派发的在途计划）。同文件 `:486` `error.message` 直出，丢失 transport/timeout 归类，与页面级 `ipdErrorText` 统一口径漂移。

## 5. 风险聚类与深度反思（映射 R25「5 类病根」框架）

| 根因类 | 本轮证据 | 反思与机制化处方（非补自觉） |
|---|---|---|
| ① 改主代码后测试没跟上 | P1（flow.vue 错误分支无测）、P2#2（stage-sub-stages 零测试） | 新增页面/api 的分支覆盖要求写进会红的门禁：扩展 `check-vitest-include-coverage`（已存在）把「api/ipd 新增实现文件必须有同名 test」升级为 FAIL 而非 warn；错误链路补负向用例（抛非 IpdRequestError 断言文案透传） |
| ③ 规则表与接线点靠人肉对账 | P2#2（同波新增两文件纪律不一致）、P2#4（helper 建了没接线）、P2#8（5 页本地 STATUS_TEXT） | 「谁后写谁占主导」的收口铁律目前只守错误码表；把「新增 api 模块必须 normalize+test」「枚举/文案只准引 _shared 单表」挂进 `check-ipd-frontend-drift.sh`（现 4 项检查扩为 6 项），违规即红 |
| ④ 前后端契约门禁 | 17 条 path 参数命名不一致持续输出噪音（门禁已存在但老账不清）、白名单 stale 1 条 | 门禁本身工作正常（EXIT=0），缺的是**存量清账节奏**：命名不一致择机统一或登记豁免口径；stale 白名单清账走看板卡人审（ratchet-data-guard 保护） |
| ⑤ 多事实源无对账 | P2#3（api→views 反向依赖）、P2#4、P2#8：码表/枚举/错误文案三个"收口"工程都留尾巴 | 三个收口工程共性问题是**只收口了一半、没有闭环检查**。处方：每个"单一事实源"工程交付时必须附带一条会红的守卫（方向依赖检查、孤儿导出检查），否则不算 done |
| 过度设计/双轨红线（用户 2026-09-24 红线） | P2#5 `ipd:guide-sub-stage` 自产自销事件总线 | 原型中没有的自创机制候选：若无页面外派发计划应改直接调用清理；**未发现**双轨请求通道/平行码表/第二套状态管理，无双轨风险 |

**总体反思**：本轮 7 个实质发现（P1×1 + P2×6）里 4 个（P1、P2#2/#4/#5）不是"写错"，而是**约定没有对应的红灯**。代码库静态指标（any=1、v-html=0、TODO=0、双通道=0）几乎无可挑剔，说明"写得干净"已内化；但凡靠"约定俗成"的部分（错误链路完整性、新增模块配套、枚举接线）就会随开发波次漂移。**下一步价值最大的不是再审一遍代码，而是把 §5 处方中的 3 条守卫做红。**
