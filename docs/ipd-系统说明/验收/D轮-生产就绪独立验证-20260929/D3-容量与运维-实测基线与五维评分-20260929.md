| 端点 | min | **p50** | p95 | max | 评价 |

| `/api/v1/auth/me` | 7.0 | **7.8** | 12.2 | 12.2 ms | 优 |
| `/api/v1/stage-actions?pageSize=10` | 7.6 | **8.9** | 11.5 | 11.5 ms | 优（表 17,838 行仍 <10ms） |
| `/api/v1/products?pageSize=10` | 10.1 | **11.5** | 16.1 | 16.1 ms | 良 |
| `/api/v1/audit-logs?pageSize=10` | 10.6 | **12.2** | 16.4 | 16.4 ms | 良 |
| `/api/v1/demands?pageSize=10` | 10.9 | **16.6** | 26.0 | 26.0 ms | 良 |
| `/api/v1/gate-elements?pageSize=10` | 17.3 | **19.0** | 25.1 | 25.1 ms | 良 |
| **`/api/v1/projects?pageSize=10`** | 69.0 | **72.0** | 76.1 | 76.1 ms | 🔴 **唯一离群，比同类慢 4–10×** |

### 1.1 🔴 `projects` 离群的性质判定：固定开销，非数据量

`projects` 表实测仅 **295 行**（`information_schema` 估 272），却是全组最慢。为区分「数据量成本」与「固定每请求开销」，做分页标度性测试（各 5 次取 p50）：

| pageSize | 1 | 10 | 50 | 100 |
|---|---|---|---|---|
| p50 (ms) | 60.9 | 66.2 | 72.0 | 62.8 |

**增长仅 +3.2%（pageSize 1→100），极差 11.1ms ⇒ 曲线平坦。**

⇒ **裁决：`projects` 的 ~60ms 是「固定每请求开销」，与返回行数无关。** 返回 1 行和返回 100 行成本相同，说明瓶颈不在 SQL 数据量，而在每请求必经的某个固定环节。三个候选根因（需 B 路用 profiler/SQL 日志定位，D 不改源码）：

1. **N+1 查询**：列表每行再查关联（`projects` 是 `Product 1:1 Project` 的一端，可能逐行反查 product/stage/gate）
2. **权限重算**：每请求对 295 行逐行做 ACL/租户过滤，而非一次性下推 SQL
3. **每请求远程调用**：如逐行调 HR/用户中心补全 owner 信息（`HrApiClient` 存在）

> ⚠ 方法论更正（D 自检缺陷 8）：本判据必须看「最大页 vs 最小页」的**方向**。首版脚本用「极差 / 最大值 > 25%」判定，因 pageSize=1 的首样本受冷缓存影响反而最慢（72ms），会误得出「随分页增长」的**相反结论**。已改为按 `growth = (large - small) / small` 判定。

### 1.2 并发退化（0 错误率，优雅退化）

| 并发 | p50 | p95 | max | 5xx/错误 |
|---|---|---|---|---|
| 串行基线 | 72.0 | — | 76.1 | 0 |
| **10 路** | 366.4 | 466.5 | 466.5 | **0** |
| **20 路** | 324.1 | 389.6 | 392.9 | **0** |
| **50 路** | 1059.1 | 1132.5 | 1133.9 | **0** |

**判定**：

1. ✅ **零失败**：50 路并发下 0 个 5xx、0 个超时、0 个连接拒绝 ⇒ 无雪崩、无连接池耗尽（HikariCP max-pool=80，dev/prod 一致；超原 spec 60 有 `SEC-HIGH-1 R9-BC-COST` BCrypt cost=10 持连接时间×10 的压测依据）。
2. ⚠ **有效并发远低于名义并发**：串行 72ms，50 路并发 p50 1059ms ≈ 14.7×。若完全并行应仍为 ~72ms，若完全串行应为 ~3600ms ⇒ **有效并发度约 5–7**，存在串行化瓶颈（与 §1.1 的固定开销同源，或线程池/锁竞争）。
3. 🔴 **测量方差过大，单次 p50 不可作 SLO 依据**：同一 10 路并发在两次独立运行中 p50 分别为 **155.9ms 与 366.4ms**（2.3× 差异）；50 路为 **724.0ms 与 1059.1ms**。本机为共享开发环境（同时跑 Docker 9 容器 + vite + MySQL + Weaviate + 看板），**噪声不可控**。⇒ 任何容量阈值判定必须：① 在隔离环境；② ≥5 轮重复；③ 报告中位数与方差。本轮不满足，故 §7 判 SLO `BLOCKED` 而非"通过"。

## 2. 失败停止（fail-fast）与输入校验

计划要求验「失败停止」。实测 6 个负例（全部只读）：

| 场景 | 端点 | HTTP | 包络 code | 耗时 | 判定 |
|---|---|---|---|---|---|
| 未认证访问受保护端点 | `/api/v1/auth/me` | 401 | `20001` | 7.01 ms | ✅ 快速拒绝 |
| 不存在的资源 ID | `/api/v1/projects/99999999999` | 403 | `30001` | 12.07 ms | ✅ 返 403 而非 404，**不泄漏资源存在性**，符合安全实践 |
| **非法分页参数** | `/api/v1/products?pageNum=-1&pageSize=99999` | **200** | **`0`** | 11.50 ms | 🔴 **非法参数被接受并正常返回** |
| 不存在的路由 | `/api/v1/nonexistent-route-xyz` | 404 | `50001` | 8.06 ms | ✅ 符合 IPD 契约包络 |
| actuator/health 用 IPD token | `/actuator/health` | 401 | `401` | 6.06 ms | ✅ 边界正确（见 §4.2） |
| actuator/shutdown 用 IPD token | `/actuator/shutdown` | **401** | `401` | 6.48 ms | ✅ **不可达**，见 §4.2 |

**fail-fast 结论**：6 个负例全部 ≤ **12.07ms** ⇒ 无一进入昂贵路径，异常处理是快速失败而非慢失败。**未发现"靠扩大超时掩盖"的情况**（计划失败路径明令禁止的行为），无端点出现超时或长尾。

### 2.1 🔴 唯一真红：分页参数无校验（潜在 DoS 向量）

`GET /api/v1/products?pageNum=-1&pageSize=99999` → **HTTP 200 `code=0`**，即：

- `pageNum=-1`（非法页码）被接受
- `pageSize=99999`（无上限）被接受

本轮实测该请求仅 11.5ms 返回，是因为 `products` 只有 368 行，`pageSize=99999` 实际只捞到 368 行。**但这是数据量小掩盖了缺陷**：

- 对 `stage_actions`（**17,838 行 / 5.4MB**）或 `audit_logs`（6,552 行 / 3.7MB）发起 `pageSize=99999`，将触发**无界查询 + 全量序列化**
- 并发场景下（§1.2 已证有效并发仅 5–7）数个此类请求即可打满连接与堆
- 属**未认证成本放大**向量：任何持有效 token 的账号（含最低权限）都能触发

**归属 B 路 P1**：在分页入参补 `@Min(1)` / `@Max(200)`（或框架统一 `PageQuery` 校验），并对超限返 `code=10001`。**D 不改源码**，仅出具裁决。

> 注：本轮**未**对 `stage_actions`/`audit_logs` 实跑 `pageSize=99999`，因为那会在共享开发环境产生真实负载并可能影响其他在途会话。该风险由「参数被接受」+「表实际行数」推得，标注为**推论而非实测**，需 B 路在隔离环境复现。

## 9. D3 自检：本轮 D 自己犯的 2 个错

| # | 错误 | 如何发现 | 影响 | 已修 |
|---|---|---|---|---|
| **8** | 分页标度性判据用「极差/最大值」而非「方向」 | 实测 pageSize=1(72ms) 反而比 100(55ms) 慢，脚本却输出「随分页增长」 | 会得出**相反结论**：把"固定每请求开销"误报为"数据量成本"，导致 B 路去优化错误的方向（加索引而非查 N+1） | ✅ 改按 `growth=(large-small)/small` 判定（§1.1） |
| **9** | 敏感日志维度初评「0 个脱敏 converter」 | 复查时发现 zsh 下 `grep --include=*.java` 未加引号触发 `no matches found`，命令**根本没执行**，我却把空输出读成"0 个" | 会对 C 路提出一条**假红指控**（"无脱敏能力"），而实际框架能力完整、60 处采用 | ✅ 改用 Python 遍历源码目录（`d3-ops-probe.py`），实测 2 个框架文件（§4.5a） |

**方法论收获（补 D1 §10 的 4 条）**：

5. **空输出 ≠ 零结果**。命令因 shell 语法失败时也可能返回空，必须先确认命令**真的执行了**（看 stderr / exit code）。缺陷 9 的根因是把"命令失败的空"当成"检索结果为空"。
6. **判据要看方向，不只看幅度**。任何"是否随 X 增长"的判定，必须比较 X 的最小端与最大端，而不是看极差占比——极差可能来自噪声端（如首样本冷缓存）。
7. **区分"测了不达标"与"无可测对象"**。模型延迟、向量查询、恢复演练三项都是后者，必须标 `BLOCKED` 并说明为何不可测；**绝不能用 TEST provider 或空库的漂亮数字冒充达标**（那是最隐蔽的假绿）。
