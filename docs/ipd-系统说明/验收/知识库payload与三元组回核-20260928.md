## 第一部分（E2）：payload 现态 & 向量三元组回核

### 0. 前提纠偏（重要）

PoC 分支 commit `129327db`（G5）实证的是 **AgentScope InMemoryStore**，不是 Weaviate。
`git diff main poc/agentscope-kernel -- ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/vector/`
输出为空——PoC 分支未改过 WeaviateVectorStoreStrategy，主干版即现态。两条线分开列。

### 1. G5 PoC（InMemoryStore 线）实际写入字段

取证：`git show poc/agentscope-kernel:ruoyi-modules/ruoyi-chat/src/test/java/org/ruoyi/chat/poc/kernel/AgentScopeRagPocIT.java`

| 键 | 值形态 | 证据方法 | 用途 |
|---|---|---|---|
| docId | "p1-spec" 等 | `doc()` | 文档标识 |
| chunk 序号 | 固定 "chunk-0" | `new DocumentMetadata(content, docId, "chunk-0", payload)` | PoC 未实现多 chunk 编号 |
| payload.projectId | "P1"/"P2" | `payload.put("projectId", projectId)` —— payload 唯一键 | KB/项目维隔离 |
| vectorName | "pP1"/"pP2"/"shared"（前缀 p+projectId） | `document.setVectorName(vectorName)` | store 级分桶，调用方手工拼 |

检索双通道：①store 级 `RetrieveConfig.vectorName("pP1")`（正例+跨桶不可见负例）；
②应用层取回后 Java 内存过滤 `getPayloadValue("projectId")`（正例+负例）。
类注释实证：AgentScope 2.0.3 RetrieveConfig 无 metadata 字段，原生过滤仅 vectorName。
嵌入模型为 StubEmbeddingModel（64 维词袋哈希），非真实模型。

### 2. Weaviate 真实 payload 现态（主干策略线）

取证：`git show poc/agentscope-kernel:ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/vector/impl/WeaviateVectorStoreStrategy.java`

- payload 仅 4 键：`text` / `fid` / `kid` / `docId`；`vectorizer("none")` 手工向量。
- **没有**：embedding_model/dim/embedded_at 版本三元组、scope 键、projectId 键、chunk 序号键。
- 分桶：**collection 级**——class 名 = 配置 `classname`（LocalKnowledge）+ kid，一库一 class；不用 vectorName。
- 检索 GraphQL 仅 `nearVector + limit`，**无 Where 过滤**（class 即隔离边界）；删除按 docId/fid。
- 小瑕疵：search 回读字段只有 text/fid/docId，未回读 kid。

### 3. 在线佐证状态（部分跑通）

- `docker ps` 确认 weaviate-weaviate-1（1.30.0）运行中，宿主端口 **28080**（8080 被 RuoYi 后端占用）。
- `curl http://127.0.0.1:28080/v1/schema` → 200 `{"classes":[]}`——**在线无任何 class 存量**，
  字段实物无法回读；本表以源码为准。该实例 /v3 路径 404（仅 v1 可用），偏差原因未深查。

### 4. 主干向量版本三元组判定

| 项 | 判定 | 证据 |
|---|---|---|
| knowledge_info.embedding_model | 列存在、入库被赋值（MapstructUtils 透传前端表单）；服务端无默认值/校验/来源核验 | `KnowledgeInfo.java` 字段 embeddingModel；`KnowledgeInfoServiceImpl.insertByBo`（validEntityBeforeSave 留有 TODO） |
| knowledge_fragment 片段级 model/dim/timestamp | **不存在** | `KnowledgeFragment.java` 仅 fid/docId/idx/content/remark/knowledgeId；schema-snapshot DDL 无三列 |
| embedded_at（全仓） | **不存在** | 全仓 grep 零命中 |
| 维度存储 | 仅模型配置级 chat_model.model_dimension；运行时反查，失败回退默认 1024（脆弱点：模型配置删改后历史集合无法复原） | `MilvusVectorStoreStrategy.getDimensionByKid` |

消费链路：写入与检索都实时取 `knowledge_info.embedding_model`「当前值」，不回看历史值
（`KnowledgeAttachServiceImpl.parse` → storeEmbeddingBo；`CustomVectorRetriever`/`ChatServiceFacade` 检索侧同）。

换模型重嵌入：**无自动机制**。`updateByBo` 改 embedding_model 无守卫（不比对旧值）→
改模型后旧向量与新查询模型混用是真实存在的静默错配窗口；唯一人工通道
`reparseKnowledge` 按 docId 清旧向量后全量重 parse，无版本追踪、无部分迁移。

### 5. knowledge_attach.status 状态机写入点

枚举 `KnowledgeAttachStatus`：WAITING(0)/PARSING(1)/COMPLETED(2)/FAILED(3)。
全部写入点在 `KnowledgeAttachServiceImpl`：上传置0；**CAS 抢占置1**
（`lambdaUpdate().set(status,1).ne(status,1)` 防并发重复解析）+ 冗余二次写（裸 updateById，小不一致）；
成功置2；异常置3 + remark 截断 255。扩展重嵌入状态应沿用 CAS 模式。

### 6. 对设计的直接结论

1. 两套隔离模型并存：主干「一 KB 一 class + 4 字段 payload」vs PoC「单 store + vectorName 桶 + payload 应用层过滤」。
   统一到维度前缀 collection 方案时，Weaviate 侧 class-per-kid 需整体换轨。
2. 片段级版本三元组是当前架构空洞：版本信息只存活于 knowledge_info 单列，换模型即静默脏读。
3. 设计若承诺「换模型自动迁移」，须先补 CAS 状态机之外的重嵌入进度态与按模型分桶共存策略。
4. G5 正负两例测试模板（对照组必须命中 + 过滤桶必须非空）可直接复制到未来 KB 四维隔离验收。

### 仍缺的证据

- 有存量数据的演示库上的 `GET /v1/schema` 实物回读（本机实例为空集）。
- Qdrant/Milvus 两策略 payload 字段集与 Weaviate 的三库一致性对表。
- `StoreEmbeddingBo.embeddingModelId` 各策略使用度；`reparseKnowledge` 的 Controller 触发面。
- G3 KernelScopeKey 四维与 G5 payload 单键 projectId 的映射展开。

### 2. 五列新属性缺口对照

现态 InfoVO/InfoForm 字段：id/userId/name/share/description/切分与检索调优参数/
vectorModel/embeddingModel/rerank 系/enableHybrid/remark。

| 新属性 | 前端现状 |
|---|---|
| scope_type | 缺失（share 0/1 语义远弱于四值归属） |
| group_id / project_id / owner_agent_id | 缺失（知识库与 IPD 项目概念未打通） |
| sensitivity | 缺失（share 可视为 PUBLIC/INTERNAL 二值前身） |
| fragment 向量三元组 | 缺失（FragmentVO 仅 id/attachId/docId/idx/content/remark） |

**最大负债：同一 InfoForm 存在 4 份平行表单实现**，新属性落地需同步 4 处（建议删孤儿）。

### 3. 端点与体验缺口

- 端点全集走 `/system/info|fragment|attach` + `/system/attach/upload|parse/{id}|reparse/knowledge/{kid}`；
- **无 status 轮询**：解析状态更新完全靠手动「刷新」按钮（触发文案自认「请稍后刷新」）——
  向量三元组版本化后解析周期变长，建议与本次升级一并补轮询/SSE；
- 智能体页 `knowledgeIds` ApiSelect 数据源 = `GET /system/info/list` 全量无过滤——
  scope/sensitivity 上线后此处是「按可见性过滤」第一改造点；AgentVO 现态无 owner/project 字段。
