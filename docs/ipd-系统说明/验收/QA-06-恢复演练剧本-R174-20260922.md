# QA-06 恢复演练剧本（R174-P1.6，2026-09-22）

> 本剧本与 `QA-06-部署演练checklist-20260919.md`（部署侧步骤）互为补充：checklist 管"首次部署+回滚"，本剧本管"运行期故障的发现→隔离→诊断→恢复→验证→复盘"。
> **真实多环境演练不在本轮授权内**（与 checklist 保持口径），dry-run 脚本可在本地反复跑。

## 一、故障分级与 RTO/RPO

| 等级 | 场景 | RTO（恢复时间目标） | RPO（数据丢失上限） | 通知范围 |
|---|---|---|---|---|
| **P0-致命** | 后端进程宕机、DB 主库不可写、双实例脑裂 | ≤ 5 min | ≤ 1 min（最近 audit 写入） | owner + 全员 |
| **P1-严重** | DB 主库只读、Redis 不可达、审计日志 hash 链断裂 | ≤ 15 min | ≤ 5 min | owner + 模块 owner |
| **P2-一般** | 第三方依赖失效（邮件/SMS/对象存储）、单实例流量过高 | ≤ 30 min | 0（无业务写入丢失） | owner |
| **P3-轻微** | 单接口 5xx 偶发、慢 SQL 增长、磁盘预警 | ≤ 4 h | 0 | 模块 owner |

**RTO 计算口径 = 告警发现 → 服务恢复 + 业务验证完成**。
**RPO 计算口径 = 故障发生 → 最近一次成功持久化的差值**。

## 二、发现层（监控触发 → 告警分级）

### 2.1 监控指标（R174-P1.5 OPS-06 已接入）

| 指标 | 来源 | 阈值（Prom 告警） |
|---|---|---|
| `up{job="ipd-backend"}` | Prometheus 抓取 /actuator/health/liveness | == 0 持续 30s → P0 |
| `jvm_memory_used_bytes{area="heap"}` | Micrometer | > 90% capacity 持续 5min → P2 |
| `hikaricp_connections_active` | Micrometer | > 90% max 持续 1min → P1 |
| `http_server_requests_seconds_count{status="500"}` | Micrometer | 5min 内增速 > 10 → P0/P1 |
| `audit_hash_chain_head_value` | 自定义 gauge | null 或 stale > 5min → P1 |
| `redis_connection_active` | Lettuce client metrics | == 0 持续 1min → P1 |
| `disk_free_bytes` | Micrometer | < 5% total → P2 |

### 2.2 告警接收链路

```
Prometheus alertmanager → 钉钉/企微 Webhook → 值班人 + 备用值班
                                    ↓
                              PagerDuty 升级（P0/P1）
```

**值班轮值表**：`docs/ipd-系统说明/ops/值班表-YYYY.md`（owner 维护）。

## 三、隔离层（故障确认 → 影响圈收敛）

### 3.1 P0 后端宕机隔离

1. **L4 切流**：`nginx upstream ipd_backend { server 127.0.0.1:16039 max_fails=1 fail_timeout=10s; ... }` 自动剔除。
3. **L7 兜底**：返回 `503 + Retry-After: 30`，前端展示"系统维护中"占位页。
4. **DB 保护**：MySQL 开启 `read_only` 禁止写入（避免脏数据进入）。

### 3.2 P1 脑裂隔离

1. **只保留一个写入实例**：通过配置中心将另一实例 `ipd.write.enabled=false`。
2. **客户端降级**：前端禁用"提交/确认"等写操作按钮，保留只读浏览。
3. **DB 读写分离检查**：`SELECT @@read_only, @@super_read_only` 双实例对比。

## 四、诊断层（症状 → 根因）

### 4.1 诊断决策树

```text
后端 /actuator/health 返 DOWN
├── livenessState=DOWN → 进程级故障（OOM / Native crash / 死锁）
│   └── 拉 jstack/jfr → 看阻塞栈
├── readinessState=DOWN → 启动期未就绪（DB/Redis 探活失败）
│   └── curl /actuator/health/readinessState → 看哪个组件 DOWN
│       ├── db=DOWN → MySQL 连不上
│       │   ├── mysql client 连测 → 网络/DNS/凭据
│       │   ├── SHOW PROCESSLIST → 是否有长事务锁
│       │   └── SHOW ENGINE INNODB STATUS → 锁等待/死锁
│       ├── redis=DOWN → Redis 连不上
│       │   └── redis-cli ping / cluster info
│       ├── mail=DOWN → SMTP 配置/网络 → 通常 P3 不阻断
│       └── neo4j=DOWN → 图数据库未启用 → 通常 P3 不阻断
├── application context 启动失败 → application.yml / Bean 装配问题
│   └── 看启动日志前 30 行 + Caused by 链
└── DB 写超时 / 锁等待 → SQL 性能问题
    └── p1-sql-watchdog.sh 抓慢 SQL
```

### 4.2 关键诊断命令（与 `scripts/ops/` 对齐）

```bash
# 1. 后端进程状态
ps -ef | grep ruoyi-admin.jar | grep -v grep
curl -fsS http://127.0.0.1:16039/actuator/health/readinessState

# 2. DB 状态
mysql --defaults-file=.codex/ipd-dev/config/mysql-client.cnf -e "SHOW STATUS LIKE 'Threads_connected'; SHOW ENGINE INNODB STATUS\G" | head -50

# 3. Redis 状态
redis-cli -h 127.0.0.1 -p 6379 ping
redis-cli -h 127.0.0.1 -p 6379 info clients | head -10

# 4. JVM 状态
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print | head -50

# 5. 审计 hash 链
mysql --defaults-file=.codex/ipd-dev/config/mysql-client.cnf -e \
  "SELECT chain_id, head_value, head_seq, updated_at FROM audit_chain_head ORDER BY updated_at DESC LIMIT 3"
```

## 五、恢复层（根因 → 动作）

### 5.1 恢复模式（4 种）

| 模式 | 适用场景 | RTO 成本 | 数据风险 |
|---|---|---|---|
| **A. 热重启** | 进程僵死、内存泄漏 | ~30s | 无 |
| **B. 灰度回滚** | 新版本引入 bug | ~5min | 无（取决于回滚点） |
| **C. 主从切换** | DB 主库硬件故障 | ~3min | 极小（半同步复制） |
| **D. 影子库恢复** | 误操作/数据损坏 | ~30min+ | RPO 取决于 dump 频率 |

### 5.2 恢复执行（按故障类型）

#### P0-A 后端进程僵死
```bash
# 1. 诊断：是否真僵死
jcmd <pid> Thread.print | head -10
# 2. 软杀：让 Spring Boot graceful shutdown
kill -TERM <pid>
sleep 15
# 3. 还活着就强杀
kill -9 <pid>
# 4. 拉新实例
nohup $JAVA_HOME/bin/java -jar ruoyi-admin/target/ruoyi-admin.jar \
  --spring.profiles.active=ipd-local,dev \
  --spring.config.additional-location=optional:classpath:./,optional:file:./.codex/ipd-dev/config/ \
  > /tmp/ruoyi-admin.log 2>&1 &
# 5. 验证：14s 内 ready
for i in {1..20}; do
  curl -fsS http://127.0.0.1:16039/actuator/health/readinessState && break
  sleep 1
done
```

#### P0-C DB 主库硬件故障
```bash
# 1. 确认主从状态
mysql --defaults-file=mysql-client.cnf -e "SHOW SLAVE STATUS\G"
# 2. 提升从库
mysql --defaults-file=mysql-client.cnf -e "STOP SLAVE; RESET SLAVE ALL;"
mysql --defaults-file=mysql-client.cnf -e "SET GLOBAL read_only=0;"
# 3. 应用层刷新连接池（等连接自然过期或重启）
# 4. 验证业务
curl -fsS -X POST http://127.0.0.1:16039/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<从ENV>"}'
```

#### P1-A 审计 hash 链断裂
```bash
# 1. 拉最近 N 个 audit log
mysql --defaults-file=mysql-client.cnf -e \
  "SELECT id, chain_id, prev_hash, row_hash FROM audit_log ORDER BY id DESC LIMIT 100"
# 2. 重算比对（AuditHashChain.verifyChain）
java -cp ruoyi-admin/target/ruoyi-admin.jar org.ruoyi.ipd.audit.AuditChainVerifier \
  --chain-id=<id> --from-id=<start> --to-id=<end>
# 3. 若真断裂，触发 P1 告警 + 切只读 + 联系 owner 决策
# 4. 若只是顺序错位（并发写入），提交顺序补偿脚本
```

## 六、验证层（恢复 → 是否真活）

### 6.1 五项硬验证（缺一不可）

| # | 验证项 | 通过判据 |
|---|---|---|
| 1 | 进程健康 | `/actuator/health/livenessState` == UP |
| 2 | DB 读写 | `INSERT+SELECT` 业务表 OK |
| 3 | Redis 连通 | `SET+GET` 测试 key OK |
| 4 | 审计链 | 新写入的 hash 与 head_value 对齐 |
| 5 | 业务接口 | 登录 + 一个核心接口 200 |

### 6.2 验证脚本（`scripts/ops/post-recovery-verify.sh`）

```bash
#!/bin/bash
# 跑在恢复后立即执行，5 项验证全绿才算恢复完成
set -e

BASE_URL="${BASE_URL:-http://127.0.0.1:16039}"
PASS=0; FAIL=0

check() {
    local name="$1"; local cmd="$2"
    if eval "$cmd" >/dev/null 2>&1; then
        echo "✅ $name"; PASS=$((PASS+1))
    else
        echo "❌ $name"; FAIL=$((FAIL+1))
    fi
}

check "liveness"      "curl -fsS $BASE_URL/actuator/health/livenessState | grep -q UP"
check "readiness"     "curl -fsS $BASE_URL/actuator/health/readinessState | grep -q UP"
check "db-write"      "mysql ... -e 'INSERT INTO recovery_warnings(level,msg) VALUES(\"INFO\",\"post-recovery\")'"
check "redis-setget"  "redis-cli ... SET test:post:$(date +%s) OK | GET ..."
check "audit-head"    "mysql ... -e 'SELECT head_value FROM audit_chain_head LIMIT 1' | grep -E '^[0-9a-f]{64}$'"
check "login"         "curl -fsS $BASE_URL/api/v1/auth/login ..."

echo "---"; echo "PASS=$PASS FAIL=$FAIL"
exit $((FAIL > 0 ? 1 : 0))
```

## 八、Dry-Run 脚本（`scripts/ops/recovery-drill.sh`）

### 8.1 设计原则

- **不真实破坏**：所有破坏动作走 mock/stub/隔离文件，写到 `/tmp/drill-<ts>/` 临时目录
- **可重复**：每次跑结果一致，CI 可纳入冒烟
- **可验证**：每个演练步骤产生可读的 pass/fail 行 + 时间戳
- **可观测**：与 /actuator/prometheus 联动（演练期间指标变化截图）

### 8.2 演练场景（8 个）

| 场景 | 模拟方式 | 验证点 |
|---|---|---|
| S1 后端进程僵死 | `kill -STOP <pid>` 60s 后 -CONT | readinessState 在 STOP 期间 DOWN，CONT 后 UP |
| S2 DB 慢查询 | 跑一个 30s 的 SELECT SLEEP(30) | p95 http_server_requests_seconds 上升 |
| S3 Redis 不可达 | `iptables` 拒 6379 端口 30s（需 sudo） | redis_lettuce 连接失败事件触发 |
| S4 磁盘满 | `dd if=/dev/zero of=/tmp/drill-fake-full bs=1M count=...` 占位 | disk_free_bytes 趋零告警 |
| S5 审计链顺序错位 | mock 注入：写入 row N，N-1 未提交 | AuditChainVerifier 检测告警 |
| S6 配置文件错误 | 临时改 application.yml 加非法 property | 启动失败日志含具体原因 |
| S7 双实例端口冲突 | 启第二个 jar 用同 16039 | BindException + JVM 退出码 |
| S8 网络分区 | `tc qdisc add dev lo root netem loss 100%` 30s | 业务接口 5xx + 自动恢复 |

### 8.3 脚本输出格式

```text
[2026-09-22 03:50:01] [INFO ] Drill start: S1 backend frozen
[2026-09-22 03:50:02] [CHECK] readinessState probe OK (200, UP)
[2026-09-22 03:50:03] [ACT  ] kill -STOP 57677 (pid 57677)
[2026-09-22 03:50:05] [CHECK] readinessState probe FAIL (DOWN) ✅ expected
[2026-09-22 03:50:05] [ACT  ] kill -CONT 57677
[2026-09-22 03:50:08] [CHECK] readinessState probe OK (UP) ✅ recovered
[2026-09-22 03:50:08] [PASS ] S1 backend frozen (RTO=3s, RPO=0)
[2026-09-22 03:50:08] [INFO ] Drill summary: 1/1 passed, 0 failed
```

### 8.4 安全网

- 演练开始前快照进程列表/PID，演练结束后强制 `kill -CONT` + 校验状态复原
- 任何 mock 数据写到 `/tmp/drill-<ts>/`，演练结束自动 `rm -rf`
- iptables/tc 命令需 root，检测到非 root 时降级为「模拟」标记（只打日志不真实改网络）
