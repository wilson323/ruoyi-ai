# 审批—续跑—清理共同根因

裁决：未闭环。最早窗口是审批事务提交与SDK真正启动之间。消费事务只落回答摘要、epoch，原官方确认与子恢复消息仍在内存。调度失败会写FAILED；进入Kernel前默认清理可能删除检查点。进程在两步之间退出时，摘要不能重建批准/拒绝。防重放是有效安全门，却不是可靠恢复协议。

原真实隔离Executor日志scheduleReject=FAILED/cleanup1/kernel0；当前源码仍有同链。Kernel已保护审批恢复的检查点，但FAILED后重试只回读已消费状态，无同回答再派发路径。子dispatch claim在SDK调用前，注释要求持久恢复而当前无对应闭包。

最小根修应在原运行私有事件持久化归一化回答与精确审批身份，区分接收/派发开始/原调用完成，保留新epoch恢复。确定未派发可审计地回到可恢复等待；已派发未知必须核原检查点和效果凭据，不盲重发。清理按是否仍有未解决派发判断，不能把已写FAILED等同可删恢复证据。不另建表/API轨。

具体源码哈希、跨层路径、修复合同与反例在同名JSON。数据库冷恢复与已加载实际旅程仍待验证。
