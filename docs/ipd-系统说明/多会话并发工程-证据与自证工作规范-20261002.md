# 多会话并发工程 · 证据与自证工作规范

- 适用：ruoyi-ai 及任何**多会话共享工作树 + 锁定第三方依赖**的仓库
- 来源：2026-10-02 一轮 AgentScope 单轨审计与 plan_exit HITL 收口中**真实踩到的 6 次失误**的提炼
- 性质：**流程规范**，不含项目业务知识；每条都附当晚的实证案例，可对照复核
- 配套：`AgentScope能力启用裁决-三方权威冲突与ADR-0077失实声明更正-20261002.md`（§1.8 自我反思记录）

> **一句话总纲**：**绿色的报告、绿色的测试、绿色的门禁，都只证明「它存在」，不证明「它对」也不证明「它还有效」。**
> 本规范的全部内容，都是把「存在」升级为「对」和「仍有效」的具体手段。

## 一、第三方 API 事实：只认锁定 JAR，不认源码镜像

### 规则

任何关于**依赖库 API 方法名、字段默认值、开关语义、调用顺序**的主张，一律以 `javap` 对**本仓实际锁定版本的 JAR** 实测为准。

```bash
# 本仓实例：AgentScope 2.0.3
CORE=~/.m2/repository/io/agentscope/agentscope-core/2.0.3/agentscope-core-2.0.3.jar
HARNESS=~/.m2/repository/io/agentscope/agentscope-harness/2.0.3/agentscope-harness-2.0.3.jar

# 公开面（方法签名 + 字段名）
javap -classpath "$HARNESS" 'io.agentscope.harness.agent.HarnessAgent$Builder'

# 默认值（构造器 iconst_*/aconst_null 与 putfield 配对）——比字段声明可靠
javap -p -c -classpath "$HARNESS" 'io.agentscope.harness.agent.memory.MemoryConfig$Builder'

# 字符串常量（提示词、路径、键名）
javap -p -constants -classpath "$HARNESS" io.agentscope.harness.agent.memory.MemoryConsolidator
```

**源码镜像只能作「设计意图参考」**，且引用时必须标注「需回查 JAR」。

### 当晚两次镜像污染（均被 `javap` 推翻）

| # | 污染主张 | 复核结果 | 若采信的后果 |
|---|---|---|---|
| 1 | 「`disableWebTools()` 是 2.0.3 官方关闭开关」 | **该方法在 2.0.3 JAR 中根本不存在** | 会为门禁设计一个不存在的检查项 |
| 2 | 「`.asyncToolTimeout(30s)` 是空操作」 | **反了**。2.0.3 `build()` 有 `messageBus==null && filesystem!=null` → 自建 `WorkspaceMessageBus` 的回退；本仓设了 `filesystem`，故 30 秒**确实生效** | 会产出一条「删掉这个无效配置」的错误改动 |

**根因**：`/Users/mac/Documents/agentscope-java` 实为 `2.0.4-SNAPSHOT`（`pom.xml:30` `<revision>`，HEAD 领先一个开发周期），本仓锁 `2.0.3`。**子智能体读镜像后自述「对照 v2.0.3 源码字节」——这句自述本身就是假的。**

### 扩展到子智能体

给智能体的任务书里**必须写死**：「API 事实只用 `javap` 对锁定 JAR 实证，禁止用源码镜像」。否则它会把镜像结论当成锁定版事实转述给你。

## 二、审计结论必须带时效三元组

### 规则

任何「**X 为 0 命中 / X 不存在 / X 未启用**」类结论，**必须附**：

```
观测时刻（HH:MM:SS） + git HEAD（短 sha） + 近 N 分钟内被修改的文件清单
```

**没有这三样的结论，一律视为过期，不得直接用于决策。**

### 当晚案例（最危险的一次）

21:39 的智能体报「全仓 `disable*()` = 0」，与我 14:36 的观测（「7 个 disable」）直接矛盾。核查发现：

| 时刻 | 事实 |
|---|---|
| 14:36 | 我观测到 3 个装配点共 7 个 `disable*()` |
| 14:58 / 15:09 / 21:04 | 兄弟会话**分批**删除了它们 |
| 14:36 → 21:39 | **我持续播报旧快照近 2 小时，一次都没重采基线** |

**为什么这次最危险**：结论是**肯定语气 + 精确 `file:line` + 字节码佐证**，读起来与一份刚做的报告毫无区别。**它不产生任何「我该怀疑一下」的信号。**

> **证据的格式会伪装证据的时效。** 一份带行号的报告如果不带时间戳，它传递的是「我刚查过」这个错觉。

### 落地做法

```bash
date "+现在: %H:%M:%S"
git rev-parse --short HEAD
find <范围> -name "*.java" -mmin -20 2>/dev/null | head   # 近 20 分钟谁在动
stat -f "%Sm  %N" <目标文件>                                # 逐个关键文件 mtime
```

**引用自己几小时前的观测前，先跑一遍这三行。**

## 三、变异自证：绿色的测试在被弄坏之前什么都不是

### 规则

新增/修改测试后，**必须**做一次变异验证：故意把被测逻辑改坏，确认测试变红。**只跑通不算数。**

```bash
# 1) 记录改前指纹
shasum -a 256 <主源文件> | cut -c1-16
cp <主源文件> /tmp/xxx.bak

# 2) 注入变异（必须保证【仍可编译】——编译失败不算验证）
python3 -c "...替换语义但保持语法有效..."

# 3) 跑测试，确认它真的红了
mvn -o -pl <module> -Dtest=<Test> test | grep -E "Tests run:|<<< FAILURE|BUILD"

# 4) 恢复并确认指纹一致
cp /tmp/xxx.bak <主源文件>
shasum -a 256 <主源文件> | cut -c1-16
```

### 当晚三次「变异没生效」

| # | 变异注入 | 实际发生了什么 | 教训 |
|---|---|---|---|
| 1 | 正则替换 | **正则没匹配上** → 跑的是未变异代码 → 4/4 全绿 | 注入后**必须回读**确认变异真的进去了 |
| 2 | 按行删除 6 行 | 多吃了 `return builder.build();` → **编译错误，测试根本没跑** | 删除类变异先数准行；`BUILD FAILURE` ≠ 测试变红 |
| 3 | ✅ 改 `askRule`→`allowRule`（保编译） | 4/4 全红，错误信息精确 | — |

> **判据**：只有「**测试跑了且断言失败**」才算变异成功。`BUILD FAILURE` 可能是编译错，必须看 `Tests run: N, Failures: M`。

### 当晚还有一次「测试本身是废的」

第一次写并发测试，断言是：

```java
assertEquals(writers, succeeded.get() + conflicted.get());   // 恒真式
assertTrue(succeeded.get() >= 1);                            // 近乎必然
```

每个写者不是成功就是抛异常，等式**永远成立**。变异后测试仍全绿 → 判定测试无效。

**改法**：用**确定性竞速注入**代替概率性并发——让 fake store 在 `getVersioned` 取出基线之后立刻执行一次竞对写入，使 CAS 失败条件可复现。

> **判据**：写完并发测试先问「**这个断言在缺陷态下会不会失败**」。想不出来，就是恒真式。

## 四、校验失败时，先怀疑校验器

### 规则

**任何「验证未通过」的结果，默认假设是「验证方法错了」，而不是「被验证物错了」**——尤其当被验证物的其它证据（时间戳、文件大小、相邻指标）都指向相反结论时。

### 当晚三次误报

| # | 报告 | 真因 | 正确做法 |
|---|---|---|---|
| 1 | 「plan_exit 修复不在运行产物」 | `unzip` 模式 `ruoyi-ipd-*.jar` 与查找模式 `ruoyi-ipd*.jar` 不匹配，**解包静默失败**，后续 grep 空 | 校验脚本**打印错误 + 退出码**，不静默 |
| 2 | 同上又发生一次 | 同类 | 同上 |

**加固写法**：

```bash
T=$(mktemp -d)
unzip -o -q "$JAR" 'BOOT-INF/lib/xxx-*.jar' -d "$T" 2>&1 | head -3
echo "解包退出码: $?"                    # ← 必须看
find "$T" -type f -name "*.jar"          # ← 打印实际产出，确认非空
LJ=$(find "$T" -type f -name "xxx*.jar" | head -1)
echo "LJ=[$LJ]"                          # ← 确认非空再往下
```

## 五、编辑他人文件：assert-first，改完回读

### 规则

编辑一个**可能被并发写入**的文件时：

1. **先 `git diff` / `shasum` 记录改前状态**
2. **用带 `assert` 的脚本做替换**（锚点不命中就中止，不写盘）
3. **改后立刻回读 diff 确认**

```python
old = '''...原文锚点...'''
assert old in s, "锚点未命中——文件已被他人改动，放弃本次编辑"
open(p, 'w').write(s.replace(old, new))
```

### 当晚案例

准备把 `ProjectAgentOfficialPermissions` 的字面量换成常量，脚本 `assert` 中止并打印「锚点未命中」。回读 diff 发现：**兄弟会话在我跑测试的那几分钟里已经自己做了这个清理**（且做得更完整，还补了注释）。

改前改后 sha 一致（`f4c5c77c7c8dd6b7`），**没有写入**。

> 若当时用 `sed` 而非 `assert first`，就会在一个已经改好的文件上再改一遍——可能把兄弟的注释覆盖掉。
> 当晚还有一次同样的正确中止：`CodingServiceImpl` 的锚点在改写过程中被兄弟改动，脚本中止未写。

### 并发写守卫

本仓有 OPS-09 钩子拦截对兄弟在途文件的写入。绕道是项目既定流程：**Python 改 + `docs/ipd-系统说明/log.md` 登记**，不要试图绕过钩子本身。

## 六、让路：别人在写就别写

### 规则

**动某个文件前，先确认它不在别人的飞行中**：

```bash
find <模块> -name "*.java" -mmin -5 2>/dev/null   # 近 5 分钟有写入 = 有人在改
stat -f "%Sm  %N" <目标文件>
```

- **有写入** → 只读核实，产出「该改什么」的清单，改动交给持有者
- **无写入（≥5 分钟静止）** → 才是写窗口

**同时只读、串行写**是本仓的既定分工：多智能体可并行派**只读核实流**，**Java 与计划文件由主协调者串行集成**。

### 当晚案例

我全程因并发让路，把实施推迟了数小时；期间兄弟会话完成了 disable 清理、文档对账、以及与我**互补的第 5 个测试**（行为版「拒绝后 plan_write 仍可修订」——正是我中途放弃的那条）。

> **让路的代价是延迟，收益是不互相覆盖。** 而且兄弟常会补上你放弃的东西——他们的方案往往建立在你没看到的另一组证据上。

## 七、文档结论会过期：加效力声明，不静默改

### 规则

发现既有文档/报告的前提失效时：

- **不要静默改掉**（下一个执行者会照着过时内容去「修复」一个不存在的缺陷）
- **在文首加「效力声明」**，逐节标注：哪些仍成立、哪些已失效、失效原因与证据
- 保留历史裁决作为**决策留痕**，加时间戳校准头，不删除

### 当晚案例

裁决稿基于「7 个 disable」写了 §1.1–§1.3 与 §1.7 步骤 1–2。21:39 前提失效后，在文首加了效力声明：

```
> §1.1–§1.3、§1.7 步骤 1–2 的核心前提已失效。
> 21:39 实测：全仓 disable*() 调用 = 0。
> 仍然有效：§1.4、§1.5、§1.6、§1.7 步骤 3–4、§1.8、§2、§3 全部
```

**其中 §1.6（官方三开关的字节码分析）仍有效**——那是对**官方 API** 的分析，与本仓是否调用无关。**区分「结论内容」与「结论前提」**是这一步的关键。

## 八、并行环境是有半衰期的

### 规则

**「服务在跑」与「服务跑的是你要验的代码」是两个必须分别验证的命题。**

```bash
# 1. 谁在监听
lsof -nP -iTCP:<port> -sTCP:LISTEN
# 2. 启动时间 vs 产物构建时间
ps -o lstart= -p <PID>
# 3. 实际运行的 jar（不是 target/ 那个，可能是别的）
ps -o command= -p <PID> | tr ' ' '\n' | grep -E '\.jar$'
# 4. 那个 jar 里到底有没有你要的改动
unzip -p "$JAR" '<内嵌模块>.jar' 2>/dev/null | ...
```

### 当晚两个层级都踩了

1. **环境层**：21:35 探测后端未起；21:36 有人起了它。一份 90 秒前的环境报告已过期。
2. **产物层**：仓库里有**三个不同的 jar**（`target/` 的、`.codex/.../backups/` 的、以及 fat jar 内嵌的模块 jar）。智能体报了 `target/` 那个的 mtime，而实际跑的是 `backups/` 那个——**差了 4 分钟，且都不含修复**。

> 若只看「16039 起来了、health 有响应」，会得出「环境就绪可验收」——然后跑出一个**必然失败**的结果，而失败原因（后端是旧代码）离表面现象（SSE 无中断）很远。
>
> `health=401` 不是故障，是 actuator 受保护的**正确**行为；**前端 200 也可能掩盖后端已死**（它的上游指向死端口）。

## 附：2026-10-07 新增三条硬规矩（当天各犯两次以上，写成条款）

这三条不是感想，是当天反复犯、且**每次都伪装成「我查过了」**的错误形态。

### 规矩一 · 验证查询行为必须断言查询条件，不能断言 mock 返回值

给 mapper 桩返回值时，「服务传了什么条件去查」与「数据库回了什么行」是**两件毫无关系的事**。
桩一律按你给的返回——把生产代码里整条 `.in(role, ...)` / `.eq(status, ...)` 删掉，
断言「返回 0」的测试照样绿。

当天两次踩坑：① `GateEngine` 的在途去重（mock `selectCount` 返回 1/0，把谓词改成 `isNull` 后 25 测全绿）；
② 津贴按 role 收窄（mock 返回带 MEMBER 行、期望算出 0，删掉过滤照样绿）。

**正确写法**：捕获真实 wrapper 再断言条件本身。

    var captor = ArgumentCaptor.forClass(LambdaQueryWrapper.class);
    verify(mapper).selectList(captor.capture());
    AbstractWrapper<?,?,?> w = captor.getValue();
    w.getSqlSegment();                                   // 不渲染则参数表恒空
    assertThat(w.getSqlSegment()).contains("role");
    assertThat(w.getParamNameValuePairs().values()).contains("MARKET_PM","RD_PM");

配套：`eq`/`in` 把值包在**惰性 Supplier** 里，不调 `getSqlSegment()` 就永远读不到。

### 规矩二 · 动手前先读真实结构，禁止凭想象写

当天连续 4 次编译失败，全部源于**凭印象写了不存在的东西**：`service`（实为 `projectService`）、
`memberMapper`（实为 `projectMemberMapper`）、`memberOf(...)`（实为 `bound(...)`）、
`ReflectionUtils` 用法臆造。

**动手顺序**：写一个自己没 grep 过的符号之前，先查真实签名；改大段代码之前先读邻近真实代码。
`test_failure` 信号出现时先怀疑「我写的名字不存在」，而不是「环境有问题」。

### 规矩三 · 边界问题先查需求原文，查到了就不许问 owner

owner 原话：**「不是也提供给你原需求吗」**。当天至少三次本该自己查却甩给了 owner：
① 「谁该领津贴」——主 Prompt v3:526/697/941 三处明写发给双PM，从未翻过；
② 「实时推送 403」——那是缺陷不是选择；
③ 「双PM 完不完整」——被问才去查，真有洞。

**判据**：需求原文能回答的自己查；只有不可逆操作（删库、迁数据、改钱的核心口径）才问。
**并且**：建了画像/权威图就拿它当判断依据，不要建完当摆设——当天清理时没用数据层画像，
连坏三次（删审计链锚点致全站登不进去、连带删验收账号、删产品线致建项目不可用），三次同一个病。

### 附：污染 vs 缺陷的区分（当天也判错过）

- **MEMBER 角色本身合法**（创建人自动回填），**问题是从没校验 + 被当成 PM 计钱**；
  「2 行脏数据」的说法不准确——那 2 行是合法成员行，只是计费口径错。
- **已落库污染为 0**：津贴台账 / 贡献度 / KPI / 项目分四表 `COUNT(*)` 全为 0，
  「超管被记 2000」只存在于计算路径，未进过库。**报「污染」前先 `COUNT(*)` 实证，
  不要从「计算路径错」推断「数据已坏」。**
