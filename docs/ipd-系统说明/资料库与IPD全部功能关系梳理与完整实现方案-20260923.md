## 一、系统性业务梳理分析

### 1.1 IPD 系统业务本质

IPD = Integrated Product Development，集成产品开发。这套系统的业务本质是：

- **六阶段流程**：概念 → 计划 → 开发 → 验证 → 发布 → 生命周期
- **多角色协同**：市场PM / 研发PM / 组长 / 超管 / 游客
- **多业务对象**：项目 / 需求 / 产品 / 招标 / 变更 / Gate / KPI / 激励 / 移交 / 审计 / 通知 / 资料库
- **全闭环**：从立项到结项，每个阶段有 Gate 评审、有 KPI 考核、有奖金分配、有文档交付、有审计留痕

### 1.2 资料库与 IPD 全部功能的关系矩阵（四级分类）

**第一级 · UI 代理层（1 个）**
- `IpdDocuments` 路由（`router/routes/modules/ipd.ts:225-229`）→ 复用平台知识库详情页
- 菜单叫"资料库"，后端是隔壁 ruoyi-chat 的 `knowledge_info / knowledge_attach / knowledge_fragment` 三表
- IPD 域只是借一个一级入口把它暴露给 PM

**第二级 · IPD 自带的"项目级知识库"（AI 文档 + RAG，2 个域）**
- `AiDocument`（项目草稿）：GENERATED → REVIEWED → ARCHIVED/REJECTED 四态，append-only 版本链，由 `parentVersionId` 自链（P1-10.1）
- `AiDocEmbedding`：审核通过即异步向量化入 RAG（`AiDocumentService.review()` 第 219 行调 `docEmbeddingService.embedAsync`），同 `embedModel` 同库单线程守护池
- 关联消费点只有一个：`AiGenerationService.generate()` 在生成 AI 表单前调 `retrieveContext(projectId, prompt)`，把同项目历史已审文档 top-3 片段注入 prompt（`AiGenerationService.java:128-132`）
- 另：`AiCopilotService` 注释里"未来接 RAG，必要时复用 retrieveContext 作为第三档上下文"——目前还没接，是预留口

**第三级 · 业务对象"挂文件"（2 类，用 OSS 不走 knowledge）**
- `Deliverable`（项目交付物，`domain/Deliverable.java`）：存 `ossId` → 平台 `sys_oss` 表（`OssFileEntity.java`），不挂 knowledge
- `Gate.materialsUrl / meetingMinutesUrl`：纯 URL 字符串字段，Gate 提交时强制非空，不引用任何知识库 ID
- 业务附件走 OSS 不走 knowledge 的根源：OSS 是落地文件（PDF/Word/Excel），knowledge 是已切片已向量化已可检索的语料——两层职责不同，不能混

**第四级 · 与资料库完全无关（约 60 个 Controller / 60 多个 domain）**
- 覆盖 IPD 流程全部六阶段：项目/需求/招标/变更/Gate/产品/奖金池/KPI/激励/移交/人员/HR同步/审计/通知/工作台等等
- grep 二次复核 `org.ruoyi.(knowledge|chat.knowledge)` + `KnowledgeInfoService/Attach/FragmentService` 全 0 命中坐实
- 用户在资料库里看到的 PDF/Word，跟他跑项目时的 IPD 业务数据，是两条互不通的存储线

### 1.3 业务逻辑根源性关联（三个约束逼出来的设计）

**约束 A：多租户共享 knowledge 不能直接被 IPD 业务读**
- 平台 `knowledge_info` 是用户私有知识库——可能是 PM 个人草稿、未审核素材、企业内部公告
- AI 大模型生成业务表单时如果直接命中，会污染 IPD 输出
- 所以 IPD 域另起 `ai_doc_embeddings`，只装"已审核的 AI 文档"（GENERATED 不过审不进 RAG），用项目 ID 隔离检索
- 这是"`AiDocument` 为什么要有人工审核门槛"的根源，schema 注释 `domain/AiDocument.java:11-13` 把这个写死了

**约束 B：业务附件和知识库语料职责不同**
- Gate 评审材料、纪要要 URL 字符串（外链给评审人看文件）
- 交付物要 OSS（落地存储、可下载、可走删除审核）
- 知识库要"已切片已向量"（可检索）
- 三层数据各自有自己的存留策略，不能强合一张表

**约束 C：AI 平台那个 knowledge 是 ruoyi-chat 通用底座，IPD 是其上层的业务壳**
- IPD 不该去抢知识库——抢了就和 chat 模块强耦合
- 所以 IPD 走两条路复用：UI 层借菜单（`IpdDocuments` 路由代理），数据层自建项目级 RAG（`ai_doc_embeddings`）
- 这就是 `router/routes/modules/ipd.ts:220-223` 那段注释"IPD 资料库基于知识库管理后端对齐，与 AI 平台'知识管理'同一份数据"——对齐的是 UI 入口和数据语义，不是数据库表

### 2.2 实施计划

#### 阶段 1：RAG 真活触发

**任务**：人工 REVIEW 一篇 AI 文档触发 `embedAsync`（推荐方式，验证真活流程）。

**前置验证（2026-09-23 fresh）**：
- `ai_model_configs` 表无 `is_active=1` 的配置 → RAG 开关未配置，`embedAsync` 会静默跳过（`AiDocEmbeddingService.java:90-92`：`if (cfg == null) return;`）
- **需先配置 `AiModelConfig`**（`embedEndpoint/embedModel` 两键），否则 RAG 真活无法触发

**实施步骤**：
0. **配置 `AiModelConfig`**（INSERT 一行 `is_active=1` 的配置，`config_json` 含 `embedEndpoint/embedModel` 两键；参考 `AiModelConfig.fromJson` 的解析逻辑）
1. 现查 `ai_documents` 表 4 行数据，找一篇 `status='GENERATED'` 的文档（mysql 现查：`SELECT id, project_id, title, status FROM ai_documents WHERE status='GENERATED' LIMIT 1;`）
2. 调 `AiDocumentService.review(versionId, operatorId)` 触发审核（versionId = 上一步查到的 id，operatorId = 当前登录用户 ID）
3. 审核通过后，`AiDocumentService.review()` 第 219 行调 `docEmbeddingService.embedAsync(row)`
4. `embedAsync` 异步向量化（单线程守护池），写入 `ai_doc_embeddings` 表
5. 等待 5-10 秒（异步向量化需时间），mysql 现查 `ai_doc_embeddings` 行数 > 0
6. 若 10 秒后 `ai_doc_embeddings` 仍 0 行，检查后端日志 `[AI-STRAT-1] 向量化失败降级` 或 `[AI-STRAT-1] 向量化跳过（配置不可用）`

**备选方式**：若 `ai_documents` 表无 `status='GENERATED'` 的文档，则写测试数据（INSERT 一篇 `status='GENERATED'` 的文档，再走步骤 2-6）。

**验收标准**：
- `ai_doc_embeddings` 行数 > 0（mysql 现查）
- `AiGenerationService.generate()` 调 `retrieveContext()` 返回非 EMPTY

**风险**：低（纯数据操作）

**回滚**：`DELETE FROM ai_doc_embeddings WHERE doc_id = ?`

#### 阶段 3：retrieveContext 分 docType

**任务**：在 `retrieveContext` 入参加 `docType` 过滤。

**前置验证（2026-09-23 fresh）**：
- `SHOW INDEX FROM ai_doc_embeddings` 显示：有 `idx_emb_project(project_id, embed_model)` 和 `idx_emb_doc(doc_id)`，**无 `doc_type` 索引**
- **需先加索引** `CREATE INDEX idx_emb_doctype ON ai_doc_embeddings(doc_type);`，否则 `docType` 过滤会全表扫描，性能差

**实施步骤**：
0. **加索引**（DDL，需 owner apply 或测试库直接跑）：`CREATE INDEX idx_emb_doctype ON ai_doc_embeddings(doc_type);`
1. Read `AiDocEmbeddingService.java` 的 `retrieveContext` 方法（line 139-192）
2. 在入参加 `String docType` 参数（nullable，null 表示不过滤 docType，返回所有类型的片段）
3. 在 SQL 查询加 `eq(AiDocEmbedding::getDocType, docType)` 条件（docType 非 null 时；docType 为 null 时不加此条件，保持向后兼容）
4. 改 `AiGenerationService.generate()` 调用 `retrieveContext` 时传 `docType`（从 `AiGenerateReq.docType()` 获取）
5. 改 `AiCopilotService` 调用 `retrieveContext` 时传 `docType`（阶段 2 已接 RAG，此处传 null 表示不过滤，保持向后兼容；前端 UI 让用户选 docType 是后续任务）
6. 写单测验证 `retrieveContext` 返回结果只包含指定 `docType` 的片段（mock 数据：同一 projectId 下插入 docType='PRD' 和 docType='MRD' 各 2 条，验证传 docType='PRD' 时只返回 PRD 的 2 条）

**验收标准**：
- `retrieveContext` 返回结果只包含指定 `docType` 的片段（单测）
- `AiGenerationService` 和 `AiCopilotService` 调用 `retrieveContext` 时传 `docType`

**风险**：中（需改 `AiDocEmbeddingService` 代码）
