### W1 开工实测修正（2026-09-28 01:0x，接线前探清后的诚实重估）

- **W1-1（ai_agent_task 哨兵对账）已闭环，且不需新代码**：核实发现「事件→行→API 直达」链已被 R236 现有 6 类测试（共 67 用例，含 `ExecutorCoverageSentinelTest` 69 码棘轮到底）机制化覆盖，错峰单模块实跑全绿。按“少造轮子/避免双轨”不重写哨兵；O-5/S5 摘 PARTIAL（详审计报告 S5）。
- **W1-2（RAG 接线）重估：原估“薄接线 S”偏乐观，实为 M 且当前不可验证**。实测：`CustomVectorRetriever`（ruoyi-chat）**非 Spring bean**（`@RequiredArgsConstructor` 手工构造），需三入参：`KnowledgeRetrievalService` + **具体知识库的** `KnowledgeInfoVo`（vectorModel/embeddingModel/阈值/重排参）+ ruoyi-chat 的 `ChatModelVo`。因此接线前置：①必须先有一个**真实存在且已嵌入向量**的知识库（knowledge_info 行 + 向量库数据）；②需 scene→KB 映射决策（哪个场景挂哪个库，属产品/数据决策=D 级）；③依赖活向量库（Milvus/Qdrant）。而当前 HTTP/运行时层 **BLOCKED_ENVIRONMENT**（FE/BE/向量库全 DOWN）——写进去无法验证能跑=本仓明令禁止的假绿。**修正结论**：W1-2 不盲目对 1119 行核心服务写不可验证的 AI 行为代码；待 O-1 起环境 + 备一个活知识库后，再按“可验证增量”落地（注入缝已定位：`AiSuggestionService.java:225 composePrompt → :238 aiGateway.chat` 之间 prepend 检索上下文，try/catch 空串降级永不 500）。
- **W1-3（记忆接线）同理重估**：`PersistentChatMemoryStore` 需活模型 + 运行时表，同属 BLOCKED_ENVIRONMENT 不可验证类；接线点（AiGateway 挂 memory + sessionId 规则）已明确，待起环境后落地。
- **裁定**：W1 三项中只有 W1-1 在当前环境可闭环（已做）；W1-2/W1-3 本质需“活依赖 + 起环境”才可验证，已 O-1 阻塞。**不为了“推进”而在 BLOCKED_ENVIRONMENT 下写不可验证代码**（避免假绿）；待 owner 拍板是否先起 O-1 环境（+备知识库）再推 W1-2/W1-3。

## 8. 知识库管理与应用专章（owner 2026-09-28 两次追加：最佳实践结合 + 定稿件自动入库）

### 8.1 仓内底座盘点（结论：五层管线齐备，缺"IPD 事件触发"与"自动打标签"两环）
已存在、直接复用，不重写：
- **接入层**：`KnowledgeAttachController/ServiceImpl`（上传/状态机 KnowledgeAttachStatus）
- **解析层**：`knowledge/impl/split/` 五类分割器（Token/Markdown/Excel/Code + SplitterSupport）+ `DocumentSplitConfig`
- **图谱层**：`KnowledgeGraphInstance/Segment` 五件套（实体-关系-段落已有表与 service）——GraphRAG 底座已在
- **检索层**：`retriever/CustomVectorRetriever` + `VectorStoreStrategyFactory`（Milvus/Qdrant）+ aiflow `knowledgeRetrieval` 节点
- **嵌入层**：`service/embed/` 多 Provider（SiliconFlow 等）；可观测：`RagTracePayloadBuilder` + Embedding 监听器
- 治理同构：本仓 SSOT+log.md 惯例与最佳实践库 OKF 篇（index.md+type+会话尾 log.md）验证同一路数，无需另建格式。

### 8.2 定稿件自动入库主链路（核心新增需求，全部复用既有件，仅一个薄 Listener）

```text
定稿事件（产品上市/LIFECYCLE 归档/Gate APPROVED/文档审核通过）
  → IpdKnowledgeIngestListener（新建，≤150 行，订阅既有领域事件，同 AiExecReviewHook 的 triggerEvent 模式）
  → 自动打标签：复用 AiGateway 单次调用产出 {产品线, 文档类型, 阶段, 密级, 关联项目ID}
     标签白名单受控（仿 suggest 的 R2 双向白名单），低置信度→标 pending_review 不自动入正库（人审兑底，BR-AI-02 同构）
  → 既有管线：attach 登记 → splitter 分片 → embed → 向量库 + KnowledgeGraph 实体抽取（先检查抽取再建图，GraphRAG 篇原则）
  → 失败不阻断业务：入库异常只记事件重试表，主流程零影响（降级安全统一口径）
```

设计红线（取自最佳实践三篇，防翻车）：
1. **可追溯**（GraphRAG 法规篇）：每片段带 源文档ID+版本+页/段锚点，检索结果可回源文对账；禁"摘要顶替原文"。
2. **先抽取检查后建图**：实体抽取质量门（抽检样本过阈才开图检索），否则只做向量检索，图谱渐进启用。
3. **蚁群分工**（LLM-Wiki 篇）：Ingest/organize/prune 三角色异步分开（定稿入库=Ingest；定期归并/去重/清理过期=独立定时任务，复用 aiflow scheduler 范式），不堆在一个大 service。
4. **只入定稿**：状态机门限——仅「已审核/已归档/已上市」文档自动入；草稿/待审永不自动入（防知识污染，G-06）。

### 8.3 管理面最佳实践补强（应知应会清单，落 O-17 验收标准）
- 知识生命周期：新增 expires_at + 季度 prune 任务（源文档被新版替代→旧片段自动标 superseded 不再命中）；
- 双态检索卫生：测试/演示知识域与生产域物理分库（沿用 knowledge 状态机 + 密级标签过滤，避免 mock 知识污染真业务问答）；
- 度量：命中率/空检率/回源采纳率三指标入现有 KPI 看板数据源（不新建仪表体系）；
- 评估集：上线前用 20 条真实提问黄金集验收（检索 top-3 命中≥目标值），后续每改分片/embedding 参数跑同一集（配置变更必跑 evals 同构）。

波次归属：8.2 自动入库属 W2（事件接线+标签 LLM 调用，需 D2 一并拍板）；8.1/8.3 的接线与度量属 W1；图谱质量门与 prune 属 W3。
