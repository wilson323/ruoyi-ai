# SSE 端点同类异常全局反思（2026-09-11）

## 一句话

SSE 端点有 8 处「认证失败 / 业务异常走到非 SSE 响应」的问题——根因是 SSE 协议对 Content-Type 严苛（必须 text/event-stream），而 Spring MVC 的 `return null` / 全局 advice JSON 401/ 500 对 EventSource 都会触发「MIME type ... is not text/event-stream」并盲目重连。一次性修完 + 写门禁防复发。

## 问题样本（用户实际遇到的）

浏览器打开 /mcp/market 页面，控制台：

```
:15666/mcp/market:1 EventSource's response has a MIME type ("text/plain") that is not "text/event-stream". Aborting the connection.
:15666/mcp/market:1 EventSource's response has a MIME type ("text/plain") that is not "text/event-stream". Aborting the connection.
:15666/mcp/market:1 EventSource's response has a MIME type ("text/plain") that is not "text/event-stream". Aborting the connection.
message.ts:38 sse重连失败.
:15666/api/v1/auth/logout:1  Failed to load resource: the server responded with a status of 401
:15666/api/v1/auth/refresh:1  Failed to load resource: the server responded with a status of 401
```

## 全局同类异常扫描结果（一次性修完）

用「产出 text/event-stream 的 controller 方法」作为扫描对象，逐文件判定。共发现 8 处同类异常 + 1 处 IpdSseController 早修：

| 文件 | 端点 | 旧行为 | 修复 |
|------|------|--------|------|
| `IpdSseController` | GET `/api/v1/resource/sse` | return null（修复前的旧模式） | 早 commit 7992c386 改为 `ResponseEntity.status(401)` |
| `SseController`（ruoyi-common-sse） | GET `/resource/sse` | `if (!StpUtil.isLogin()) return null;` | 同步 401（模式 A） |
| `AiCopilotController` | GET `/api/v1/ai-copilot/chat/stream` | `requireInternal()` 抛异常 → advice JSON 401 | 入口 try-catch + `SseErrorEmitter.completeWithError`（模式 B） |
| `WorkflowController` | POST `/workflow/run` | `ThreadContext.getCurrentUser()` 抛异常无保护 | 入口 try-catch + 推 error 帧 |
| `ChatController` | POST `/chat/send` | 无鉴权注解，业务调用抛异常无保护 | 入口 try-catch + 推 error 帧 |
| `CodingController` | POST `/coding/chat` | `requireLegacyEnabled` 抛异常无保护 | 入口 try-catch + 推 error 帧 |
| `CodingHarnessController` | GET `/coding/harness/.../stream` | `owner()` 抛异常无保护 | 入口 try-catch + 推 error 帧 |
| `ShortDramaController` | 2 个 stream 端点 | `LoginHelper.getUserId()` 抛异常无保护 | 入口 try-catch + 推 error 帧 |

**统一抽出的工具类**：`ruoyi-common-sse/src/main/java/org/ruoyi/common/sse/core/SseErrorEmitter.java`——把「推 error 帧 + complete() + 处理 IOException/IllegalStateException」的样板沉淀到一个静态方法，6 个 controller 复用，避免每个控制器再写一遍 try-catch。

**两种合法修复模式**：

- 模式 A（同步拒绝）：方法返回 `ResponseEntity<SseEmitter>`，未鉴权直接 401——适用于「连接建立前」就要鉴权的场景（如 IpdSseController、SseController）
- 模式 B（异步错误帧）：先 `new SseEmitter` 返回，鉴权/业务异常在 try-catch 中通过 `SseErrorEmitter.completeWithError(emitter, code, msg, log)` 推 error 帧——适用于「连接建立后业务异步执行」的场景

两种都避免 EventSource 收到「200 + 空体」或 JSON 响应。

## 之前为什么没查出来（治理层根因）

按 R25 / R30+ 病根框架对照：

### 1. 集成测试覆盖盲区（病根①「改主代码后测试没跟上」）

- IpdSseController、SseController 在本轮修复前**完全没有对应测试**——之前新增 11 个 cca30905 文件时只覆盖了 ChatModelCredentialPolicy 等业务类，没碰 controller 响应形态
- 测试金字塔倒置：单元测试覆盖了「白名单逻辑」，但没覆盖「控制器响应形态契约」

### 2. 验证只看「正常路径」，没看「拒绝路径」（病根④「前后端契约无门禁」）

- 之前验「SSE 通了」是看后端 ACCEPTED 日志（正面验证），没看过 REJECTED 路径下浏览器实际收到什么（负向验证缺位）
- 后端 `Connection: keep-alive` + `Content-Length: 0` 是「看上去 200」的状态，但不是「看上去 SSE」——人眼看日志只会说「200 OK 好」，不会想到「200 OK 但缺 Content-Type」

### 3. EventSource 浏览器 API 语义错位是隐蔽知识

- EventSource 只接受 `200 + text/event-stream`；其他全部（200 + 空体、200 + JSON、401、403、500）触发 error 事件 + 「MIME type ... is not text/event-stream」报错（仅在 200 非 SSE 时）
- 这个差异在教科书级 SSE 文档里没有突出，是 EventSource API 的隐藏行为
- 开发者直觉认为「401 比 200 好」，但在 EventSource 场景里 401 同样触发 error——只是错误消息不同（MIME 错 vs HTTP 错）

### 4. 治理门禁无对应条款

- R25 9 大门禁覆盖死代码 / 跨仓契约 / i18n / 实体残废 / 文档死链 / 重复 SSOT——**没有一条针对 SSE 端点的响应形态契约**
- `ipd-frontend-drift-guard.cjs` 关注前端 API 漂移，不看后端 SSE 控制器
- `scripts/check_demo_default_off.sh` 等 R30+ 门禁关注配置 / SQL / 文档——SSE 控制器契约是空白

### 5. 「return null = 默认返回」是 Spring MVC 隐藏陷阱

- 用 `return null` 表达「拒绝/失败」是 Spring MVC 的反模式（Spring 不会自动转 401，会写 200 + 空体）
- 但很多开发者（包括我自己）写过这种代码——「没东西可返回就 null」是直觉，但 SSE 场景下暴露
- IDE / 静态检查工具不报警（编译通过、类型正确）

### 6. SSE 协议对错误响应无标准

- HTTP REST 有 RFC 7231 / RFC 7807（problem+json）定义 4xx/5xx 响应体
- SSE 协议（WHATWG）只规定了「正常流」的字段和格式，对**错误响应没有强制约定**——浏览器 EventSource 实现各自决定（Chromium 的策略就是「只看 200 + text/event-stream」）
- 各家框架（Spring / Express / FastAPI）对「SSE 端点鉴权失败」的默认行为不一致——Spring 走 advice JSON，Express 多返回 401

### 7. IPD / 非 IPD 模块的 advice 策略不统一

- IPD 模块的 `IpdServiceExceptionAdvice` 已被精心设计——L238-241 静默处理 `AsyncRequestNotUsableException`（SSE 客户端断开场景，注释明确说「2026-09-11 实测于 IpdSseController」），但**没有针对「SSE 端点 + 鉴权失败」的特化**——advice 不知道当前请求是 SSE 端点，仍然返回 JSON 401
- 非 IPD 模块（aiflow / chat）的 advice 走 RuoYi 平台默认 `GlobalExceptionHandler`，同样问题
- 「advice 层补一次 SSE 特化」是统一解决方案——但工程量与收益比不划算，本轮优先在 controller 层做兜底（6 处 try-catch）

### 8. 「日志 ACCEPTED = 链路 OK」是认知陷阱

- 后端日志 `status=ACCEPTED` 给人「正常」的直觉，但没区分「正常连接 1 次」与「同一连接持续 30 分钟」
- 用户浏览器 token 过期 = 「连接建立后中途失效」，日志只记录「请求被拒绝」——无法看出「连接已经建立了多少次 + 中断了多少次」

## 改进机制（防止复发）

### 1. 统一工具类：`SseErrorEmitter`（已建）

`ruoyi-common-sse/src/main/java/org/ruoyi/common/sse/core/SseErrorEmitter.java`：

```java
public static void completeWithError(SseEmitter emitter, String code, String message, Logger log)
```

- 吞 `IllegalStateException`（emitter 已 complete）与 `IOException`（客户端断开）
- 不依赖特定业务异常类（code/message 字符串传入）
- 6 个 SSE controller 直接调用，避免样板扩散

### 2. 门禁脚本：`scripts/check_sse_contract.sh`（已建）

按 R30+ 三层哨兵设计（自证能红）：

1. **输入层哨兵**：扫描 `produces.*MediaType.TEXT_EVENT_STREAM_VALUE` 数量 < 1 → fail（防 grep 路径错位）
2. **解析层哨兵**：每个 SSE controller 必须满足以下两种合法模式之一：
   - 模式 A：`grep -q "ResponseEntity<SseEmitter>"`（同步 401）
   - 模式 B：`grep -qE "SseErrorEmitter\.[a-zA-Z]+\("`（异步错误帧）
3. **负向验证**：临时撤掉 import + 调用 → 门禁必须红；恢复后必须绿

自检结果：
```
正向：✅ OK（6 个 SSE controller 全部已配保护）
负向：⛔ FAIL（撤掉 WorkflowController 的 import + 调用后）
恢复：✅ OK
```

注意：grep 必须精确到**调用语句**（`SseErrorEmitter.xxx(`），不能只看 import 声明——否则只注释调用行 import 仍在仍会假绿（自检第一版踩坑实录）。

### 3. 沉淀记忆（待 commit）

- 「SSE 端点响应契约：避免 return null / 避免依赖 advice JSON，统一走 SseErrorEmitter.completeWithError 或同步 401」
- 「EventSource 浏览器 API 隐藏行为：只接受 200 + text/event-stream，其他全部走 error 事件」
- 「控制器响应形态契约门禁：grep 调用语句而非 import，避开 sed 注释即绕过的假绿」
