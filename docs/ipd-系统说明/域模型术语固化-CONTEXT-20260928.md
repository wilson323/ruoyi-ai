## 结论一：Product ⇄ Project = 1:1 双向外键（名词面 / 动词面分离）

**代码现态取证**（均已实查确认 uk）：

- `docs/script/sql/schema/schema-snapshot-2026-09-09.sql`：
  `products` 表有列 `project_id`（注释「关联项目（1:1 唯一）」）+
  唯一键 `uk_products_project (project_id)`；
  `projects` 表有列 `product_id` + 唯一键 `uk_projects_product (product_id)`
  + `uk_projects_code (code)`——**两端各持对方外键且各建唯一索引**，
  即 1:1 双向。
- `ruoyi-modules/ruoyi-ipd/src/main/resources/db/migration/V001__project_product_unique.sql`：
  双向唯一键的幂等迁移脚本原态（先查 INFORMATION_SCHEMA.STATISTICS 再加）。
- `docs/script/sql/update/ipd_r215p1_projects_product_id_nullable_20260924.sql`：
  `projects.product_id` 放开 NOT NULL（待指派池/解绑场景），
  **uk_projects_product 保留**——可空不破坏 1:1 语义
  （MySQL 唯一索引允许多 NULL；解绑后两端指针 NULL 可重建，
  契约见该文件头注三条既有契约）。
- 六阶段执行：`projects.current_stage`
  取值 `CONCEPT|PLAN|DEV|VALID|LAUNCH|LIFECYCLE`（schema-snapshot），
  另有 `declared_stage`/`lifecycle_status`（ON_SALE|LIMITED|EOL|ARCHIVED）。
- 名词面资产属性在 `products`：`product_code`/`product_name`/`model_code`/
  `source`（ADMIN_IMPORT|PM_NEW|GUEST_OTHER）/`group_id`/
  `retired_at`/`retirement_locked`（退市只读锁）。

**术语表（固化两条）**：

1. **Product（产品）＝名词面＝资产目录**：产品是可持有、可展示、可退市
   的资产实体（编码、型号、归属产品组、退市锁），回答「我们有什么」。
2. **Project（项目）＝动词面＝六阶段执行**：项目是 CONCEPT→PLAN→DEV→
   VALID→LAUNCH→LIFECYCLE 的执行载体（立项指标、阶段推进、成员绑定、
   奖金与贡献核算挂点），回答「我们正在做哪一版」。
   **本项目不是经典 IPD 的「立项即新建产品」**：Product 与 Project 是
   同一事物的两面，1:1 绑定（立项即绑既有/新建 Product 指针，
   「其他/不确定」允许暂存待指派池 product_id=NULL）。

**一句话关系图**：
`ProductGroup → Product ⇄ Project → (ProjectMember ↔ Person)`
（Product 经 `products.group_id` 归组；Product⇄Project 经
`uk_products_project`/`uk_projects_product` 双向 1:1；
Project 经 `project_members.project_id/person_id` 绑双 PM 人员。）
## 结论二：「工作空间」一词双指问题（必须消歧）

**现象**：产品内「工作空间」一词同时指向两个不同东西——
①Product 资产聚合页（看产品全景：资料/需求/里程碑/退市态），
②Person 任务入口（工作台：我的待办、next-step、AI 建议汇聚）。
两页数据主体不同（资产 vs 人）、聚合逻辑不同（§结论一的 nouns vs verbs），
混称会导致需求、文档、代码命名三处漂移。

**建议规范词（本篇推荐口径）**：

| 规范词 | 固定指向 | 数据主体 | 知识库聚合（接 KB 篇 §5） |
|--------|----------|----------|---------------------------|
| **产品空间**（=**工作空间**，同物异名） | Product 资产聚合页（ProductWorkspace） | 名词面资产目录 | GROUP + PROJECT 作用域库 |
| **工作台** | Person 任务入口 | 动词面人的待办 | PERSON + AGENT 库（+ 上下文项目库） |

- 禁用组合：不再用「工作空间」指代工作台（Person 任务入口）；历史文案中出现的
  「工作空间」应在触碰该文件时顺手按下述裁决改判（不做集中批量重写，
  避免与兄弟会话撞车）。
- **规范词最终裁决（owner 2026-09-28 拍板，升级为权威条目）**：
  **「产品空间」即「工作空间」**——同物异名，统一指向 ProductWorkspace
  （`GET /api/v1/products/{id}/workspace` 聚合：product / projects / demands / metrics）；
  **不同产品空间对应不同的工作空间内容与数据范围**（`projects.product_id`、
  `requirements.product_id` 单列等值过滤，E2 回核证据
  `ProductWorkspaceController.java:54,57`，metrics 全部派生自已过滤集合）。
  「工作台」固定为 Person 任务入口，支持选择不同产品空间后实时加载该空间内容
  （首个项目阶段进度 + 空间内待办快捷入口，前端 2026-09-28 落地）。
  改判口径：历史文案「工作空间」指产品聚合页 → 产品空间；指个人任务页 → 工作台；
  联动 `docs/ipd-系统说明/naming-convention.md` 由触碰该文件时顺手升级。

**一句话关系图**（同结论一骨架，标注两入口挂载位；2026-09-28 裁决后口径）：
`ProductGroup → Product〔产品空间＝工作空间，名词面入口〕 ⇄ Project〔工作台任务=动词面执行〕 → (ProjectMember ↔ Person〔工作台=人入口〕)`

## 结论三：数字员工目标态（agent_info → DigitalEmployee）

**现态病根取证**：`docs/script/sql/ruoyi-ai.sql` 的 `agent_info` DDL
**无任何归属字段**——只有 `tenant_id`、`knowledge_ids`（JSON 数组，
多对多授权线索）、`model_id`/`mcp_tool_ids`/`skill_names` 与审计列。
数字员工既不挂在人下也不挂在项目下 ⇒ 检索隔离只能靠「授权清单枚举」
打补丁，是四维隔离（group/project/person/agent）的**病根**：
agent 维存在，但 agent→person、agent→project 两条边缺失。

**目标态 DigitalEmployee**（引用 Part A 草案）：
`docs/script/sql/update/kb-partA-ddl-draft-20260928.sql` 为 `agent_info`
补 `owner_person_id`（谁的员工，问责主体）+ `project_id`（哪个项目的员工，
任务归属）两条边，另补 `sensitivity`（员工可处理敏感级上限）；
与 `knowledge_info` 的新增归属键**同构**（同一套四维语义，人和员工
在隔离模型里同级）。任务级先例：
`docs/script/sql/update/20260926-ai-agent-tasks.sql` 的
`ai_agent_tasks.project_id NOT NULL`——数字员工的每次执行已经强制挂项目，
但员工本体没挂，目标态把本体补齐。
`knowledge_ids` 保留为「显式授权」而非唯一归属线索（详见 KB 篇 §5）。

**一句话关系图**（全链合拢）：
`ProductGroup → Product ⇄ Project → (ProjectMember ↔ Person)`，
`数字员工 AiAgentTask 经 ai_agent_tasks.project_id 挂 Project；
agent_info 本体经 Part A 补 owner_person_id（→Person）与 project_id
（→Project）两条边，DigitalEmployee = Agent + 两条归属边 + 敏感级上限`
