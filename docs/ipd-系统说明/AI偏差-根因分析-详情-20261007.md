## 二、证据（每条含实测口径）

### 2.1 纠错是常态事件，不是例外

| 读数 | 口径 | 数值 |
|---|---|---|
| 自我纠错登记条数 | `grep -E '推翻\|误读\|证伪\|判断错\|纠正' docs/ipd-系统说明/log.md \| wc -l` | **129 条** |
| 沉淀教训条数 | `memory/*.md`（排除 MEMORY.md） | 67 条 |

**比例 ≈ 2 : 1** —— 每沉淀 1 条记忆，就发生 2 次自我纠错。纠错频率远高于沉淀频率，这就是「为什么这个项目反复需要重新梳理」的量化答案。

### 2.2 「反复学」是采样偏差造成的错觉

读 `memory/` 全部条目的 `originSessionId` 字段：**11 条核心复发证据中，`44d94d0e-257a-404b-9bf9-97f525c37d3b` 一个会话贡献 5 条**。

该会话是 2026-10-03 的《全局项目规范漂移》，43MB / 363 问。

> 记忆库看起来有 67 条独立教训，实际独立教训数远小于此——大部分是少数几个高压会话的重复采样。

### 2.3 纪律当天写、当天又犯（决定性证据）

- 《结论纪律》四条硬动作写入 CLAUDE.md：**2026-10-03**（commit `906da8c4` 那批）
- 同期 `tool-parameters-must-be-verified-not-assumed.md` 记：「**2026-10-03 单会话内同类错误 7 次**」
- 同期 `self-written-parser-needs-known-case-validation.md` 记：「**同一件事连错三次**」

**结论：写纪律这个动作本身，对触发它的那类任务没有约束力。**

### 2.4 偏差随「单会话连续推理轮数」增长，与并发度无关

**这一条推翻了我自己的初始假设，先记留痕。**

初始假设：9 月密集复发（30 篇 / 4 天）是因为多智能体并发。实测后**不成立**：

| 日期 | 会话数 | 提问数 | 其中子智能体会话 | 提问/会话 |
|---|---|---|---|---|
| 09-07 | 96 | 506 | 89 | 5.3 |
| 09-08 | 11 | 80 | 8 | 7.3 |
| 10-02 | 5 | 46 | 4 | 9.2 |
| 10-03 | 20 | 185 | 13 | 9.3 |
| **10-04** | **4** | **410** | 2 | **102.5** |
| 10-05 | 1 | 42 | 0 | 42.0 |

09-07 看着热闹（96 会话）但 89 个是子智能体、每个都浅；10-04 只有 4 个会话却密度 102.5 问/会话，是 09-07 的 **19 倍**，而 10-04 正是复发最集中的一天之一。

**修正后的结论：偏差的驱动变量是「单会话内连续推理性判断的轮数」，不是并发度。** 长会话里，纪律条文会被上下文稀释，而「顺手读个数」的成本优势随轮数累积而放大。

### 2.5 治理覆盖面错位（最严重的发现）

实测 `.claude/settings.json`：

- 挂载 **10 个 hook 事件、19 条钩子**
- `PreToolUse` 7 组 / `PostToolUse` 9 组 / `SessionStart` 4 组 / `Stop` 3 组 / `PreCompact` 2 组 / `UserPromptSubmit`、`SessionEnd`、`SubagentStart`、`SubagentStop`、`Notification` 各 1 组
- `PostToolUse` 的 matcher 只有 `Write|Edit|MultiEdit`、`Bash`、`Write|Edit` 等，**全部是「写入动作」**

**没有一条钩子挂在「产出结论」上。**

即：本仓所有治理防的是「别把坏东西写进仓库」，而最致命的偏差是**把一个错的数字说给 owner 听**——这类错误可以一个字都不写进任何文件，它发生在回答里，现有治理对它完全失明。

补充证据：唯一的「收尾自检」类钩子（PostToolUse 组 9）内容是打印一句提醒然后 `exit 0`：

```
[Layer 1 提醒] 变更已落盘。请确认：① 证据已写入 plan.md ② 文档已同步 ③ 本单元已验证
```

**让 AI 读一句话去自觉——这正是 R1（代价不对称）的完美例证。**

### 2.6 本仓最精确的一句自我诊断

`docs/ipd-系统说明/log.md` 原文：

> 「差一点用没读懂的尺子推翻一份做对的报告。」

同文件另有：「推翻漂移审计的 P0-01 / P0-02：端口链与 fail-fast 在 HEAD 上均已修复」。

**即：偏差不只产生错结论，还曾差点把一份正确报告毁掉；而审计报告携带的 P0 结论若不复核，会导致去修不存在的问题。**

## 三、根除方案

判据只有一条：**它降低验证成本，还是只提高违规成本？** 只提高违规成本的方案，按 R1 一律无效。

### 方案 A（P0）：让「猜的读数」在形式上拿不出可交付形态

现状：模型可以只报一个数字。
改法：**任何出现在回复里的数字，必须同时携带仪器自检输出。**

- 计数 → 附「扫描范围 + 排除项 + 总数」三件套
- 查询 → 附「顶层键名 + 数组长度 + 首条样本」
- 状态 → 附「命令原文 + 退出码」

**验收标准**：把自检输出删掉，数字应当无法单独引用。做不到就是没改到。

**为什么有效**：它把验证从「AI 自觉多跑一次工具」变成「不跑就没有交付物」——**降低交付成本，而不是提高违规成本**。这是唯一能穿过 R1 的做法。

### 方案 B（P0）：为 Stop 事件加「数字出口检查」

现状：`Stop` 有 3 组钩子，但无一条检查结论中的数字。
改法：Stop 钩子拦截最终回复，若回复中出现「共 N 个 / N 处 / N%」类量化断言而无对应工具调用记录，则拦下并要求补自检输出。

**这是补 R3 的零覆盖缺口**——把治理从「写入时」扩展到「出口时」。

### 方案 C（P1）：长会话强制插入

在 `PreCompact` 与 `SessionStart` 已有钩子基础上，加**会话轮次计数**：单会话超过 N 轮（如 100）时，强制在回复前附带一次读数自证。

**为什么针对 R2**：纪律写在上下文最前面会被稀释，但「会话已进行 137 轮」这个事实是**新鲜的、每轮都会看到的**。

### 方案 D（P1）：记忆库检索口径统一

**问题**：想统计历史教训的人，搜「推翻/误读/证伪」会得出完全错误的结果（实测 3/67 vs 真实 46/68 命中）。
**改法**：`memory/` 条目统一加一个受控词表标签（如 `failure-mode: unverified-reading`），并在 MEMORY.md 顶部给出标签表与检索命令。

### 方案 E（P2）：审计报告一律标注时效三元组

每份「审计/梳理」报告头部必须带：**生成时间 / 扫描范围 / 校验方式**。引用其结论前必须比对当前字节。

**已有正面样本**：`log.md` 里「库侧真实历史（实测；我第一版判断被自己的证据推翻，留痕如下）」——把推翻过程留痕是好实践，值得制度化。

`.claude/hooks/block-dangerous-git.sh:50-52` 取远端名的 sed 是：

```
s/.*git[[:space:]]+(-[^[:space:]]+[[:space:]]+)*push[[:space:]]+//p
```

该模式要求 `git` 与 `push` 之间**只能夹以 `-` 开头的 token**。`git -C /path push …` 夹的是 `-C /path`，`/path` 不以 `-` 开头 → 整行匹配不上 → `REMOTE` 为空 → 第 53 行**回落到 `origin`** → 查本仓 origin（私有）→ 第 100 行 `exit 0` 放行。而 `-C` 指定的仓库与本仓毫无关系。

**本会话独立复现（阳性对照齐全）**：

| 命令 | 退出码 | 应然 |
|---|---|---|
| `cd /tmp/fakerepo2 && git push upstream main` | **2（拦）** | 2 ✅ |
| `git -C /tmp/fakerepo2 push upstream main` | **0（放行）** | 应为 2 ❌ |
| `git push -C /tmp/fakerepo2 upstream main` | **0（放行）** | 应为 2 ❌ |

机制直证（不靠推测）：

```
输入[git push upstream main]           → REMOTE解析=[upstream]      正确
输入[git -C /tmp/x push upstream main] → REMOTE解析=[空→回落origin]  漏
```

（`/tmp/fakerepo2` 的 upstream 指向公开仓 `ageerle/ruoyi-ai`，即铁律一明令禁止的目标。）

**严重度 P0**：这是本仓 19 条守卫中**唯一**守着「不可逆对外写入」的一条，也是《推送铁律一》的执行者。它漏了，意味着该铁律可被一句 `git -C` 架空。

**修复建议**：解析远端前先整体剥掉 `git [-C <dir>|-c k=v|--git-dir=<d>]*` 参数段；且 `-C`/`--git-dir` 指向的目录一旦不是本仓 REPO_ROOT，就按「未知仓库」处理、一律走阻断分支。

**旁证（同一守卫的正面表现）**：本会话在写复现脚本时，守卫把**测试命令自身**拦下了（命令文本含 `git push upstream main` 字面量），并正确识别目标为 `ageerle/ruoyi-ai`，留痕 `.harness/audit/blocked-2026-10-07.jsonl`。说明它对常规写法有效，**漏的只是分支**——正是 `silent-guard-omission-pattern` 描述的「判据写对了但漏一个分支，失败长得像成功」。
