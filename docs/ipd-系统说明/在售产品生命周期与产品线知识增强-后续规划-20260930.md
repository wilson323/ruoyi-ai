1. 给各产品线的 IPD 智能体提供「这条线已经在卖什么」的原始数据。

- 游客需求可进需求池并停在待指派。没有「对照已售型号，给出迭代建议并写回关联」这一步。

## 3. 新产品 IPD 要补的数据架构

新品过程继续走六阶段。要让该产品线的智能体用上历年数据，先补下面这些结构，再谈自动执行。

| 结构 | 作用 |
|---|---|
| 型号主档与项目分离 | 主档是已售型号；项目只表示一次迭代或一个确认后的新品缺口 |
| 15 条目录产品线 | 按主档产品线建空间，编码与现有三条空间分开 |
| 子品类 | 76 个子品类挂在对应产品线下，作为检索和需求归类的第二层 |
| 型号、客户型号 | 主档身份。同一产品型号可对应多个客户型号 |
| 规格槽位 | 39 种表头先归一成少量规格项，再给智能体比较。不把整表原列塞进提示词 |
| 产品线知识范围 | 检索键是产品线 + 型号，和项目文档检索分开 |
| 需求—型号关联 | 外部需求命中已售型号时，记下型号、建议类型（迭代 / 新品缺口 / 不采纳）和依据 |
| 市场与服务事实 | 销量、工单、故障、认证到期、竞品快照，每条带取证日期。没有事实就标缺失，不生成趋势 |

智能体在某条产品线上运行时，默认带上该线的子品类、型号规模和按需检索到的型号规格。不把 25,382 行整表放进每一次运行。

## 5. 在售产品生命周期（智能体接管市场动态）

主路径：

1. **在册。** 型号、客户型号、产品线、子品类、规格进入知识，状态视为已销售目录，不走六阶段。
2. **外部需求。** 需求进入需求池后，智能体对照主档。命中已售型号则生成迭代建议并关联该型号；未命中则标为新品缺口，等人确认后才开 IPD 项目。
3. **技术服务。** 工单、故障、退换按型号汇总，形成健康度。缺数据的维度保持为空。
4. **市场与竞争力。** 多维同时看：需求变化、服务成本、认证有效期、关键器件、竞品技术替代。每维有取证日期，按周期刷新。`IPD-LC07` 已有这组口径，后续改为读事实表，而不是在提示词里现编。
5. **人确认。** 采纳迭代则开一个项目，该项目才走六阶段。进入退市则走既有退市评审和 `IPD-LC08` 停产评估。目标设计：AI 提交可审核产物，人员确认后才由受控服务改状态。退市至少要能区分停止营销、停止接单、停止生产、备件与软件支持截止。当前 `Product` 实体没有这四段字段。2026-09-09 快照有 `retired_at`、`retirement_locked` 和 `product_retirements` 审批态，`Product.java` 未映射退市列。本轮未查库，不能写成已建表。
6. **回写。** 迭代上市或退市公告生效后，回写主档的规格、替代关系和目录状态，供下一次分析使用。

健康度与竞争力是一块持续运行的能力，不是某个项目阶段里的一张卡片。
