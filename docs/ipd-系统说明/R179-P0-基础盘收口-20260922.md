## 2. Task P0-2 解 5 个 live test skipped — ❌ 真阻塞（已根因，未假绿）

### 2.1 计划假设错在哪
计划 P0-2 Step3 写「环境型 skip：删 .skip 标记」。**实测：这些不是普通 `.skip`，删了会假绿/必红**。真实门禁机制分两类：
- `api/ipd/auth-live`、`api/ipd/project-live`：`describe.skipIf(!liveModeEnabled())` — `IPD_LIVE_ACCEPTANCE` **非空即可**激活。
- `views/ipd/{portal,ai-docs,auth}/*-live`：`process.env.IPD_LIVE_ACCEPTANCE === 'market-900103-existing-password'`（portal/ai-docs）或 `'market-900103-natural-expiry'`（views/auth）— **需精确值**。

首轮误用 `IPD_LIVE_ACCEPTANCE=1`，只激活前 2 文件，后 3 文件仍 skip（正确行为，非缺陷）。

### 2.2 真跑结果（正确 env 值）
- **单独跑 api/ipd/auth-live**（`market-900103-existing-password`）：`4 passed | 4 failed`。
- **5 文件连跑**（`=1`）：`19 failed`（auth-live 5 + project-live 14），portal/ai-docs/views-auth 仍 skip。

### 2.3 根因（两层，铁证）
**根因A — 登录限流器 5/60s（主因）**：
`IpdAuthController.java:50`：
```java
@RateLimiter(key = "#{#request.username()}", time = 60, count = 5, limitType = LimitType.IP,
    message = "登录尝试过于频繁，请稍后再试")
```
live test 每用例独立 login：auth-live 单文件 8 次 login、5 文件合计 23+ 次，**同用户名+IP 60秒内超 5 次即被限流**。实测失败用例的 Serialized Error：
```
{ status: 400, code: 10001, kind: 'http', envelopeMessage: '登录尝试过于频繁，请稍后再试', traceId: 'c3655b3f...' }
```
即 auth-live 前 5 次 login 过、第 6+ 次（refresh/envelope/allowlist 用例）被限流。**live test 设计与安全限流器根本冲突**。

**根因B — 限流响应契约错配（真 bug，影响真实用户）**：
后端限流返 **HTTP 400 + code 10001 + envelopeMessage '登录尝试过于频繁'**；但前端 `auth.ts:159-174` 的消息优先级：
```
loginCredential(仅 status===401 && code===10001) → messageFromCode(code) → HTTP状态兜底(429→'请求过于频繁')
```
限流是 **400**（非 401、非 429），loginCredential 不匹配、429 分支不匹配，落到 `messageFromCode(10001)` = **'输入信息不符合要求，请检查后重试'**，**覆盖掉后端真实的 '登录尝试过于频繁'**。
- 后果1：真实用户触发登录限流，看到的是「输入信息不符合要求」（误导），而非「登录尝试过于频繁」。
- 后果2：**code 10001 被"凭证错误"与"限流"复用语义冲突**（test「login 错误口令」期望 IPD_LOGIN_CREDENTIAL_TEXT='用户名或密码错误'，实得 '输入信息不符合要求'）。

### 2.4 为何不擅自修（owner 决策级）
- 根因A 修复需动**后端安全配置**（限流阈值/test-profile 豁免）→ 影响生产防爆破姿态 + 兄弟共享，需 owner 授权。
- 根因B 修复需动**前端核心 auth 映射 或 后端 code 语义**（限流独立 code / 返 429 / 前端尊重 envelopeMessage）→ 契约变更，共享高危。
- 改测试断言让其转绿 = AGENTS.md 明令禁止的**假绿**（「把断言改成现状能转绿但契约缺口仍在」）。

### 2.5 建议修复路径（交 owner/兄弟拍板）
1. **限流 vs live test**：①live test 改为复用单次 login token（不每用例重登）；或 ②dev/test profile 提高/豁免 login 限流阈值（owner 定）；或 ③每 login 间隔 ≥60s（不现实）。推荐 ①+②。
2. **契约错配**：后端限流独立业务码（不复用 10001）+ 前端 `messageFromCode` 尊重后端 envelopeMessage（或限流返 HTTP 429 对齐前端既有 429 分支）。
3. 修复前，live test 维持 `skipIf` 门禁（**禁止删 skip 假绿**）。
