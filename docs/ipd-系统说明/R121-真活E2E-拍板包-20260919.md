## 三、三案详述（请 owner 拍板）

### 方案 A（推荐）：先 owner 确认兄弟会话是否在跑任务 → kill PID 34560 → 起 IPD 后端连 ipd_dev → 跑 check-e2e-fe-be.sh → 收真活 E2E 报告

2. 若兄弟会话确认**不在跑**：
   - a. 起 IPD 后端：`mvn -o -pl ruoyi-modules/ruoyi-ipd spring-boot:run -Dspring-boot.run.profiles=dev &`（连 ipd_dev@13306）
   - b. 启前端 15666：`pnpm --filter @vben/web-antd run dev &`（在 ruoyi-ipd-web 仓）

**风险**：
- 若兄弟会话突然拉起 IPD 后端 → 本会话需要立刻让出（撞车 0 严守触发）
- 启动后端需要 30s-1min（MyBatis-Plus 启动 + 雪花 ID 分配）

**工作量**：1 hr（含 owner 确认 5 min + 起后端 5 min + 起前端 2 min + 跑脚本 1 min + 写报告 10 min + 容错 buffer 30 min）

## 四、推荐与理由

### 推荐：方案 A

**理由**：

1. **R119 病根 #4 必须真活闭环**——"自证能红"是机制下限（脚本写得对），"业务真活绿"是机制上限（5 项契约确实跑过）。R121 = 5 契约真活绿 = 治理轮首次全绿。
2. **撞车 0 红线可以 owner 协调解除**——R118 首次发现 PID 34560 是 14 天前，兄弟会话 owner 早就知道撞车 0 状态。一句话 ping 兄弟会话 = 5 min，不破坏 OPS-09。
3. **14 天撞车 0 持续是治理恶化信号**——R109-R118 4 轮 + R119 1 轮 = 5 轮治理报告都在"撞车 0 待 R121"上挂着。R121 必须有结论，否则撞车 0 = 永远 0。

### 不推荐 B 的核心理由

- 14 天撞车 0 + 方案 B = 永远撞车 0 = 治理恶化（撞车 0 本质是「兄弟会话没释放端口」+「本会话不主动抢」的双向协议）
- 但**方案 B 不是"不治理"**，而是「接受撞车 0 永久化」—— 这等同于承认兄弟会话永远在跑 IPD 后端任务，本会话永远不跑真活 E2E。这不是事实（兄弟会话迟早会停）。
- 选 B 的话，需要在 R121 拍板包上明确写「接受撞车 0 状态 + 14 天 + 永久」，作为治理轮结论。

### 不推荐 C 的核心理由（强调）

- C 等同于把 R119 病根 #4 的脚本**自我阉割**——R119 写脚本时专门强调「自证能红」是为了避免 R25 的"假绿失效"。C 是反向操作。
- C 改完后，**scripts/check-e2e-fe-be.sh 会从 R119 根除矩阵里的"✅ 激活"变为"❌ 失效"**，跟 R25 那 3 个失效脚本同类问题。这是治理倒退。
- C 也不是 B 的子集（B 是「不跑」，C 是「跑但不算 FAIL」），C 实际比 B 更糟（C 还消耗了写代码的时间）。
