# R39 根因反思报告 — 端点三向对账暴露的契约治理缺位

> **作者**:R39 治理轮 · 主协调会话
> **日期**:2026-09-18
> **触发**:用户原话"对于端点比对产品设计说明书、合同、及代码深度思考反思根源性原因"
> **方法**:三向对账门禁脚本 `scripts/check-contract-tri-source.sh`(R39 新增)+ 现查 grep 失衡比

---

## 1. 一句话结论

**工程合同层从未成为对账层** — RuoYi-AI 二开成 IPD 产品经理系统的过程中,后端 229 个 Controller 端点 / 前端 120 个 API mock / spec 26 个端点三方各自生长,**合同层(工程合同 DOC-01/05/业务决策确认)0 个 URL 字面量**,导致"端点层"的对账机制从设计层缺位,所有 mock 与实现的对齐全靠人工对账与事后修订。

这不是单点 bug,而是 R25 五病根框架的第 4 类"前后端契约无门禁"的**设计层表现**——门禁没建在契约层,而是事后补在了 Mock 字段、SQL 约束、HTTP 状态码等下游环节。

### 2.2 失衡比分析

```
spec(26) : contract(0) : backend(229) : frontend(120)
   1    :     0    :    8.8x   :   4.6x
```

**关键观察**:

1. **后端 229 个 vs spec 26 个 = 8.8x 超标**
   - 后端真活端点比 spec 多 203 个,**这些端点没有 spec 文档记录**,但 fe 仍按 120 个 mock 调用
   - 意味着:开发过程中有大量"spec 缺位但实现存在"的端点
   - 风险:任何 spec 重构(如 R37 路径前缀补 /v1/)都会漏改这 203 个

2. **contract 0 个 vs 其他三方 26~229 个**
   - 合同层完全没参与端点对账,合同从未约束过端点 URL
   - 工程合同(`DOC-01 业务决策确认`、`DOC-05 接口契约`)用的是**业务字段名 + 状态机描述**,没有 URL 模式
   - 这是 R39 用户原话"反思根源性原因"要抓的核心

3. **fe 120 个 vs be 229 个 = 53% 调用覆盖**
   - fe 调用端点 ⊂ be 实现端点(基本没看到 fe 调用 be 不存在的端点)
   - 但 be 有 **109 个端点没有 fe 调用**(`229 - 120`),即"后端有前端无",可能:
     - 内部 RPC / 定时任务 / 后台管理端
     - 预留但未实现前端入口
     - **孤儿端点**(R39 Agent D 评审分类中"A 类 P0 必须修")

4. **spec 26 个 vs fe 120 个 vs be 229 个**
   - spec 是 fe 子集(spec 26 ⊂ fe 120)
   - fe 是 be 子集(fe 120 ⊂ be 229)
   - 但**没有任何源头能闭环对账**,fe 调用 be 没实现的、be 实现 spec 没记的、contract 全程缺位

## 3. R39 用户原话"反思根源性原因"——五病根映射

### 病根 ①:测试假绿(改主代码后测试没跟上)

**映射证据**:
- 229 个 be 端点有 203 个在 spec 之外
- spec 重构 R37(`附录 D.0.6 路径前缀补 /v1/ 一致化`)只补了 spec 26 个,**没补 be 203 个**
- 测试全绿(因为测试断言了"现状"而不是"契约",见 AGENTS.md 「构建/测试」假绿陷阱)

**根因**:
> **测试基线锚错了对象** — 测试断言的是"实现行为",不是"契约行为"。当 spec 是唯一事实源时,测试应该断言"fe 调用 → be 返回"符合 spec,但实际断言的是"现状自洽"。

### 病根 ②:提交不完整(引用了 untracked 文件,fresh clone 必炸)

**映射证据**:
- 合同层没 URL 字面量 = 合同从未"提交完整"
- 后端 203 个 spec 外端点 = "未跟踪"的实现
- 工程合同 owner 在 AGENTS.md 已授权勘误级更新,但**没有"合同必须包含端点 URL"的强制约束**

**根因**:
> **"什么算完成"的标准没有量化锚点** — AGENTS.md / CLAUDE.md / DOC-01/05 都没明文说"每个端点必须在 spec/contract/be/fe 四个来源至少出现 N 次",所以开发过程是"先把代码写了,文档后补",但"文档后补"这一步**没有门禁触发**。

### 病根 ③:规则表与接线点靠人肉对账

**映射证据**:
- 三向失衡比 8.8x / 0 / 4.6x 是**纯人工**发现的,R39 之前没人发现
- "后端有前端无"的 109 个孤儿端点是 Agent D 人工分类才暴出来
- 没有任何 SQL 表 / GitHub Issue / 自动化脚本能产生"端点失衡比"这个指标

**根因**:
> **对账机制全在会话上下文里,没沉淀到数据层** — 智能体每次都"重新发现",没有 `endpoint_inventory.sql` 之类的真相源(只在三向对账脚本的 TEMP_DIR 里存在,运行结束就消失)。

### 病根 ④:前后端契约无门禁

**映射证据**(本次 R39 的核心抓手):
- contract 0 个 URL 字面量 = 契约层从设计就缺位
- 现有的 `scripts/check-api-contract-fe-be.mjs` 只对账 **be ↔ fe**,没对账 **be ↔ spec**、**spec ↔ contract**
- `scripts/check-doc-db-drift.sh`(R37)是表名漂移对账(be ↔ spec 表名),但**没做端点 URL 对账**
- R39 新增 `scripts/check-contract-tri-source.sh` 是**第一个**把 spec ↔ contract ↔ be ↔ fe 四向接上的门禁

**根因**:
> **门禁建在了错误的层** — R37 把表名对账建在"doc ↔ db"层,R38 把 fe/be 对账建在"api ↔ route"层,**没有人把对账建在"合同层 ↔ 实现层"**——这是契约缺位的工程表现。

### 病根 ⑤:多事实源无对账

**映射证据**:
- spec(26) / contract(0) / be(229) / fe(120) = 4 个事实源,**相互不知道彼此存在**
- 文档(map.json)、看板镜像、SSOT 都只追踪"任务有没有完成",不追踪"端点有没有对齐"
- 三向对账脚本首次跑出 R42 主仓真实数据,但**没有任何看板卡片**记录"端点失衡比 8.8x"

**根因**:
> **SSOT 不含端点** — SSOT 看板(`docs/ipd-系统说明/开发计划-看板镜像.md`)只追踪"任务状态",不追踪"实现 ↔ 契约的对齐状态"。端点是系统的血脉,但不在 SSOT 视野内。

## 6. 限制与风险

### 6.1 R39 脚本局限

- **worktree 是 R38 起点**,缺 `ruoyi-ipd` 模块 / `docs/开发说明/spec/` 端点 / Controller,**脚本在 worktree 跑空**
- **修复路径**:`BACKEND_CTRL_DIR` 改为 `ruoyi-modules/ruoyi-ipd/src/main/java/org/ruoyi/ipd/controller/`(主仓路径),并在主仓跑一次拿真数据
- **不在 R39 主仓写文件**(违反 AGENTS.md + 撞兄弟会话),只在 worktree 保留脚本,等兄弟会话合流

### 6.2 失衡比可能掩盖的真相

- 229 个后端端点可能含 100+ 个 **CRUD 基类自动生成**(`RuoYi-Vue-Plus` 框架的 `BaseController`),真活业务端点可能只有 50~80 个
- 120 个前端 API 可能含 80+ 个**未启用的 mock**(`// TODO` / `disabled: true`)
- **真实失衡比需排除框架生成与 mock 占位后重算**,这是 R40+ 工作

### 6.3 不在 R39 范围

- 不修 fe mock 与 be 实现的具体不匹配(那是 R40+ 的 P1/P2 工作)
- 不改 spec / contract 内容(违反 G-04 产品设计圣经不可改)
- 不动测试基线(R40+ 工作)
- 不动 SSOT 看板(R40+ 工作)
