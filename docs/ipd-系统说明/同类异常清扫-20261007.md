## 4 · 静默降级 / 失败放行（fail-open）

按「判据是『查不到』还是『查失败』」分类。**关键区分：查不到 = 判定结果；查失败 = 判不出来，不该按判定结果处理。**

### 4.1 ⚠️ `GateElementResultService.java:231-240` — 查失败被当查不到

```java
private int resolveMinCustomerVerifications() {
    if (businessConfigService != null) {
        try {
            return businessConfigService.getInt(MIN_VERIFICATION_KEY);
        } catch (Exception ex) {
            // fall through        ← 异常被吞，无日志
        }
    }
    return systemConfigService.getIntValue(MIN_VERIFICATION_KEY, 5);
}
```

`getInt` 抛异常（配置服务不可用 / DB 抖动）时静默落到默认值 5，**catch 块内无任何 log**。这是 G1-1 客户一手验证的**通过阈值**——阈值被静默改动直接影响 Gate 能否通过。属 fail-open。

**修法**：catch 内 `log.warn` 记录异常 + 失败原因（配置项 key、异常类型），让降级可观测。

### 4.2 ✅ `GateEngine.java:166-189` — 已改 fail-closed（正面案例）

`:202-205` javadoc 记录：`2026-10-07 改 fail-closed`，原实现 catch 后「按无记录处理」= 查询失败当没有 Gate = 放行。现已改为「判不出来 → 拦停 + 提示重试」。`:174-177` 的「无评审记录 → 放行」是**正确的"查不到"判定**，两者已正确区分。

### 4.3 ✅ `IpdKnowledgeAccessGate.java:124-136` — 有意 fail-closed

catch `SaTokenException` / `Exception` 均 `return null`，`:132-133` 明写「会话侧任何意外……都不得把 profile 装配变成放开」并 `log.warn`。降级方向 = 收紧，正确。

### 4.4 其他 catch-return（阴性）

`IpdIdorGuard:325`（`currentTenantId`，javadoc `:314-319` 说明无 Sa-Token 上下文按"租户上下文缺失"处理）、`SystemConfigServiceImpl:276,288`、`SwitchingAcceptanceService:510`、`HandoverService:763`、`AiSuggestionService:315,718`、`StageActionService:717`（`NumberFormatException` → null）、`DeletionRequestServiceImpl:725`、`KpiSharedReconcileService:334`——均为**框架/工具层或纯解析**，非业务判定路径，或判据确为"查不到"。

`NodeAgentResolver:67`、`EndpointUrlValidator:83`、`AiGateway:472`、`DeepDirectExecutor:177`（`:177` 注释明写「非数值不猜、不默认 0——由上层成对/非空校验拦下」）——**有意为之，有注释依据**。
